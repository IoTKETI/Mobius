Mobius 3.0.1 · Guide

From installation to everyday use

Mobius is an IoT server platform that implements the oneM2M international standard. This guide explains what Mobius is and how it is built inside, in what order to install it, how to start it, and how to use it in practice.

Version
3.0.1
Runtime
Node.js
Database
MySQL · SQLite
Request binding
HTTP

01 — Introduction

Introduction

What Mobius is

Mobius receives the data an IoT device sends, stores it, and opens it up so that applications can fetch it.

Built ad hoc, every such server ends up with its own address scheme, its own data shape and its own way of handling permissions. oneM2M is the international standard that settles those questions, and Mobius implements the topmost server role in it, the IN-CSE (Infrastructure Node — Common Services Entity). Because it follows the standard, devices and applications written for Mobius work against any other oneM2M platform.

Mobius is written in Node.js and its source is open. It stores resources in MySQL or SQLite; which one it uses is a single setting.

In one line

Devices push, applications pull, and Mobius sits between them handling storage, identity and notifications.

Where it sits

Mobius is middleware between devices and applications. A device uploads data and Mobius stores it; an application reads that data through the standard REST API. In the other direction, when an application writes a control value, a device that subscribed to that resource receives a notification.

The tree is the address

oneM2M data is stored as a tree, like a file explorer, and the path through that tree is the URL. Creating a resource does not mean writing an API for it: the moment it exists, it has an address.

Because of this, no separate API design is needed. A container may hold another container, and there is no depth limit. Every resource carries the attributes the standard defines — creation time (ct), name (rn), expiration time (et), access policy (acpi) and so on.

Resource types

These are the resource types Mobius can create. The ty number goes in the request's Content-Type to say what is being created.

tyNameWhat it does
1accessControlPolicyDecides who may do what
2AEOne device or application. Its entry point into the tree
3containerHolds data, with optional retention limits
4contentInstanceOne reading. Written once, never modified
5CSEBaseRoot of the tree — Mobius itself
9groupTreats several resources as one
10locationPolicyHow location data is collected
13mgmtObjDevice management objects (firmware, battery, device info)
14nodeA physical node
16remoteCSEAnother CSE this one is registered with
23subscriptionWatches for change and sends notifications
24semanticDescriptorSemantic annotation
27multimediaSessionMultimedia session
28flexContainerContainer with freely defined attributes
91–98hd_*Home-domain moduleClasses — lighting, colour, door lock, temperature, battery
On SQLite

The SQLite backend handles six types: accessControlPolicy, AE, container, contentInstance, CSEBase and subscription. Creating any other type is refused with 501 before anything is written, so the tree is never left half-built. Run on MySQL if you need them all.

02 — Architecture

Architecture

Mobius divides its modules along the path a single request takes. Knowing that path tells you which file to open.

The path of a request

An incoming HTTP request passes through these stages. Each does its own part and hands over.

Two rules hold this flow together. Sending the response and returning the database connection happen exactly once per request, and response bytes leave from one place only, responder.js. Sending twice, or not at all, would strand a connection, so both rules are enforced structurally rather than by convention.

How the modules divide

The files you will open most often.

FileResponsibility
mobius.jsEntry point. Sequences configuration, port check, boot record and server start
app.jsHTTP server and routing. Forks the workers and receives requests
mobius/resource.jsThe core of resource handling: per-type attribute checks, create and update
mobius/sql_action.jsWhere every SQL statement is built, with values passed as bindings
mobius/db/Database facade, backend adapters and schema files
mobius/security.jsAccess control: may this requester touch this resource
mobius/sgn.js · sgn_man.jsFinds subscriptions, builds the notification and sends it over HTTP, CoAP or MQTT
mobius/responder.js · shape.jsThe single response exit, and where the response body is assembled
mobius/settle.jsPer-request settler that makes the response and the connection return happen once
mobius/conf_load.js · conf_schema.jsReads the configuration, and the single source of which settings exist
tools/First-run wizard, settings commands, schema migration runner
admin/Admin console, run as its own process

Master and workers

Mobius forks one worker per CPU core and spreads requests across them. The master handles no requests; it runs two periodic jobs.

  • Retention sweep — removes data beyond a container's count or size limit, oldest first. It re-counts the live rows before deleting, so an inflated stored counter cannot cause it to delete data that is within the limit.
  • Counter reconciliation — brings each container's stored count and size back in line with the data.

If a worker dies unexpectedly the master starts a replacement. When it dies for a configuration reason — port already in use, no configuration file, broken seal — the master does not respawn it and exits with the same code, so a problem that needs fixing is not papered over by restarts.

The database layer

Building SQL and running it are separate jobs. sql_action.js builds the statement; the facade in mobius/db/ hands it to the adapter for whichever backend is selected. Core code does not know whether it is running on MySQL or SQLite.

That is why switching backends is one setting, and adding one is a matter of dropping in a single mobius/db/<name>.js file. Every value travels as a binding, which is what makes SQL injection through discovery parameters structurally impossible.

Directory layout

Mobius/
mobius.js            # entry point — this is what you run
app.js               # HTTP server, workers, routing
package.json         # dependencies and npm commands
conf.json            # settings (written on first start)

mobius/              # the core
  resource.js        # resource handling
  sql_action.js      # SQL construction
  security.js        # access control
  sgn.js sgn_man.js  # subscription notifications
  responder.js       # response exit
  conf_load.js …     # configuration loading
  ae.js cnt.js …     # one file per resource type
  db/
    index.js         # backend facade
    mysql.js         # MySQL adapter
    sqlite.js        # SQLite adapter
    mobiusdb.sql     # MySQL schema — import this at install time
    mobiusdb_sqlite.sql

tools/               # setup wizard, settings commands
admin/               # admin console (separate process)
log/                 # access log and boot record

03 — Installation

Installation

What you need

ComponentRequiredNotes
Node.jsYesThe runtime Mobius executes on. An LTS release is recommended
MySQLOptionalThe production store. Needed if you want every resource type
SQLiteAutomaticComes with the module install; nothing to set up separately
MQTT brokerOptionalOnly if notifications go to mqtt:// addresses (Mosquitto or similar)
Trying it for the first time

Start with SQLite. There is no database server to install and the store is created on the first start. Node.js is all you need.

Order of work

Installing Node.js

Download an LTS release from nodejs.org and install it. Then check that both commands print a version.

terminal
node -v
npm -v

The database

Using SQLite

Nothing to do. The next step's npm install brings in the SQLite module, and the store file and its tables are created on the first start.

Using MySQL

Install a MySQL server, create one database and import the schema file. That single import is the whole install — the file carries the tables, the indexes and the migration ledger, so nothing is left to apply afterwards.

terminal
# 1. create the database
mysql -u root -p -e "CREATE DATABASE mobiusdb DEFAULT CHARACTER SET utf8mb3;"

# 2. import the schema (from the Mobius source folder)
mysql -u root -p mobiusdb < mobius/db/mobiusdb.sql

With a tool such as MySQL Workbench, create the mobiusdb schema and use Data Import → Import from Self-Contained File with mobius/db/mobiusdb.sql. The result is the same.

Database name

The default is mobiusdb. To use another name, run npm run conf -- set dbName <name> after installing.

MQTT broker (optional)

If notifications will go to mqtt:// addresses you need a broker. Install Mosquitto and start its service. If notifications only go over HTTP, you can skip this.

Source and modules

  1. Get the source

    terminal
    git clone https://github.com/IoTKETI/Mobius.git
cd Mobius

    Without Git, download the ZIP from the GitHub page and unpack it.

  2. Install the modules

    terminal
    npm install

    A node_modules folder appears. There is no build step, so this is the end of the installation.

04 — Running

Running

First start

When there is no conf.json, Mobius runs the setup wizard itself. No separate install command is needed.

terminal
node mobius.js

It asks seven questions, writes the answers to conf.json, and then starts.

QuestionDefaultNotes
Databasemysqlmysql or sqlite
DB password—Asked only for MySQL. Hidden while you type
CSE nameMobiusRoot of the tree. Every address begins with /<name>
CSE-ID/Mobius2Identifier of this CSE
SP-ID//keti.re.krService provider identifier
Super-user originSpondeA request with this origin skips every access check
HTTP port7579The port the server listens on
The super-user origin is a master key

Put that value in a request header and every access check is skipped. On a server reachable from outside, replace the default with something hard to guess and limit who knows it.

With the CSE name left at Mobius and the port at 7579, the root of the tree is now http://localhost:7579/Mobius.

Starting it again

terminal
node mobius.js          # using conf.json
npm start               # the same command

node mobius.js sqlite   # force SQLite this time
node mobius.js mysql    # force MySQL this time
Running as a service

Started first under pm2 or systemd, where there is no terminal, Mobius cannot run the wizard, so it exits without writing a configuration file. Run it once from a terminal to create conf.json, then put it under the supervisor.

Check that it is up

Read the root resource. A response means the server is healthy.

terminal
curl -i http://localhost:7579/Mobius \
  -H "Accept: application/json" \
  -H "X-M2M-RI: check1" \
  -H "X-M2M-Origin: Sponde"
response
HTTP/1.1 200 OK
X-M2M-RSC: 2000
Content-Type: application/json

{"m2m:cb": {"rn": "Mobius", "ty": 5, "csi": "/Mobius2", …}}

X-M2M-RSC: 2000 is the oneM2M success code. It is separate from the HTTP status, so read both.

Reading and changing settings

Settings are handled by command, not by a web page. conf.json holds the database password and the super-user value, so it is deliberately kept to whoever can reach the server.

terminal
npm run conf                      # the whole list with applied state
npm run conf -- csebaseport       # one key in detail
npm run conf -- set cseBase Vita  # change a value
npm run conf -- unset maxBodyBytes # back to the default
npm run conf -- edit              # walk through the main keys again
npm run conf -- --all             # include advanced keys

npm run status                    # is it up, is a restart pending

Settings are read once at startup. After changing a value you must restart, and the npm run conf listing tells you which keys are waiting for one.

Keys that would cut off existing devices if set wrongly — the CSE name, the port — are marked as gated. Changing one prints a warning and asks you to type the key name before it is written.

Sealed secrets

The database password and the super-user value are changed through the tool only. Edit either of them by hand in conf.json and the next start refuses to run. A companion file, conf.seal.json, holds a fingerprint of the two and catches the mismatch.

terminal
npm run setup -- --dbpass      # re-enter the DB password
npm run setup -- --superuser   # re-enter the super-user origin

At either prompt, pressing Enter keeps the current value and just recreates the seal. If you are coming from an older version and have no seal yet, do this once.

Admin console

An operator screen that runs from the same repository as a separate process. It finds and removes expired resources and resources whose parent is gone, reviews access policies, and shows subscription state and statistics.

terminal
# set a password first — without one the console will not start
npm run conf -- set adminPassword 'your-password'

# start the console
node admin/server.js

# or let Mobius start it as a child of the master
npm run conf -- set adminAutoStart on

Settings and process control are deliberately not in the console; both are command-line work.

When it will not start

Mobius distinguishes why it could not start by exit code, so that it never sits alive but unable to serve.

CodeMeaningWhat to do
12Port already in useStop the other process or change csebaseport
13No conf.jsonRun node mobius.js once from a terminal to create it
14Secret seal does not matchRecreate it with npm run setup -- --superuser
1Could not reach the databaseCheck the DB is up and the password and database name are right

Per-request timing is not printed to the console; it is the last field of log/access-*.log. The configuration a running server actually applied is recorded in log/mobius-boot.jsonl, which is what npm run status reads.

05 — Usage

Usage

The examples below work as written if you run them in order. They assume a server at localhost:7579 with the CSE named Mobius.

The shape of a request

Every request carries two headers.

HeaderPurpose
X-M2M-RIRequest identifier. Any value, different per request; it comes back in the response
X-M2M-OriginWho is asking. Access control decides on this value
Content-TypeOnly when creating: application/json; ty=<number> says what to create
Acceptapplication/json. Mobius speaks JSON only

Registering an AE

A device or application first registers as an AE — its entry point into the tree. Send exactly S as the origin and Mobius generates an identifier for it.

create an AE
curl -X POST http://localhost:7579/Mobius \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-ae-1" \
  -H "X-M2M-Origin: S" \
  -H "Content-Type: application/json; ty=2" \
  -d '{"m2m:ae": {"rn": "myAE", "api": "A.company.myapp", "rr": true}}'
response (201 · RSC 2001)
{"m2m:ae": {
  "rn": "myAE",
  "ty": 2,
  "aei": "S2026090812345601a3",   <-- keep this value
  "ri":  "2-2026090812345601a3",
  …
}}

The returned aei is this AE's identity. Put it in X-M2M-Origin for every later request from this AE. If you want a specific identifier, send that instead of S and it is used as the aei.

  • rn — resource name; it becomes a segment of the address
  • api — application identifier required by the standard
  • rr — whether this AE can receive requests

Creating a container

A container holds data. Create it under the AE.

create a container
curl -X POST http://localhost:7579/Mobius/myAE \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-cnt-1" \
  -H "X-M2M-Origin: S2026090812345601a3" \
  -H "Content-Type: application/json; ty=3" \
  -d '{"m2m:cnt": {"rn": "temperature", "mni": 1000}}'

mni is how many entries this container keeps. Beyond that, the master's retention sweep removes the oldest. To limit by size instead, give mbs in bytes. Without either, entries accumulate essentially without bound.

Storing and reading data

Readings go in as a contentInstance. It is written once and never modified, so the normal pattern is one per measurement.

store one reading
curl -X POST http://localhost:7579/Mobius/myAE/temperature \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-cin-1" \
  -H "X-M2M-Origin: S2026090812345601a3" \
  -H "Content-Type: application/json; ty=4" \
  -d '{"m2m:cin": {"con": "23.5"}}'

con is the content, and it is a string — to store JSON, put it in as a string.

Reading the latest

most recent reading
curl http://localhost:7579/Mobius/myAE/temperature/la \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-la-1" \
  -H "X-M2M-Origin: S2026090812345601a3"

la is the latest, ol the oldest. This is the address a dashboard uses most often to show a current value.

Reading the container itself

container state
curl http://localhost:7579/Mobius/myAE/temperature \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-cnt-2" \
  -H "X-M2M-Origin: S2026090812345601a3"

In the response, cni is how many entries it holds and cbs their total size in bytes.

Discovery

To find out what exists, walk the tree. With fu=1 the response is a list of addresses for the resources that match.

find every container
curl "http://localhost:7579/Mobius?fu=1&ty=3" \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-dis-1" \
  -H "X-M2M-Origin: Sponde"
response
{"m2m:uril": ["Mobius/myAE/temperature", "Mobius/myAE/humidity"]}
FilterMeaningExample
tyResource typety=3 · ty=3&ty=4
rnExact resource namern=temperature
lblCarries this labellbl=outdoor
cra · crbCreated after · beforecra=20260101T000000
lvlHow deep to walklvl=2
lim · ofstLimit · offsetlim=100&ofst=100
When the result is truncated

A response with X-M2M-CTS: 1 means there is more, and X-M2M-CTO is the ofst to use next. Those two let you page to the end.

Subscriptions and notifications

To be told whenever a new value arrives, attach a subscription and put the address to notify in nu.

create a subscription
curl -X POST http://localhost:7579/Mobius/myAE/temperature \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-sub-1" \
  -H "X-M2M-Origin: S2026090812345601a3" \
  -H "Content-Type: application/json; ty=23" \
  -d '{"m2m:sub": {
        "rn": "watch",
        "nu": ["http://192.168.0.10:9000/noti"],
        "nct": 2
      }}'

Every new value in that container now POSTs to that address. nu is an array, so a subscription can notify several places, and the scheme of each address decides how it is sent.

AddressHow it is delivered
http://…HTTP POST. The receiver's response is read and logged as accepted, rejected or failed
mqtt://…MQTT publish; needs a broker configured
coap://…CoAP request
Notifications are send-and-forget

Mobius does not retry a notification, and does not delete a subscription because delivery failed. If the receiver is briefly down, that notification is gone. For values you cannot miss, have the application poll la as a backstop.

Access control

By default requests are not filtered by who sent them. To decide who may touch a resource, create an accessControlPolicy and attach it.

create a policy
curl -X POST http://localhost:7579/Mobius \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-acp-1" \
  -H "X-M2M-Origin: Sponde" \
  -H "Content-Type: application/json; ty=1" \
  -d '{"m2m:acp": {
        "rn": "readonly",
        "pv":  {"acr": [{"acor": ["S2026090812345601a3"], "acop": 51}]},
        "pvs": {"acr": [{"acor": ["Sponde"], "acop": 63}]}
      }}'

acop is the sum of the operations you allow.

ValueOperationValueOperation
1CREATE8NOTIFY
2RETRIEVE16DELETE
4UPDATE32DISCOVERY

So 51 is create, retrieve, delete and discovery (1+2+16+32), and 63 is everything. pv governs the resources the policy is attached to; pvs governs who may change the policy itself.

Attach it to the container.

attach the policy
curl -X PUT http://localhost:7579/Mobius/myAE/temperature \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-acp-2" \
  -H "X-M2M-Origin: Sponde" \
  -H "Content-Type: application/json" \
  -d '{"m2m:cnt": {"acpi": ["/Mobius/readonly"]}}'

From now on only requesters the policy allows can use that container. To see what a policy would block before attaching it, the admin console's access-policy screen can simulate it.

Reading response codes

Responses carry both an HTTP status and a oneM2M result code (X-M2M-RSC). These are the ones you will meet.

RSCHTTPMeaning
2000200Retrieve, update or delete succeeded
2001201Created
2002200Deleted
2004200Updated
4000400Bad request — check the body and the headers
4004404No such resource
4103403An access policy refused it
4105409Something with that name already exists
5000500Something went wrong inside — check the log
5001501The current backend does not handle that type

A failed response carries the reason in m2m:dbg as a single line. Read that line first.

Where to go next

If you use Postman, collecting these requests is worth the few minutes. Put the server address and the CSE name in environment variables and you will not have to retype them.

The source and the latest changes are in the GitHub repository. For the standard itself, see the specifications at oneM2M.
