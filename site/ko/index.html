Mobius 3.0.1 · 가이드

설치부터 활용까지

Mobius는 oneM2M 국제 표준을 구현한 IoT 서버 플랫폼입니다. 이 문서는 Mobius가 무엇이고 안이 어떻게 생겼는지, 어떤 순서로 설치하고 어떻게 띄우며, 실제로 어떻게 쓰는지를 차례대로 설명합니다.

01 — 소개

Mobius 소개

Mobius란 무엇인가

Mobius는 사물인터넷 기기가 보낸 데이터를 받아 저장하고, 그 데이터를 애플리케이션이 가져갈 수 있게 열어 주는 서버 소프트웨어입니다.

이런 서버를 각자 만들면 기기마다 주소 규칙도, 데이터 모양도, 권한 처리 방식도 달라집니다. oneM2M은 그 부분을 국제 표준으로 정해 둔 규격이고, Mobius는 그 표준에서 가장 위에 있는 서버 역할인 IN-CSE(Infrastructure Node — Common Services Entity)를 구현한 것입니다. 표준을 따르므로 Mobius에 맞춰 만든 기기와 애플리케이션은 다른 oneM2M 플랫폼에서도 그대로 동작합니다.

Mobius는 Node.js로 작성되었고 소스가 공개되어 있습니다. 저장소는 MySQL 또는 SQLite를 쓰며, 어느 쪽을 쓸지는 설정 한 줄로 고릅니다.

한 줄 요약

기기는 데이터를 올리고, 애플리케이션은 가져가고, Mobius는 그 사이에서 저장·인증·알림을 맡습니다.

어디에 놓이는가

Mobius는 기기와 애플리케이션 사이에 놓이는 미들웨어입니다. 기기가 데이터를 올리면 Mobius가 저장하고, 애플리케이션은 표준 REST API로 그 데이터를 조회합니다. 반대로 애플리케이션이 제어 값을 쓰면 그 변화를 구독하고 있던 기기가 알림으로 받습니다.

리소스 트리가 곧 주소다

oneM2M의 데이터는 파일 탐색기처럼 트리로 쌓입니다. 그리고 그 트리의 경로가 그대로 URL이 됩니다. 리소스를 하나 만들면 그것을 읽고 쓰는 API가 따로 만들어지는 것이 아니라, 만든 순간 주소가 생깁니다.

이 구조 덕분에 별도의 API 설계가 필요 없습니다. 컨테이너 아래에 컨테이너를 또 만들 수 있고 깊이 제한도 없습니다. 각 리소스에는 표준이 정한 속성이 붙습니다 — 만든 시각(ct), 이름(rn), 만료 시각(et), 접근 정책(acpi) 같은 것들입니다.

다루는 리소스 타입

Mobius가 만들 수 있는 리소스 타입입니다. ty 번호는 요청의 Content-Type에 붙여 무엇을 만들지 알려 주는 값입니다.

SQLite로 돌릴 때

SQLite 백엔드는 accessControlPolicy · AE · container · contentInstance · CSEBase · subscription 여섯 타입을 다룹니다. 나머지 타입을 만들려고 하면 저장을 시도하지 않고 501로 거절하므로 트리가 반쯤 만들어진 상태로 남지 않습니다. 모든 타입이 필요하면 MySQL로 띄우십시오.

02 — 구조

내부 구조

Mobius는 요청 하나가 지나가는 길을 기준으로 모듈이 나뉩니다. 무엇을 고칠 때 어디를 열어야 하는지는 이 길을 알면 정해집니다.

요청이 지나가는 길

HTTP 요청이 들어오면 다음 순서로 지나갑니다. 각 단계는 자기 몫만 하고 다음으로 넘깁니다.

두 가지 규칙이 이 흐름을 지킵니다. 응답을 내보내고 데이터베이스 커넥션을 돌려주는 일은 요청마다 정확히 한 번 일어나고, 응답 바이트가 나가는 자리는 responder.js 한 곳뿐입니다. 응답을 두 번 보내거나 빠뜨리면 커넥션이 묶인 채 남기 때문에 이 두 규칙을 구조로 고정해 두었습니다.

모듈이 나뉜 기준

자주 열어 보게 되는 파일들입니다.

파일맡은 일
mobius.js진입점. 설정 읽기 → 포트 확인 → 부팅 기록 → 서버 실행 순서만 잡는다
app.jsHTTP 서버와 라우팅. 워커를 만들고 요청을 받는다
mobius/resource.js리소스 조작의 핵심. 타입별 속성 검사와 생성·갱신 동작
mobius/sql_action.js모든 SQL을 만드는 곳. 질의 빌더로 조립하고 값은 바인딩으로 넘긴다
mobius/db/데이터베이스 파사드와 백엔드 어댑터, 스키마 파일
mobius/security.js접근 정책 검사. 요청자가 그 리소스를 다룰 수 있는지 판단한다
mobius/sgn.js · sgn_man.js구독을 찾아 알림 본문을 만들고, HTTP·CoAP·MQTT로 보낸다
mobius/responder.js · shape.js응답을 내보내는 유일한 출구와 응답 본문을 만드는 곳
mobius/settle.js요청 하나의 정산기. 응답 전송과 커넥션 반납을 한 번만 하게 만든다
mobius/conf_load.js · conf_schema.js설정을 읽어 들이는 곳과, 어떤 설정 키가 있는지의 단일 기준
tools/첫 설치 마법사, 설정 명령, 스키마 마이그레이션 러너
admin/관리 콘솔. 별도 프로세스로 뜬다

마스터와 워커

Mobius는 CPU 코어 수만큼 워커 프로세스를 만들어 요청을 나눠 처리합니다. 마스터는 요청을 처리하지 않고 두 가지 주기 작업만 맡습니다.

  • 보관 한도 정리 — 컨테이너에 정한 개수·용량 한도를 넘은 오래된 데이터를 지웁니다. 지우기 전에 실제 개수를 다시 세므로, 저장된 카운터가 부풀어 있어도 살아 있는 데이터를 지우지 않습니다.
  • 카운터 정합 — 컨테이너가 들고 있는 개수·용량 값을 실제 데이터와 맞춥니다.

워커가 예기치 않게 죽으면 마스터가 다시 띄웁니다. 다만 설정 문제로 죽은 경우 (포트가 이미 쓰이는 중, 설정 파일 없음, 봉인 불일치)에는 다시 띄우지 않고 같은 코드로 함께 종료합니다. 고쳐야 할 문제를 재시작으로 덮지 않기 위해서입니다.

데이터베이스 계층

SQL을 만드는 곳과 실행하는 곳이 분리되어 있습니다. sql_action.js가 질의를 만들면 mobius/db/의 파사드가 지금 고른 백엔드의 어댑터에 넘겨 실행합니다. 코어 코드는 자기가 MySQL 위에서 도는지 SQLite 위에서 도는지 모릅니다.

그래서 백엔드를 바꾸는 일이 설정 한 줄이고, 새 백엔드를 붙이는 일은 mobius/db/<이름>.js 파일 하나를 두는 일이 됩니다. 값은 전부 바인딩으로 넘어가므로 탐색 질의 파라미터를 통한 SQL 주입이 구조적으로 생기지 않습니다.

디렉터리 구조

Mobius/
mobius.js            # 진입점 — 이 파일을 실행한다
app.js               # HTTP 서버 · 워커 · 라우팅
package.json         # 의존 모듈과 npm 명령
conf.json            # 설정 (첫 실행 때 만들어진다)

mobius/              # 코어
  resource.js        # 리소스 조작의 핵심
  sql_action.js      # SQL 조립
  security.js        # 접근 정책
  sgn.js sgn_man.js  # 구독 알림
  responder.js       # 응답 출구
  conf_load.js …     # 설정 로딩
  ae.js cnt.js …     # 리소스 타입별 처리
  db/
    index.js         # 백엔드 파사드
    mysql.js         # MySQL 어댑터
    sqlite.js        # SQLite 어댑터
    mobiusdb.sql     # MySQL 스키마 — 설치 때 이 파일을 넣는다
    mobiusdb_sqlite.sql

tools/               # 설치 마법사 · 설정 명령
admin/               # 관리 콘솔 (별도 프로세스)
log/                 # 액세스 로그와 부팅 기록

03 — 설치

설치

준비물

무엇필요한가설명
Node.js반드시Mobius를 실행하는 런타임. LTS 버전을 권합니다
MySQL선택운영용 저장소. 모든 리소스 타입을 다루려면 필요합니다
SQLite자동모듈 설치 때 함께 들어옵니다. 따로 설치할 것이 없습니다

처음 써 본다면

SQLite로 시작하십시오. 데이터베이스 서버를 설치할 필요가 없고, 첫 실행 때 저장소가 자동으로 만들어집니다. Node.js만 있으면 됩니다.

설치 순서

Node.js 설치

nodejs.org에서 LTS 버전을 받아 설치합니다. 설치가 끝나면 터미널에서 버전이 찍히는지 확인합니다.

터미널
node -v
npm -v

데이터베이스

SQLite로 쓸 때

할 일이 없습니다. 다음 단계의 npm install로 SQLite 모듈이 들어오고, 첫 실행 때 저장소 파일과 표가 자동으로 만들어집니다.

MySQL로 쓸 때

MySQL 서버를 설치한 뒤 데이터베이스를 하나 만들고 스키마 파일을 넣습니다. 이 한 번으로 설치가 끝납니다 — 스키마 파일이 표와 인덱스, 마이그레이션 이력까지 담고 있어서 따로 적용할 것이 남지 않습니다.

터미널
# 1. 데이터베이스를 만든다
mysql -u root -p -e "CREATE DATABASE mobiusdb DEFAULT CHARACTER SET utf8mb3;"

# 2. 스키마를 넣는다 (Mobius 소스 폴더에서)
mysql -u root -p mobiusdb < mobius/db/mobiusdb.sql

MySQL Workbench 같은 도구를 쓴다면 mobiusdb 스키마를 만들고 Data Import → Import from Self-Contained File에서 mobius/db/mobiusdb.sql을 골라 넣으면 같습니다.

데이터베이스 이름

기본값은 mobiusdb입니다. 다른 이름을 쓰려면 설치 후 npm run conf -- set dbName <이름>으로 바꿉니다.

MQTT 브로커 (선택)

구독 알림을 mqtt:// 주소로 보낼 계획이면 브로커가 필요합니다. Mosquitto를 설치하고 서비스를 시작해 두십시오. HTTP 주소로만 알림을 받을 거라면 없어도 됩니다.

소스와 모듈

  1. 소스를 받는다

    터미널
    git clone https://github.com/IoTKETI/Mobius.git
cd Mobius

    Git이 없다면 GitHub 페이지에서 ZIP으로 받아 풀어도 됩니다.

  2. 모듈을 설치한다

    터미널
    npm install

    node_modules 폴더가 생기면 됩니다. Node.js는 따로 빌드할 것이 없어 여기까지가 설치입니다.

04 — 구동

구동

첫 실행

설정 파일 conf.json이 없으면 Mobius가 스스로 마법사를 돌립니다. 별도의 설치 명령이 필요 없습니다.

터미널
node mobius.js

일곱 가지를 차례로 묻고, 답을 conf.json에 적은 뒤 그대로 서버를 띄웁니다.

묻는 것기본값설명
데이터베이스mysqlmysql 또는 sqlite
DB 비밀번호—MySQL을 골랐을 때만 묻습니다. 입력하는 동안 화면에 보이지 않습니다
CSE 이름Mobius트리의 뿌리 이름. 모든 주소가 /이름으로 시작합니다
CSE-ID/Mobius2이 CSE의 식별자
SP-ID//keti.re.kr서비스 제공자 식별자
수퍼유저 OriginSponde이 값으로 요청하면 접근 검사를 모두 건너뜁니다
HTTP 포트7579서버가 열 포트
수퍼유저 Origin은 마스터 키입니다

이 값을 요청 헤더에 넣으면 모든 접근 제어를 건너뜁니다. 외부에 노출되는 서버라면 기본값 대신 추측하기 어려운 값으로 바꾸고, 아는 사람을 제한하십시오.

CSE 이름을 Mobius로 두고 포트를 7579로 두었다면, 이제 트리의 뿌리 주소는 http://localhost:7579/Mobius입니다.

다시 띄울 때

터미널
node mobius.js          # conf.json 의 설정대로
npm start               # 같은 명령

node mobius.js sqlite   # 이번만 SQLite 로
node mobius.js mysql    # 이번만 MySQL 로
서비스로 띄울 때

pm2나 systemd처럼 터미널이 아닌 환경에서 처음 띄우면, 마법사를 돌릴 수 없으므로 설정 파일을 만들지 않고 종료합니다. 터미널에서 한 번 실행해 conf.json을 만든 뒤 서비스에 올리십시오.

떴는지 확인

뿌리 리소스를 조회해 봅니다. 응답이 오면 서버가 정상입니다.

터미널
curl -i http://localhost:7579/Mobius \
  -H "Accept: application/json" \
  -H "X-M2M-RI: check1" \
  -H "X-M2M-Origin: Sponde"
응답
HTTP/1.1 200 OK
X-M2M-RSC: 2000
Content-Type: application/json

{"m2m:cb": {"rn": "Mobius", "ty": 5, "csi": "/Mobius2", …}}

X-M2M-RSC: 2000이 oneM2M의 성공 코드입니다. HTTP 상태와 따로 붙는 값이라 두 개를 함께 봅니다.

설정 보기와 바꾸기

설정은 웹 화면이 아니라 명령으로 다룹니다. conf.json에 데이터베이스 비밀번호와 수퍼유저 값이 들어 있어서, 서버에 접속할 수 있는 사람만 다루도록 한 것입니다.

터미널
npm run conf                      # 전체 목록과 적용 상태
npm run conf -- csebaseport       # 한 항목만 자세히
npm run conf -- set cseBase Vita  # 값을 바꾼다
npm run conf -- unset maxBodyBytes # 기본값으로 되돌린다
npm run conf -- edit              # 주요 항목을 차례로 다시 묻는다
npm run conf -- --all             # 고급 항목까지 본다

npm run status                    # 지금 떠 있는지, 재기동이 필요한지

설정은 기동할 때 한 번 읽습니다. 값을 바꿨으면 재기동해야 반영되고, npm run conf 목록이 어떤 항목이 재기동을 기다리는지 알려 줍니다.

CSE 이름·포트처럼 잘못 바꾸면 기존 기기가 붙지 못하는 항목은 관문으로 표시됩니다. 바꾸려 하면 경고를 보여 주고 항목 이름을 직접 타이핑해야 넘어갑니다.

비밀 값 봉인

데이터베이스 비밀번호와 수퍼유저 값은 도구로만 바꿉니다. 편집기로 conf.json을 열어 이 둘을 손으로 고치면 다음 기동이 거부됩니다. 옆에 놓인 conf.seal.json이 두 값의 지문을 들고 있다가 어긋나면 잡아냅니다.

터미널
npm run setup -- --dbpass      # DB 비밀번호 다시 입력
npm run setup -- --superuser   # 수퍼유저 Origin 다시 입력

둘 다 프롬프트에서 그냥 Enter를 치면 값은 그대로 두고 봉인만 새로 만듭니다. 예전 버전에서 올라와 봉인이 아직 없다면 이 방법으로 한 번 만들어 두십시오.

관리 콘솔

Mobius와 같은 저장소, 다른 프로세스로 도는 운영자용 화면입니다. 만료된 리소스와 부모가 사라진 리소스를 찾아 지우고, 접근 정책을 검토하고, 구독 상태와 통계를 봅니다.

터미널
# 비밀번호를 먼저 정한다 (없으면 콘솔이 뜨지 않는다)
npm run conf -- set adminPassword '고른-비밀번호'

# 콘솔을 띄운다
node admin/server.js

# 또는 Mobius 가 띄우게 한다 — 마스터의 자식 프로세스로 함께 뜬다
npm run conf -- set adminAutoStart on

설정과 프로세스 제어는 콘솔에 없습니다. 그 둘은 명령으로만 다룹니다.

안 뜰 때

Mobius는 뜨지 못한 이유를 종료 코드로 구분합니다. 프로세스만 살아 있고 요청을 못 받는 상태로 남지 않게 하기 위해서입니다.

코드뜻할 일
12포트가 이미 쓰이는 중다른 프로세스를 끄거나 csebaseport를 바꿉니다
13conf.json이 없다터미널에서 node mobius.js를 한 번 실행해 만듭니다
14비밀 값 봉인이 어긋난다npm run setup -- --superuser로 봉인을 다시 만듭니다
1데이터베이스에 붙지 못했다DB가 떠 있는지, 비밀번호와 데이터베이스 이름이 맞는지 봅니다

요청별 처리 시간은 화면이 아니라 log/access-*.log의 마지막 필드에 있습니다. 지금 어떤 설정으로 떠 있는지는 log/mobius-boot.jsonl에 남고, npm run status가 그것을 읽어 보여 줍니다.

05 — 활용

활용

아래 예제는 순서대로 실행하면 그대로 동작합니다. 서버가 localhost:7579에서 Mobius라는 이름으로 떠 있다고 가정합니다.

요청의 기본형

모든 요청에 두 개의 헤더가 필요합니다.

헤더무엇
X-M2M-RI요청 식별자. 아무 값이나 넣되 요청마다 다르게 합니다. 응답에 그대로 돌아옵니다
X-M2M-Origin요청자 식별자. 접근 제어의 판단 기준이 됩니다
Content-Type만들 때만 필요합니다. application/json; ty=<번호> 꼴로 무엇을 만들지 알려 줍니다
Acceptapplication/json. Mobius는 JSON만 다룹니다

AE 등록

기기나 애플리케이션은 먼저 AE로 등록합니다. 트리에 들어오는 입구를 만드는 일입니다. X-M2M-Origin에 정확히 S를 넣으면 Mobius가 식별자를 만들어 돌려줍니다.

AE 만들기
curl -X POST http://localhost:7579/Mobius \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-ae-1" \
  -H "X-M2M-Origin: S" \
  -H "Content-Type: application/json; ty=2" \
  -d '{"m2m:ae": {"rn": "myAE", "api": "A.company.myapp", "rr": true}}'
응답 (201 · RSC 2001)
{"m2m:ae": {
  "rn": "myAE",
  "ty": 2,
  "aei": "S2026090812345601a3",   <-- 이 값을 보관하십시오
  "ri":  "2-2026090812345601a3",
  …
}}

돌려받은 aei가 이 AE의 신분증입니다. 이후 이 AE로 하는 요청의 X-M2M-Origin에 이 값을 넣습니다. 원하는 식별자가 따로 있다면 S 대신 그 값을 넣으면 그대로 aei가 됩니다.

  • rn — 리소스 이름. 주소의 한 칸이 됩니다
  • api — 애플리케이션 식별자. 표준이 요구하는 값입니다
  • rr — 이 AE가 요청을 받을 수 있는지 여부

컨테이너 만들기

데이터를 담을 그릇입니다. AE 아래에 만듭니다.

컨테이너 만들기
curl -X POST http://localhost:7579/Mobius/myAE \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-cnt-1" \
  -H "X-M2M-Origin: S2026090812345601a3" \
  -H "Content-Type: application/json; ty=3" \
  -d '{"m2m:cnt": {"rn": "temperature", "mni": 1000}}'

mni는 이 컨테이너가 최대 몇 건까지 보관할지입니다. 넘으면 오래된 것부터 마스터의 정리 작업이 지웁니다. 용량으로 제한하려면 mbs에 바이트 수를 줍니다. 두 값을 주지 않으면 사실상 제한 없이 쌓입니다.

데이터 저장과 조회

실제 값은 contentInstance로 넣습니다. 한 번 만들면 바꾸지 않는 기록이라, 센서 값이 올라올 때마다 하나씩 쌓는 것이 정상입니다.

값 하나 넣기
curl -X POST http://localhost:7579/Mobius/myAE/temperature \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-cin-1" \
  -H "X-M2M-Origin: S2026090812345601a3" \
  -H "Content-Type: application/json; ty=4" \
  -d '{"m2m:cin": {"con": "23.5"}}'

con이 값입니다. 문자열이므로 JSON을 넣고 싶으면 문자열로 만들어 넣습니다.

최신 한 건 읽기

가장 최근 값
curl http://localhost:7579/Mobius/myAE/temperature/la \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-la-1" \
  -H "X-M2M-Origin: S2026090812345601a3"

la는 가장 최근 것, ol은 가장 오래된 것입니다. 대시보드가 현재 값을 보여 줄 때 가장 많이 쓰는 주소입니다.

컨테이너 자체 보기

컨테이너 정보
curl http://localhost:7579/Mobius/myAE/temperature \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-cnt-2" \
  -H "X-M2M-Origin: S2026090812345601a3"

응답의 cni가 지금 들어 있는 개수, cbs가 총 바이트입니다.

탐색

무엇이 있는지 모를 때 트리를 훑습니다. fu=1을 붙이면 조건에 맞는 리소스의 주소 목록이 돌아옵니다.

컨테이너 전부 찾기
curl "http://localhost:7579/Mobius?fu=1&ty=3" \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-dis-1" \
  -H "X-M2M-Origin: Sponde"
응답
{"m2m:uril": ["Mobius/myAE/temperature", "Mobius/myAE/humidity"]}
조건뜻예
ty리소스 타입ty=3 · ty=3&ty=4
rn이름이 정확히 일치rn=temperature
lbl라벨이 붙어 있는 것lbl=outdoor
cra · crb생성 시각 이후 · 이전cra=20260101T000000
lvl훑을 깊이lvl=2
lim · ofst개수 제한 · 건너뛸 개수lim=100&ofst=100
결과가 잘렸을 때

응답에 X-M2M-CTS: 1이 붙으면 더 있다는 뜻이고, X-M2M-CTO가 다음 요청에 쓸 ofst 값입니다. 이 둘로 끝까지 넘길 수 있습니다.

구독과 알림

컨테이너에 새 값이 들어올 때마다 알림을 받으려면 subscription을 답니다. nu에 알림을 받을 주소를 적습니다.

구독 만들기
curl -X POST http://localhost:7579/Mobius/myAE/temperature \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-sub-1" \
  -H "X-M2M-Origin: S2026090812345601a3" \
  -H "Content-Type: application/json; ty=23" \
  -d '{"m2m:sub": {
        "rn": "watch",
        "nu": ["http://192.168.0.10:9000/noti"],
        "nct": 2
      }}'

이제 이 컨테이너에 값이 들어올 때마다 그 주소로 POST가 갑니다. nu는 배열이라 여러 곳에 보낼 수 있고, 주소의 종류에 따라 보내는 방식이 갈립니다.

주소 형태어떻게 보내나
http://…HTTP POST. 받는 쪽 응답까지 읽어 성공·거절·실패를 로그에 남깁니다
mqtt://…MQTT 발행. 브로커 설정이 필요합니다
coap://…CoAP 요청
알림은 보내고 끝입니다

Mobius는 알림을 보낸 뒤 재시도하지 않고, 실패했다고 구독을 지우지도 않습니다. 받는 쪽이 잠깐 꺼져 있으면 그 알림은 사라집니다. 놓치면 안 되는 값이라면 애플리케이션이 주기적으로 la를 읽어 보완하십시오.

접근 제어

기본적으로는 요청자를 가리지 않습니다. 특정 리소스를 누가 다룰 수 있는지 정하려면 accessControlPolicy를 만들고 리소스에 붙입니다.

정책 만들기
curl -X POST http://localhost:7579/Mobius \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-acp-1" \
  -H "X-M2M-Origin: Sponde" \
  -H "Content-Type: application/json; ty=1" \
  -d '{"m2m:acp": {
        "rn": "readonly",
        "pv":  {"acr": [{"acor": ["S2026090812345601a3"], "acop": 51}]},
        "pvs": {"acr": [{"acor": ["Sponde"], "acop": 63}]}
      }}'

acop은 허용할 동작을 비트로 더한 값입니다.

값동작값동작
1CREATE8NOTIFY
2RETRIEVE16DELETE
4UPDATE32DISCOVERY

51은 조회·생성·삭제·탐색(1+2+16+32), 63은 전부입니다. pv가 대상 리소스에 대한 권한이고, pvs는 이 정책 자체를 고칠 수 있는 권한입니다.

만든 정책을 컨테이너에 붙입니다.

정책 붙이기
curl -X PUT http://localhost:7579/Mobius/myAE/temperature \
  -H "Accept: application/json" \
  -H "X-M2M-RI: r-acp-2" \
  -H "X-M2M-Origin: Sponde" \
  -H "Content-Type: application/json" \
  -d '{"m2m:cnt": {"acpi": ["/Mobius/readonly"]}}'

이제 이 컨테이너는 정책이 허용한 요청자만 다룰 수 있습니다. 정책을 붙이기 전에 무엇이 막히는지 미리 보고 싶다면 관리 콘솔의 접근 정책 화면에서 모의 실행할 수 있습니다.
