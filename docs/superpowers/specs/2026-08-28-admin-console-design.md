# Mobius 리소스 관리 콘솔 설계

- 작성일: 2026-08-28
- 대상 브랜치: `fix/p0-fanout-loop-and-ae-notify` 기준
- 기준 커밋: `bad4d4c`

## 배경

운영 중인 Mobius 에는 리소스를 사람이 들여다보고 정리할 수단이 없다. oneM2M discovery 는 기계용 API 이고, 관리자가 "어떤 AE 가 살아 있는가, 이 컨테이너는 언제 마지막으로 쓰였는가, 만료된 건 무엇인가"를 묻는 도구가 아니다.

그런데 이 서버에는 만료 리소스가 계속 쌓인다. 자동 정리 루틴이 세 가지 이유로 반쯤만 동작하기 때문이다.

**증거 1 — AE·컨테이너는 만료돼도 삭제되지 않는다.** `sql_action.js:3570` 의 `delete_lookup_et` 쿼리:

```sql
select ri from lookup where et < '...' and ty <> '2' and ty <> '3' and ty <> '5'
```

`ty` 2(AE), 3(container), 5(CSEBase) 를 제외한다. CIN·SUB·ACP 만 지워진다.

**증거 2 — SQLite 에서는 아예 동작하지 않는다.** 같은 함수가 `db.getResult`(MySQL 전용)만 호출하고 `global.usesqlite` 분기가 없다.

**증거 3 — 실패해도 흔적이 없다.** `if (!err) { ... }` 뿐이고 `else` 가 없어, 실패 시 콜백조차 호출되지 않고 조용히 사라진다.

추가로 `app.js:180` 의 `setInterval(del_expired_resource, 24h)` 는 마스터 프로세스에서만 등록되므로 재기동하면 첫 실행이 24시간 뒤다.

이 콘솔은 그 구멍을 사람이 메우는 도구다. 자동 삭제 범위를 넓히는 대신 **관리자가 확인하고 판단해 삭제하거나 만료를 연장하는 경로**를 제공한다.

## 목표

1. 리소스 트리와 각 리소스의 생성·수정·만료 시각, 최근 사용 여부를 확인한다
2. 만료된(또는 임박한) 리소스를 걸러내고, 확인 후 삭제하거나 만료를 연장한다
3. 리소스별 접근 권한(ACP)을 확인하고 편집하며 리소스에 연결·해제한다
4. Mobius 와 함께 동작하되 **별도 프로세스·별도 포트**로 운영한다

## 비목표

- Mobius 의 자동 만료 삭제 범위 확대 (위험하고, 이 콘솔이 그 역할을 대신한다)
- oneM2M 리소스 **생성** 기능 전반 (ACP 생성은 예외 — 권한 관리에 필수)
- 다중 사용자·역할 분리 (관리자 1명 전제)
- SQLite 의 지원 리소스 타입 확대
- `acco`(IP 화이트리스트·시간창) 편집 — 읽기 전용 표시만

| 항목 | 결정 |

## 1. 코드베이스에서 확인된 제약

설계는 아래 사실 위에 서 있다. 전부 실제 코드와 실측 데이터로 확인했다.

### 1.1 데이터 모델

`lookup` 단일 테이블이 트리 전체를 담는다.

- `ri` = 구조화 경로 (`/Mobius/test_p52/test_cnt`), `pi` = 부모 경로
- `sri` / `spi` = 비구조화 ID 쌍. CIN 의 `sri` 는 `4-20260323062138780381` 형식이라 **사전순 = 시간순**
- `ct` / `lt` / `et` = `YYYYMMDDThhmmss` 문자열. 실측 154행 전부 15자로 균일
- 타입별 상세는 `ae` / `cnt` / `cin` / `acp` / `sub` 위성 테이블에 `ri` FK

### 1.2 인덱스 현황 — 규모 설계를 좌우한다

| | MySQL | SQLite |
|---|---|---|
| `lookup` | PK `(pi,ri,ty)`, `ri_UNIQUE(ri)`, `idx_lookup_ty`, `idx_lookup_ct`, `idx_lookup_sri`, `idx_lookup_pi` **INVISIBLE** | `ri` PK **뿐** |
| `cin` | PK `(ri,pi)`, `cin_ri_idx(pi,ri,cs)` | `ri` PK 뿐 (`pi` 인덱스 없음) |
| `et` | **없음** | **없음** |

`mobiusdb_sqlite.sql` 에 `CREATE INDEX` 가 **0개**다. SQLite 에서는 자식 조회·타입 필터·만료 필터가 전부 풀스캔이다. MySQL 은 `idx_lookup_pi` 가 `/*!80000 INVISIBLE */` 라 옵티마이저가 무시한다.

### 1.3 삭제는 비동기이고 HTTP 200 은 완료가 아니다

`resource.js:2463` 의 `delete_action`:

```js
db_sql.delete_ri_lookup(request.db_connection, resource_Obj[rootnm].ri, function (err) {
    if(!err) {
        if (leaf_ty_list.indexOf(String(resource_Obj[rootnm].ty)) < 0) {
            setImmediate(delete_descendants_background, resource_Obj[rootnm].ri);
        }
        // ... callback('200')
```

`leaf_ty_list = ['1','4','9','17','23']` 이므로 **AE(2)·CNT(3) 는 리프가 아니고 배경 삭제 경로를 탄다.** 대상 행 하나만 지우고 200 을 돌려준 뒤 자손은 나중에 지운다.

`delete_descendants_background`(`resource.js:2426`)는 MySQL 경로에서 커넥션을 잡고 서브트리 삭제가 끝날 때까지 놓지 않으며(2448·2457행), 커넥션을 못 얻으면 **상한 없이** 5초마다 재시도한다(2436행).

> **설계 귀결 A.** 일괄 삭제의 진행률 분모를 HTTP 요청 수로 잡으면 거짓말이 된다.
> **설계 귀결 B.** 콘솔의 동시성 제한은 HTTP 발사 속도만 조절할 뿐 서버 안에 쌓이는 배경 작업을 줄이지 못한다. 카나리 실행과 지연 관측이 필요하다.

### 1.4 워커 간 캐시 무효화가 없다

`app.js:58` 의 `global.cache_resource_url` 은 워커별 무제한 인메모리 캐시다. `app.js:1232` 의 `check_resource_from_url` 이 캐시 히트 시 그 행으로 바로 응답을 만든다. 그런데 `process.send` / `worker.send` 를 쓰는 곳이 **한 군데도 없다.**

워커 A 가 리소스를 지워도 워커 B~N 은 계속 200 을 돌려준다. CPU 코어 수만큼 워커가 뜨므로 실서비스에서 재현된다. **기존 버그이며, 이게 없으면 콘솔의 "지웠다"가 사용자에게 거짓이 된다.**

### 1.5 사용 이력은 존재하지 않는다

`hit` 테이블은 `ct`(=`YYYYMMDD`) 를 PK 로 하는 **날짜별 서버 전체 집계**다. 실측:

```
{ct:"20260313", http:25, mqtt:0, coap:0, ws:0}
```

리소스 식별자가 없다. 또 oneM2M 규약상 RETRIEVE 는 `lt` 를 갱신하지 않으므로 "마지막으로 읽힌 시각"은 어디에도 없다.

MQTT/CoAP/WS 프록시는 전부 `http.request` 로 CSE 포트에 재진입하므로(`pxy_mqtt.js:444`), 수집 지점을 HTTP 라우터 한 곳에 두면 모든 프로토콜이 잡힌다.

### 1.6 ACP 판정 모델

`acp.pv` / `pvs` 에 `{acr:[{acor:[...], acop:비트마스크, acco:{acip,actw}}]}` JSON.

acop 비트: `1`=CREATE `2`=RETRIEVE `4`=UPDATE `8`=DELETE `16`=NOTIFY `32`=DISCOVERY (`63`=전체)

`security.js:408` 의 `exports.check` 가 단일 진입점이며 세 갈래로 갈린다.

1. `x-m2m-origin` 이 `usesuperuser`(현재 `'Sponde'` 하드코딩)면 **무조건 통과**
2. `acpi` 가 있으면 `security_check_action_pv` 가 `pv` 를 강제
3. `acpi` 가 비면 — `ty` 가 33/23/4/3 인 경우 `select_acp_cnt` 로 조상의 acpi 를 찾고, 그래도 없으면 `security_default_check_action` 폴백

> **주의 — 흔한 오해.** `useaccesscontrolpolicy` 는 ACP 를 켜고 끄는 스위치가 **아니다.** 이 값과 무관하게 `acpi` 가 있으면 `pv` 는 정상 강제된다. `useaccesscontrolpolicy` 는 **폴백 경로(`security_default_check_action`, `security.js:384`)의 동작만** 바꾼다.
>
> | | `enable` | `disable` (기본값) |
> |---|---|---|
> | `origin == cr` | 전부 허용 | 전부 허용 |
> | 그 외 origin | 전부 거부 | **C(1)·R(2)·Discovery(32) 만 허용**, U(4)·D(8)·N(16) 거부 |
>
> 즉 `acpi` 가 없는 리소스는 "무방비"가 아니라 **"누구나 읽고 만들 수 있지만 생성자만 고치고 지울 수 있는"** 상태다. 콘솔이 "강제되지 않음" 배너를 무차별로 띄우면 그 자체가 거짓말이 되고, 관리자가 "어차피 안 걸리니까"라며 ACP 를 붙였다가 실제 클라이언트가 차단된다.

**상속의 종지 조건.** `select_acp_cnt`(`sql_action.js:2264`)는 `lookup.pi` 체인을 쓰지 않는다. **요청 URL 문자열을 뒤에서부터 한 세그먼트씩 잘라** `WHERE ri = "<잘린 경로>"` 로 조회하고, 그 조상의 `acpi` 가 비어 있으면서 **`ty == '3'`(container) 일 때만** 위로 재귀한다. 즉 컨테이너 사슬을 타고 올라가다 AE(ty=2) 를 만나면 그 AE 의 `acpi` 를 반환하고 멈춘다. 콘솔은 이 경로 문자열 기반 탐색과 종지 조건을 **그대로** 재현해야 한다.

**깨진 `acpi` 참조.** `security_check_action_pv`(`security.js:28-37`)는 `select_acp_in` 결과가 0건이면 거부가 아니라 `origin == cr` 폴백으로 떨어진다. 참조하던 ACP 가 사라지면 그 리소스는 조용히 **생성자 전용**이 된다.

**그리고 그 ACP 는 실제로 사라진다.** `delete_lookup_et` 의 제외 목록은 `ty` 2/3/5 뿐이고 **ty=1(ACP) 은 빠져 있지 않다.** ACP 는 만료되면 서버가 자동 삭제한다. 만료 임박 ACP 는 삭제 큐가 아니라 **권한 사고 예방 큐**의 최우선 항목이어야 한다.

### 1.8 인증 우회 취약점 — `acor` 정규식 방향 역전

`security.js:154`(`pv` 경로)와 `security.js:338`(`pvs` 경로) 모두:

```js
var re = new RegExp('^' + from + '$');          // from = 요청의 X-M2M-Origin
for (var acor_idx in pvObj.acr[index].acor) {
    if (pvObj.acr[index].acor[acor_idx].match(re) || ... === 'all' || ... === '*') {
```

**요청자가 보낸 origin 이 정규식 패턴이 되고, 저장된 `acor` 값이 그 패턴에 매칭되는 대상이다.** 방향이 뒤집혀 있다. 클라이언트가 `X-M2M-Origin: .*` 로 보내면 `acor` 에 무엇이 들어있든 전부 매칭되어 ACP 를 통째로 우회한다.

> **설계 귀결.** 콘솔의 유효 권한 매트릭스가 `acor: KETI_MUV → RETRIEVE` 를 "저 AE 만 읽을 수 있음"으로 그리면 거짓말이 된다. 매트릭스에 이 사실을 명시하고, **별건 보안 수정**으로 분리해 추적한다(이 설계의 범위 밖이지만 콘솔 배포 전에 고치는 것이 옳다).

### 1.7 실측된 데이터 무결성 문제

로컬 `mobius.db` 에서 컨테이너별 `cnt.cni` 와 실제 CIN 행 수를 대조한 결과:

| 컨테이너 | `cnt.cni` | 실제 CIN 행 | |
|---|---|---|---|
| `/Mobius/test_p52/test_cnt` | 22 | 22 | 일치 |
| `/Mobius/UserInfos/demo_keti_re.kr` | 2 | 2 | 일치 |
| `/Mobius/ae_test/cnt1` | 100 | 100 | 일치 |
| `/Mobius/AE_PhH1776225724/c1` | **3** | **19** | **불일치** |

`cni`/`cbs` 는 `checkAndPurge` 의 보관 한도 판정 입력이므로, 어긋나면 보관 정책이 잘못 계산된다. 콘솔에 진단·재계산 기능을 넣을 근거다.

## 2. 시스템 구성

```
┌──────────────────────────┐   읽기 SELECT   ┌────────────────────────┐
│  Mobius Admin            ├────────────────>│  MySQL / SQLite        │
│  독립 프로세스 · 포트 7580 │   (읽기 전용)    │  lookup, cnt, ae, acp  │
│  단일 워커                │                 │  hit, hit_ri (신설)     │
│                          │                 └───────────┬────────────┘
│  Vue 3 SPA (정적 서빙)    │                             │ 읽기·쓰기
│  admin.db (자체 상태)     │                             │
└──────────┬───────────────┘                 ┌───────────┴────────────┐
           │  oneM2M HTTP                    │  Mobius CSE :7579      │
           │  X-M2M-Origin: <admin origin>   │  cluster 워커 N개       │
           └────────────────────────────────>│                        │
              PUT (et/속성) DELETE POST(acp)  └────────────────────────┘
```

### 2.1 왜 하이브리드인가

**읽기를 DB 직접으로** — 트리 전개, 만료 필터, 사용 이력 집계는 oneM2M discovery 로 표현할 수 없거나 표현해도 훨씬 느리다.

**쓰기를 oneM2M API 로** — DB 에 직접 쓰면 워커별 좀비 캐시(§1.4), 구독 알림 누락(`resource.js:2550`), 부모 카운터 어긋남, 하위 트리 고아 행이 전부 발생한다. 콘솔이 oneM2M 의미론을 재구현하지 않는다.

### 2.2 왜 같은 저장소인가

별도 프로세스지만 저장소는 공유하고 `admin/` 디렉터리에 둔다. `mobius/db` 파사드와 스키마 정의를 `require` 해야 MySQL/SQLite 이중 지원을 중복 구현하지 않는다. 별도 저장소면 파사드를 복제해야 하고, 복제본은 반드시 어긋난다.

### 2.3 클러스터를 쓰지 않는다

접속자가 1명이고, 워커가 여럿이면 일괄 작업 큐 상태를 공유할 수 없다.

## 3. 선행 작업 (Mobius 본체 변경)

각각 독립 배포 가능하며, 콘솔 없이도 그 자체로 개선이다.

### P0-1. 워커 간 캐시 무효화 브로드캐스트

```
워커 → process.send({t:'cache-inv', ri})
마스터 → 전 워커에 broadcast
각 워커 → cache_resource_url 에서 제거:
          ① ri  ② '<pi>/la'  ③ '<ri>/' 접두어를 가진 모든 키
```

무효화를 발신하는 지점은 현재 `delete cache_resource_url[...]` 를 하는 모든 곳(`app.js:2354`, `2564-2575`, `resource.js:415`, `759`, `2488`)이다.

부수 작업으로 `cache_resource_url` 에 **상한(LRU 또는 최대 항목 수)** 을 둔다. 지금은 무제한 증가라 장기 구동 시 메모리 누수다.

### P0-2. `hit_ri` 수집

```sql
CREATE TABLE hit_ri (
  ri   VARCHAR(200) NOT NULL,
  ct   VARCHAR(8)   NOT NULL,          -- YYYYMMDD
  http INT DEFAULT 0, mqtt INT DEFAULT 0,
  coap INT DEFAULT 0, ws   INT DEFAULT 0,
  PRIMARY KEY (ri, ct)
);
```

**규칙 — CIN 은 수집 대상이 아니다.** CIN 마다 행을 만들면 `hit_ri` 가 `lookup` 보다 커진다. CIN 에 대한 접근은 **부모 CNT 에 귀속**시킨다. `/la`(latest) 접근도 마찬가지로 CNT 에 귀속한다.

**수집 방식** — 요청 경로에서 DB 를 때리지 않는다. 워커별 인메모리 `Map<ri, {http,mqtt,coap,ws}>` 에 누적하고 `wdt.js` 로 **10초마다 배치 UPSERT** 한다. 기존 `set_hit` 이 전 워커가 같은 한 행을 매 요청 UPSERT 하는 핫로우 경합도 같은 버퍼로 흡수한다.

**콘솔 자신의 트래픽을 제외한다.** 콘솔은 oneM2M HTTP 로 리소스를 조회하므로, 이를 그대로 집계하면 **인스펙터를 열 때마다 그 리소스의 "마지막 접근"이 오늘로 갱신되어 판정 신호를 스스로 오염시킨다.** `hit_ri` 수집 지점에서 콘솔 origin 을 제외한다. 마찬가지로 `et` 연장 UPDATE 는 `lt` 를 갱신해 "최근 수정됨"을 만들므로, 콘솔이 건드린 `lt` 변경은 `admin.db` 의 감사 로그와 대조해 판정에서 걸러낸다.

**보관** — 판정 기준(무접근 90일)보다 길게 **120일**. 보관과 판정 기준이 같으면 경계에서 판정이 불안정해진다. 일 1회 정리. 리소스 삭제 시 해당 `ri` 의 행도 정리한다(배치).

**수집 시작일 기록** — `admin.db` 에 `hit_ri` 수집 시작일을 남긴다. 신설 테이블이므로 가동 초기 수 주간 "무접근"은 **전부 거짓 신호**다. UI 는 이 구간을 `없음 (수집 12일차)` 로 표기하고, 수집 기간이 판정 기준보다 짧으면 무접근 기반 일괄 선택을 막는다.

### P0-3. 인덱스

**SQLite** — `mobiusdb_sqlite.sql` 에 추가. 인덱스는 테이블과 달리 `CREATE INDEX IF NOT EXISTS` 로 기존 DB 에도 붙는다.

```sql
CREATE INDEX IF NOT EXISTS idx_lookup_pi     ON lookup(pi);
CREATE INDEX IF NOT EXISTS idx_lookup_ty_et  ON lookup(ty, et);
CREATE INDEX IF NOT EXISTS idx_lookup_pi_sri ON lookup(pi, sri);
CREATE INDEX IF NOT EXISTS idx_cin_pi        ON cin(pi);
CREATE INDEX IF NOT EXISTS idx_hit_ri_ct     ON hit_ri(ct);
```

**MySQL** — 마이그레이션 SQL 을 README 에 명시.

```sql
ALTER TABLE lookup ALTER INDEX idx_lookup_pi VISIBLE;
CREATE INDEX idx_lookup_ty_et  ON lookup(ty, et);
CREATE INDEX idx_lookup_pi_sri ON lookup(pi, sri);
```

`idx_lookup_ty_et` 하나로 만료 목록·정렬·건수가 전부 커버링 인덱스 범위 스캔이 된다. `(pi, sri)` 는 CIN 의 `sri` 가 사전순=시간순이라는 성질을 이용해 컨테이너 내 최신순 페이징을 **진짜 키셋**으로 만든다. 현재는 `WHERE pi=? ORDER BY ct DESC` 가 자식 전량 filesort 다(`sql_action.js:2105` 가 이미 그렇게 동작한다).

### P0-4. `security.js` 판정부를 순수 함수로 추출

콘솔의 "유효 권한" 표는 서버의 실제 판정과 반드시 일치해야 한다. 로직을 복제하면 어긋나고, 어긋난 권한 표는 없는 것보다 나쁘다.

```
mobius/acp_eval.js  (신설, 순수 함수 — DB·request 의존 없음)
  evaluate({ pvList, originator, acop, clientIp, now, creator, enforcement })
    → { allowed: bool, reason: 'acr-match' | 'creator' | 'superuser'
                              | 'default-open' | 'denied', matchedAcr }
```

`security.js` 는 DB 조회와 상속 체인 탐색만 남기고 판정은 이 함수에 위임한다. 콘솔은 같은 함수를 `require` 한다. Mobius 쪽도 이 부분이 처음으로 단위 테스트 가능해진다.

### P0-5. `usesuperuser` 를 설정으로 분리 + 콘솔 전용 origin

`app.js:64` 의 `global.usesuperuser = 'Sponde'` 를 `conf.json` 으로 뺀다. 콘솔은 별도의 전용 origin 을 쓴다. 감사 로그에서 "콘솔이 한 일"과 "사람이 한 일"이 구분되고, 배포처별로 바꿀 수 있다.

> **선행 작업에서 의도적으로 제외** — `delete_lookup_et` 의 AE/CNT 제외와 SQLite 미동작은 **고치지 않는다.** 자동 삭제 범위 확대는 위험하고, 콘솔이 그 역할을 대신하는 것이 이 프로젝트의 취지다. 다만 실패 시 콜백을 부르지 않는 결함(§배경 증거 3)은 진단 로그를 남기도록 최소 수정한다.

## 5. 읽기 계약 — 규모 대응

### 5.1 불변식

1. **CIN 은 트리 노드도, 큐 대상도 아니다.** 오직 CNT 행의 파생 수치로만 등장한다
2. **그 파생 수치의 출처는 `cnt.cni`/`cbs` 조인이지 `COUNT(*)` 가 아니다.** `cnt_man` 이 1초 디바운스로 갱신하므로 근사치이며, UI 는 그 이유를 정확히 말한다
3. **전역 `COUNT(*)` 를 실행하지 않는다.** 건수는 `LIMIT n+1` 로 `n+` 표기하거나 배치 스냅샷을 읽는다
4. **정렬 축은 인덱스가 있는 컬럼으로 제한한다.** `ct`, `et`, `ty`, `sri`, `ri`. 파생 축(마지막 접근, CIN 수, 만료 경과일) 정렬은 **현재 페이지 안에서만** 허용한다
5. **비싼 파생 컬럼은 현재 페이지 50행에만 계산한다.** 유효 ACP, 90일 히트, 실제 자식 수

### 5.2 화면별 주 쿼리

| 화면 | 쿼리 | 인덱스 | 비고 |
|---|---|---|---|
| 트리 자식 | `WHERE pi=? AND ty<>4 ORDER BY ty, rn LIMIT 200` | `lookup(pi)` | CIN 을 쿼리에서 제외 |
| 만료 목록 | `WHERE ty IN (2,3) AND et < ? ORDER BY et LIMIT 51` | `lookup(ty,et)` | 커버링 범위 스캔 |
| 경로 범위 | `WHERE ri >= ? AND ri < ?` (접두어) | MySQL `ri_UNIQUE` | 범위 내 CIN 제외에 `ty` 필요 |
| CIN 목록 | `WHERE pi=? AND sri < ? ORDER BY sri DESC LIMIT 51` | `lookup(pi,sri)` | 진짜 키셋 페이징 |
| 컨테이너 지표 | `lookup JOIN cnt ON ri` | PK | `cni`/`cbs` vs `mni`/`mbs` 게이지 |
| 사용 이력 | `hit_ri WHERE ri=? AND ct>=?` | PK | 리소스당 최대 90행 |
| 고아 탐지 | `LEFT JOIN lookup p ON l.pi=p.ri WHERE p.ri IS NULL` | — | **배치 전용.** 화면에서 라이브 실행 금지 |
| ACP 참조 수 | `acpi` 역인덱스 테이블 | 물리화 필요 | `acpi` 는 인덱스 없는 JSON 텍스트. `LIKE '%ri%'` 풀스캔 금지 |

### 5.3 `acpi` 역인덱스

"이 ACP 를 참조하는 리소스가 몇 개인가"는 `lookup.acpi` 가 인덱스 없는 JSON 텍스트라 ACP 하나당 풀스캔이 된다. ACP 40개면 화면 한 번 여는 데 풀스캔 40회다.

`admin.db` 에 역인덱스를 물리화한다.

```sql
CREATE TABLE acp_ref (acp_ri TEXT, res_ri TEXT, PRIMARY KEY (acp_ri, res_ri));
```

배치로 갱신하며 신선도 시각을 함께 표시한다. 라이브가 아님을 숨기지 않는다.

### 5.4 SQLite 계약

인덱스를 P0-3 으로 넣더라도 SQLite 는 소규모 전용이다. 콘솔 기동 시 `lookup` 행 수를 확인해 임계치(예: 50만)를 넘으면 **경고를 띄우고 무거운 화면(고아 진단, 전역 집계)을 비활성화**한다.

## 6. 쓰기 경로와 일괄 작업

### 6.1 단건

`services/cse.js` 가 Mobius 에 요청 하나를 보내고 응답의 `X-M2M-RSC` 를 **그대로** UI 에 노출한다. 콘솔이 재해석하지 않는다. 표기는 Mobius 가 실제로 쓰는 문자열 리터럴(`'404-1'`, `'409-5'`, `'500-4'`)을 그대로 쓴다 — 관리자가 Mobius 콘솔 로그와 대조할 수 있어야 한다.

### 6.2 일괄 작업의 5단계

§1.3 의 두 귀결 때문에 단순 반복 호출로는 안 된다.

```
① 대상 확정     질의식 + 스냅샷 시각을 작업에 함께 저장
② 영향 추정     Σ cnt.cni 로 예상 삭제 행 수. 최근 접근 있는 대상을 분리 표시
③ 프리플라이트  실행 직전 대상 전체를 RETRIEVE 해 존재·et·cni·lt 를 재확인.
                그 사이 되살아나거나 연장된 대상은 자동 제외하고 차이를 미리보기에 표시
④ 아카이브      대상의 리소스 JSON 전문을 admin.db 에 저장 (필수, 옵션 아님)
⑤ 카나리        먼저 10건 실행 → Mobius 응답 지연 관측 → 임계 초과면 중단·감속
⑥ 본실행        나머지 실행 → 사후 검증
```

**프리플라이트가 스냅샷 기반 IA 의 최대 약점을 없앤다.** 미리보기 숫자를 오래된 스냅샷에서 뽑으면 실행 시점에 대상 집합이 이미 달라져 있다.

**"최근 접근 있는 대상"은 `hit_ri` 단독으로 판정하지 않는다.** `hit_ri` + CNT 의 `lt`/`st` + `cni` 증가분을 합성해야 수집 미성숙 구간에서도 작동한다. 이 블록은 경고 문구가 아니라 `[이 N건 선택 해제]` **버튼**으로 제공한다.

**진행률의 분모는 요청 수가 아니라 예상 삭제 행 수(Σ`cni`)** 다. 요청 축과 서버 정리 축을 **두 개의 막대로 분리**해 보여준다.

```
요청   ████████████████████ 300/300 전송 완료
정리   ███████░░░░░░░░░░░░░ 서버가 자손 삭제 중 (약 12,400행 중 4,100행 남음)
```

### 6.3 사후 검증

HTTP 200 이 완료가 아니므로(§1.3), 작업의 마지막 단계에 **재조회 + 고아 잔존 검사**를 붙인다.

1. 삭제 성공으로 집계된 대상 `ri` 를 재조회한다. **여전히 존재하면 실패로 재분류한다**
2. 대상들의 자손이 `lookup` 에서 실제로 사라졌는지 확인한다

이 서버의 지배적 실패 모드는 "머리는 지워졌고 몸통은 남은" 상태이며 어떤 RSC 로도 보고되지 않는다 — Mobius 가 `delete_orphan_lookup` 을 따로 돌리는 이유다.

**`'404-1'` 을 "이미 없음 = 성공"으로 접지 않는다.** 경로 오타, 구조화 `ri` 와 비구조화 `sri` 혼동, 조상이 먼저 지워진 순서 문제가 전부 성공으로 흡수되어 "128건 삭제 성공"이 실제로는 0건일 수 있다. 성공/실패가 아닌 **제3의 결과 코드 `미확인 — 대상 부재`** 로 남긴다.

**AE 재등록 함정.** AE 를 지워도 클라이언트가 자동 재등록하면 AE 리소스는 다시 나타난다. "지웠는데 다시 보이니 괜찮았나 보다"라는 최악의 오해가 생기지만 하위 CNT/CIN 은 이미 영구 소실된 뒤다. 성공 판정을 "노드가 사라짐"으로 정의하지 않고, 재조회 시 `ct` 가 삭제 시각 이후면 **재등록된 별개 리소스**로 구분해 표시한다.

### 6.4 아카이브

CIN 은 복구 불가하지만 AE/CNT/SUB/ACP 는 메타데이터다. 삭제 직전 대상의 리소스 JSON 전문(속성 + `acpi` + `lbl` + 부모 경로)을 남기면 껍데기 재생성이 가능하다. 오삭제 사고의 대부분은 "엉뚱한 AE 를 골랐다"이고, 그 경우 필요한 것은 데이터가 아니라 등록 구조의 복원이다.

**확인 다이얼로그의 이름 타이핑보다 카나리 실행이 값싸고 강한 방어다.** 화면에 300 이라 적힌 걸 300 이라 옮겨 치는 건 마찰일 뿐 검증이 아니다.

### 6.5 제공하지 않는 것

- **CIN 다중 선택 일괄 삭제.** 수만 건 정리는 CNT 삭제나 `mni` 조정으로 유도한다. 서버의 `checkAndPurge` 가 이미 하는 일을 HTTP 요청 수만 건으로 흉내 내지 않는다
- **상한 없는 CSV 내보내기.** 최대 행 수를 두고 초과 시 명시한다
- **"만료 스캔 주기 변경" / "서버 즉시 스캔".** 만료 정리는 Mobius 워커 안의 `setInterval` 이라 oneM2M API 로 건드릴 수단이 없다. 없는 제어권을 UI 에 그리지 않는다. 콘솔이 정직하게 말할 수 있는 건 **"콘솔이 마지막으로 스캔한 시각"** 과 **"누적 미정리 건수 추이"** 뿐이다

### 6.6 제3의 결론: 보존

삭제도 연장도 아닌 "확인했고 그대로 둔다"를 지원한다. 콘솔 로컬 DB 가 아니라 **`lbl` 라벨에 마킹해 서버에 남긴다.** oneM2M UPDATE 로 이미 쓸 수 있고, 다른 경로에서도 보이며 질의로 다시 걸린다.

| **직접 지정** | 이 리소스의 `lookup.acpi` 에 실제로 들어있는 ACP |
| **상속** | `acpi` 가 비어 경로 세그먼트를 잘라 올라가며 찾은 조상의 ACP (`select_acp_cnt`, `ty=='3'` 인 동안만 재귀) |
| **암묵 / 우회** | ACP 부재 시 생성자 통과, 폴백의 C/R/Discovery 개방, 슈퍼유저 origin 우회, 깨진 `acpi` 참조로 인한 생성자 전용 전락 |

### 7.1.1 매트릭스에는 `acor` 행만 그리면 안 된다

`acpi` 가 없는 리소스를 "권한 없음"이라는 빈 상태로 그리면 항상 틀린 그림이다. 실제 규칙(§1.6)을 두 개의 상시 행으로 명시한다.

| 원발신자 | C | R | U | D | N | Di | 출처 |
|---|---|---|---|---|---|---|---|
| `cr` (생성자) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | 폴백 — 생성자 전권 |
| 그 외 모든 origin | ✓ | ✓ | · | · | · | ✓ | 폴백 — `useaccesscontrolpolicy='disable'` |
| `<usesuperuser>` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | 슈퍼유저 우회 (하드코딩) |
| ...`acor` 행들 | | | | | | | 직접 지정 / 상속 |

`acor` 행 옆에는 §1.8 의 정규식 역전 때문에 **"이 제한은 요청자가 `X-M2M-Origin: .*` 로 우회할 수 있음"** 을 명시한다.

### 7.2 무게중심은 전역 집계가 아니라 단건 검증

"유효 권한 없는 리소스 목록" 같은 전역 큐는 비CIN 20만 행 각각에 조상 체인 탐색이 필요해 성립하지 않는다. 대신 **유효 권한 시뮬레이터**를 둔다.

```
리소스: /Mobius/ae_test/cnt1        원발신자: [CAdmin        ]  작업: [RETRIEVE ▾]

  정책 판정   허용   ← acp_eval.evaluate() (P0-4 공유 함수)
  실제 결과   허용   ← 판정 경로: acpi 있음 → pv 강제 → acr[0] 일치
                      두 줄이 어긋나는 동안 카드에 강조 테두리
```

**"실제 결과"는 배너로 뭉뚱그리지 않고 실제 코드 경로를 그대로 계산한다** — `acpi` 유무에 따른 분기, 상속 종지 조건, 폴백 규칙, 슈퍼유저 우회를 전부 반영한다. 그래야만 배너보다 정직해진다.

조상 체인 몇 회 조회로 끝나 규모와 무관하게 성립한다. 전역 "유효 권한 없는 리소스" 큐는 만들지 않는다.

### 7.3 안전장치

- **자기 잠금 방지.** 시뮬레이터의 원발신자 기본값을 **콘솔 origin** 으로 둔다. 콘솔이 슈퍼유저 origin 이면 서버의 마지막 안전망(ACP 의 DELETE 비트)이 콘솔에는 작동하지 않고, 슈퍼유저가 아니면 반대로 `acpi` 없는 리소스에 대한 일괄 삭제가 폴백의 U/D 거부에 걸려 **전량 실패**한다. 삭제 확인 다이얼로그에 "콘솔 = 우회 계정인가"를 항상 표시한다.
- **저장 전 diff 최상단 고정 행.** "이 변경 후에도 콘솔 자신이 이 리소스들에 UPDATE/DELETE 를 유지하는가". 잠금 경로는 `pvs` 하나가 아니다 — ① `acpi` 교체가 새 ACP 에 콘솔 origin 의 U/D 를 안 담으면 그 리소스들을 영구히 관리 불가로 만들고, ② AE 하나의 `acpi` 에 제한적 ACP 를 걸면 상속을 타고 그 아래 전체가 한 번에 잠기며, ③ 만료된 ACP 가 서버에 지워지면 참조 리소스가 전부 생성자 전용이 된다.
- **정직성 표시.** 배너는 리소스별 실제 판정 경로에 따라 다르게 쓴다. `acpi` 가 있으면 "이 리소스는 `pv` 가 강제됩니다", 없으면 "폴백 규칙 적용 — 생성자 전권 / 그 외 C·R·Di 만". **`useaccesscontrolpolicy` 값만 보고 "강제 안 됨"을 무차별로 띄우지 않는다.**
- **상속 행은 기본 잠금.** 편집하려면 원본 ACP 를 열거나 "직접 지정으로 복사"해야 한다. 부모 ACP 를 무심코 고쳐 수십 개 리소스에 파급되는 사고를 UI 구조로 막는다. 복사 시 경고: "이후 상위의 ACP 를 바꿔도 이 리소스는 따라가지 않습니다."
- **`acor` 정규식 경고.** §1.8 때문에 `acor` 기반 제한은 우회 가능하다. 매트릭스가 이를 숨기지 않는다.

## 8. 정보구조(IA)

### 8.1 원칙

**1순위 작업이 곧 홈의 기본 질의다.** 앱을 열면 `ty:(2,3) et:<now` 가 이미 실행된 표가 떠 있다. 진입 후 첫 조작이 "대상이 정렬된 표"여야 한다.

주 은유는 **질의·데이터그리드**다. 트리는 보조 수단이다. 수백만 행에서 트리를 다 펼치는 건 불가능하고, "만료된 AE 300개를 만료 경과일 순으로 처리"는 트리가 구조적으로 못 하는 작업이다(정렬 축이 없고, 판정 수치가 노드에 없으며, 고아는 트리에 그릴 자리조차 없다).

다만 계층 이동은 인덱스 정합적으로 제공한다 — **경로 접두어 범위 필터**(MySQL `ri_UNIQUE` 범위 스캔)와 **↑부모 / ↓자식 이동**(PK `(pi,ri,ty)` 선두 범위 스캔).

### 8.2 화면

| 우선순위 | 화면 | 내용 |
|---|---|---|
| P0 | **만료 임박 ACP** | 권한 사고 예방 큐. ACP 는 만료되면 서버가 자동 삭제하고, 참조 리소스가 조용히 생성자 전용이 된다(§1.6). 삭제 대상이 아니라 **연장 대상**이므로 정리 대상 그리드와 시각적으로 분리한다 |

| P0 | **작업 모니터** | 카나리·진행률 2축·부분 실패·재시도·아카이브 |

### 8.3 판정 칩

300건을 눈으로 훑는 대신 칩으로 안전한 부분집합부터 처리하게 한다. 카나리 실행의 자연스러운 근거가 된다.

| 칩 | 조건 |
|---|---|
| 안전 삭제 후보 | 만료 초과 + 무접근 + `cni`=0 |
| 확인 필요 | 만료 초과 + 무접근 + `cni`>0 |

| 판정 보류 | `hit_ri` 수집 기간 < 판정 기준 |

`판정 보류` 는 무접근 기반 일괄 선택에서 자동 제외된다.

### 8.4 부모별 그룹 요약

300건이 실제로는 특정 AE 두세 개 아래 몰려 있는 경우가 많다. `pi` 별 만료 건수 그룹 요약 행을 제공해 "이 AE 통째로"라는 더 안전한 단위 판단을 가능하게 한다.

### 8.5 위험의 비대칭을 배치에 반영한다

- 되돌릴 수 있는 `[et 연장]` 과 되돌릴 수 없는 `[삭제]` 를 같은 시각적 무게로 나란히 두지 않는다
- **열람 화면에는 되돌릴 수 없는 쓰기 버튼을 두지 않는다.** 데이터 뷰어에서 개별 CIN 삭제를 제공하지 않는 이유이기도 하다
- 다건 삭제의 확인은 화면에 떠 있는 숫자를 옮겨 적는 방식이 아니라 **대상 중 무작위로 뽑힌 1건의 마지막 경로 세그먼트**를 입력하게 한다. 미리보기를 실제로 읽어야만 통과한다

### 8.6 작업의 재현성

작업은 자신을 만든 **질의식과 대상 스냅샷 시각**을 함께 보관하고 URL 로 직렬화한다. 다음 달에 같은 정리를 재현할 수 있고, 사후에 "무엇을 왜 지웠는가"가 경로 목록이 아니라 조건으로 남는다.

실패 수습은 `[실패 15건을 그리드에서 열기]` → `ri:in(...)` 질의 생성으로 폐루프를 닫는다. `ri` 가 UNIQUE 인덱스라 IN 목록 조회가 정확히 N회 인덱스 probe 로 끝난다.

## 9. 프런트엔드

Vue 3 + TypeScript + Vite + Pinia + vue-router.

oneM2M 속성명이 `ri`/`pi`/`ty`/`ct`/`lt`/`et`/`acpi` 같은 약어라 타입 정의가 사실상 문서 역할을 한다. `acop` 비트마스크도 타입으로 잠근다.

## 12. 미해결 사항

1. **`cache_resource_url` 상한 정책** — LRU 최대 항목 수를 얼마로 둘지. 운영 리소스 규모를 알아야 정할 수 있다
2. **카나리 지연 임계치** — Mobius 응답 지연이 얼마를 넘으면 감속할지. 실측 후 조정
3. **MySQL 인덱스 추가의 운영 영향** — 대형 `lookup` 에 `CREATE INDEX` 는 락을 잡는다. 온라인 DDL 가능 여부를 배포처 MySQL 버전으로 확인해야 한다
4. **콘솔 origin 을 슈퍼유저로 둘 것인가** — 슈퍼유저면 서버의 마지막 안전망(ACP 의 DELETE 비트)이 콘솔에 작동하지 않고, 아니면 `acpi` 없는 리소스 일괄 삭제가 폴백의 U/D 거부로 전량 실패한다. 어느 쪽이든 대가가 있어 배포 정책으로 결정해야 한다
5. **`grp` 의 `macp` 경로** — 그룹 팬아웃(`/fopt`)은 `macp` 로 접근을 검사한다(`app.js:2007` 등). 현재 유효 권한 모델은 이 경로를 다루지 않는다. 그룹을 실제로 쓰는 배포에서는 매트릭스가 불완전한 그림이 되므로, 최소한 "이 리소스는 그룹 `macp` 로도 접근 가능"을 별도 표시해야 한다. SQLite 는 `grp` 를 지원하지 않으므로 MySQL 배포에서만 문제가 된다
6. **만료된 AE/CNT 의 기본 조치가 삭제인가 연장인가** — 실제 배포에서 대부분이 "살아있는데 `et` 만 잘못 설정된" 리소스라면, 홈의 프레이밍이 "지워야 할 것들"이 아니라 "만료 설정이 잘못된 것들"이어야 한다. 배포 데이터를 봐야 정할 수 있다
7. **판정 임계값 초기값** — 만료 초과 며칠, 임박 며칠, 무접근 며칠. 튜닝하지 않은 상태에서 대상이 수천 건이면 관리자가 화면 자체를 불신한다
