## 1. 원래 목표는 무엇이었나

> "mysql 모드와 sqlite 모드 2개가 도는데, 이들을 모두 지원하기 위해 작업을 했는데
> 조금은 땜빵식으로 한 것 같아. DB 관련한 함수들을 정형화 규격화 레이어화해서
> 정작 코어에서는 내가 mysql에 넣는건지, sqlite에 넣는 건지 모르게 동작구조를
> 만들고 싶어. 기존 동작을 유지하면서 하나씩 바꿔가면서 만들고 싶은데 가능할까?"

**완료 기준**: `global.usesqlite` 를 읽는 곳이 `mobius/db/index.js` **한 곳**뿐일 것.

이 목표는 **여전히 유효하고, 방향도 맞다.** 다만 진행하면서 성격이 하나 늘었다 —
전환하려고 함수를 하나씩 들여다보다 보니 **실제로 깨져 있던 것들이 계속 나왔다.**
그게 지금까지 작업의 절반 이상을 차지한다.

## 4. 남은 작업

### A. 원래 목표 — `usesqlite` 31곳 제거

분류(`2026-08-26-branch-classification.md`)와 지금까지 진행을 합치면:

| 유형 | 남은 수 | 성격 |
|------|--------|------|
| MERGE (가짜 분기, 기계적 전환) | 약 20 | 두 분기가 같은 일을 한다 |
| REVIEW (진짜 분기, 판단 필요) | 약 8 | `insert_lookup` 등 컬럼 수가 다르다 |
| 검색/discovery 계열 | 약 3 | `search_lookup_sqlite` 이원화 |

가장 큰 덩어리는 **discovery 재귀 CTE 통일** — MySQL 배치 반복문 ↔ SQLite 재귀 CTE.
이건 별도 회차가 필요하다.

### C. 관리자 UI 연동

## 5. 동시 생성 시 식별자 충돌 — 방안

### 실측

CIN 40건을 동시에 POST 했다.

```
응답 분포: {"201": 17, "409": 23}
실제 저장: 17건
409 본문: {"m2m:dbg":"resource is already exist"}
```

**57% 가 유실된다.** 재시도가 없으면 그대로 데이터 손실이다.

### 원인

```js
// mobius/resource.js:925
resource_Obj[rootnm].rn = request.ty + '-' + moment().utc().format('YYYYMMDDHHmmssSSS');
```

`rn` 은 **밀리초 타임스탬프뿐이고 타이브레이커가 없다.** 같은 ms 에 두 건이 들어오면
`rn` 이 같아지고 → `ri` 가 같아지고 → `lookup` PK 충돌 → 409.

워커가 17개라 동시성이 높을수록 충돌이 잦다.

**작성자는 이 문제를 알고 있었다** — `sri` 에는 이미 랜덤 3자리를 붙인다:

```js
// mobius/resource.js:1134, mobius/cb.js:95
... + moment().utc().format('YYYYMMDDHHmmssSSS') + (Math.random() * 999).toFixed(0).padStart(3, '0');
```

`rn` 에만 안 붙어 있다.

### 함께 봐야 하는 문제 — `la` 가 틀린 값을 준다

`la`(최신) 해석이 백엔드마다 다르다.

| 백엔드 | 정렬 기준 | 정밀도 |
|--------|----------|-------|
| SQLite | `order by ct desc` | **초** |
| MySQL | `order by ri desc` | 밀리초 (ri 에 포함) |

`ct` 는 `YYYYMMDDTHHmmss` 로 초 단위다. 실측: CIN 22건에 서로 다른 `ct` 는 **2개뿐**.

```
rn 내림차순(진짜 최신순): ...251, ...250, ...247, ...243, ...242
la 를 10회 조회한 결과:   {"4-20260828003448242": 10}
```

**모호한 게 아니라 일관되게 틀린 값을 준다.** MySQL 은 `ri` 로 정렬해서 맞다.

### 방안

두 문제의 뿌리가 같다 — **시간 기반 식별자의 해상도와 타이브레이커**.

#### 안 1 — `rn` 에 랜덤 접미사 (sri 와 동일)

```js
rn = ty + '-' + ts + (Math.random() * 999).toFixed(0).padStart(3, '0');
```

| 장점 | 단점 |
|------|------|
| 최소 변경, `sri` 와 일관 | 충돌 확률이 0 이 아니다 |
| | 같은 ms 에 40건이면 생일 문제로 충돌 기대값이 무시 못 할 수준 |

#### 안 2 — 워커별 단조 시퀀스 (권장)

```js
// mobius/resource.js
var _rn_seq = 0;
var _rn_last = '';

function next_rn(ty) {
    var ts = moment().utc().format('YYYYMMDDHHmmssSSS');
    if (ts === _rn_last) { _rn_seq++; }
    else { _rn_last = ts; _rn_seq = 0; }
    // 워커 태그로 프로세스 간 충돌을 막는다 (cluster.worker.id, 없으면 0)
    return ty + '-' + ts + WORKER_TAG + String(_rn_seq % 1000).padStart(3, '0');
}
```

| 장점 | 단점 |
|------|------|
| **결정적** — 같은 워커 안에서는 충돌이 원천적으로 없다 | 한 워커가 같은 ms 에 1000건을 넘기면 순환 (현실적으로 도달 불가) |
| 워커 태그로 프로세스 간 충돌도 막는다 | `rn` 이 5자 길어진다 (`varchar(45)` 여유 충분) |
| **고정 폭이라 사전순 == 시간순** → `la` 정렬 키로 그대로 쓸 수 있다 | |

**기존 데이터와 섞여도 정렬이 깨지지 않는다.** 옛 `rn`(19자)과 새 `rn`(24자)을 문자열
비교하면, 타임스탬프 부분이 고정 폭이라 차이는 그 뒤에서만 난다. 같은 ms 라면
옛 것이 앞에 오고, 다른 ms 라면 타임스탬프가 결정한다. **마이그레이션이 필요 없다.**

#### 안 3 — `ct` 에 밀리초 저장

oneM2M 은 `YYYYMMDDTHHMMSS,mmm` 형식을 허용한다.

| 장점 | 단점 |
|------|------|
| `ct` 자체가 정확해진다 | **API 응답 형식이 바뀐다** — 클라이언트 호환성 문제 |
| | 기존 데이터에는 ms 가 없어 혼재 |
| | 식별자 충돌(문제 1)은 여전히 안 풀린다 |

#### 권장

**안 2 + `la` 정렬 통일.**

1. `rn` 생성을 워커별 단조 시퀀스로 바꾼다 → 동시 생성 유실이 사라진다.
2. SQLite `select_latest_resource` 를 `order by rn desc` (또는 `ri desc`)로 바꾼다 →
   MySQL 과 같아지고, `la` 가 진짜 최신을 준다.

`ct` 는 건드리지 않는다. API 형식이 바뀌면 클라이언트가 깨지고, 정작 충돌 문제는
안 풀리기 때문이다.

**검증 방법**: 지금 만든 실측을 그대로 되풀이하면 된다 — 동시 40건 POST 후
`{"201": 40}` 이 나오고, `la` 가 `rn` 최댓값과 일치하면 성공이다.

## 6. 방향 점검 — 이 구조가 맞나

**맞다.** 다만 처음 예상과 달라진 것이 둘 있다.

### 달라진 것 1 — "땜빵을 정리한다" 보다 "깨진 것을 찾는다" 가 커졌다

전환하려고 함수를 열어 보면 대개 뭔가 깨져 있었다. 3절의 12건이 그렇다.
이건 낭비가 아니라 **전환 작업의 실질적 가치**다 — 파사드로 옮기지 않았으면
`cni` 가 안 줄어드는 것도, 만료 스윕이 정반대로 도는 것도 계속 몰랐을 것이다.

다만 그만큼 `usesqlite` 제거 속도는 예상보다 느리다 (44 → 31).

### 달라진 것 2 — 스키마 변경은 하지 않기로 확정했다

"`cin` 과 `cnt` 가 분리돼 SQL 이 복잡하니 합치자" 를 실측으로 검토했다
(`2026-08-27-cin-write-path-efficiency.md`).

| | 병합으로 아끼는 것 | 병합으로 잃는 것 |
|---|---|---|
| 삽입 1건 | 0.012 ms | — |
| discovery 스캔 | — | 11.05 → 22.62 ms (**2배**) |
| 스캔 대상 크기 | — | 0.69 → 11.20 MB (**16배**) |

**순손실이다.** `lookup` 을 좁게 유지하는 현재 구조가 맞다.

### 확인된 것 — 파사드 설계는 잘 버티고 있다

- Knex 를 빌더로만 쓰는 결정: 실행/풀은 기존 드라이버가 그대로 담당해 위험이 낮았다.
- 콜백 규약(`cb(null, r)` / `cb(true, err)`)을 안 바꾼 것: 호출부 109곳을 안 건드렸다.
- 등가성 하네스: 회차마다 32단계를 비교해 회귀를 즉시 잡았다.
  이번 회차에서 **의도한 1단계만** 달라진 것을 확인했다.
