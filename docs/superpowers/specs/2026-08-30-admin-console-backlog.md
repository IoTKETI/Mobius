# 관리 콘솔 — 들어오는 것 추적

여러 세션이 같은 저장소에서 동시에 움직인다. 콘솔 화면을 확정해 놓으면 코어가
바뀌면서 화면이 뒤따라 깨지므로, **만들기 전에 무엇이 오는지 먼저 적어 둔다.**

이 문서는 살아 있는 목록이다. 다음 두 가지를 기록한다.

1. **감시 기록** — `lite` 에 들어온 변경 중 콘솔에 영향이 오는 것과, 그 판정
2. **대기 목록** — 지금 만들 수 있는 것 / 코어가 먼저 와야 하는 것 / 기각한 것

판정에는 근거를 붙인다. "그럴 것 같다" 로 화면을 만들면 없는 문제에 화면을
붙이게 된다 — 실제로 한 번 그럴 뻔했다(아래 §5 의 mobius4 건).

> **원칙의 근거가 바뀌었다 (2026-08-30).** 예전 근거는 "콘솔은 별도 프로세스라
> 워커의 캐시 무효화 IPC 에 낄 수 없다" 였다. `4809843` 이 리소스 캐시를 통째로

> 더 강해졌다.
>
> - **`subl`.** 알림은 `sub` 테이블이 아니라 부모의 `subl` 을 보고 나간다. DB 에
>   직접 쓰면 `subl` 이 안 따라와 유령이 하나 더 생긴다.
> - **부모 행 잠금.** `update_subl` 이 MySQL 에서 `SELECT … FOR UPDATE` 로 부모를
>   잡는다. HTTP API 를 타야 그 잠금 안으로 들어간다.
> - 구독 알림 · 부모 카운터 · 하위 트리 삭제가 여전히 앱 레이어에 있다.
>
> **읽기는 오히려 안전해졌다.** 캐시가 없으니 콘솔이 DB 에서 읽은 것과 서버가
> 응답하는 것이 항상 같다 — 전에는 워커마다 달랐다.

### 콘솔 함수를 만들어 주실 분들께

콘솔은 별도 프로세스이고 배포 `lookup` 은 5,740만 행이다. 두 제약이 따라온다.

- **워커 메모리에 닿지 못한다.** 워커가 메모리에만 들고 있는 집계는 콘솔이 읽을
  수 없다. DB 나 파일로 나와야 한다.
- **전역 `COUNT(*)`, 선행 와일드카드 `LIKE`, 인덱스를 못 타는 술어는 풀스캔이다.**
  상한을 둔 개수 세기 + 키셋 페이징으로 주면 좋다. 상한에 걸렸으면 조용히 자르지
  말고 `capped` 로 알려 준다 — 화면이 "여기까지가 전부" 로 보이는 것이 가장 나쁘다.
- 커서는 **불투명한 문자열 하나**로. 쪼갤 수 있는 커서는 언젠가 쪼개진다
  (실측: 두 조각 커서에서 한쪽만 넘겼더니 결과가 틀린 게 아니라 루프가 안 닫혔다).

### `518fe56` — json 전용 관문, 콘솔은 지난다

`admin/cse.js` 는 `Content-Type: application/json;ty=N` 을 보낸다. 관문이
부분 문자열로 봤다면 걸릴 자리라 실제 클라이언트 객체로 시험했다.

```
콘솔 클라이언트 POST (application/json;ty=2)   -> 201
  retrieve (Accept: application/json)          -> 200
  setExpiry = update (파라미터 있음)            -> 200
대조군: application/xml 본문                    -> 400   (관문 동작)
함정:  application/json;ty=3;note=xmlish       -> 201   (오인 없음)
```

관문이 `JSON_ONLY_DENY` 를 mime 에만 걸어(`/^(application|text)\/(.*\+)?(xml|cbor)$/`)
파라미터를 보지 않으므로 안전하다.

> **`[json_only]` 로그로 xml/cbor 코드 제거를 판단할 때 콘솔은 표본이 아니다.**
> 콘솔은 json 만 보내므로 그 로그에 절대 안 찍힌다. 로그가 비어 있어도
> "콘솔이 안 쓴다" 는 정보는 들어 있지 않다.

### `4809843` — `cache_man` 을 걷어냈다

콘솔 세션이 만든 `mobius/cache_man.js`(303줄 + 테스트 653줄)를 지웠다. 판단
근거를 남긴다 — 지운 것을 나중에 누가 되살리려 할 때 읽으라고.

**별칭 키 구멍.** 캐시 키는 `request.ri`(클라이언트가 보낸 URL 그대로)인데
무효화 키는 `request.url`(DB 행의 정규 `ri`)이다. 응답의 `ri` 자리에 `sri` 가
들어가므로, **서버가 알려 준 주소로 다시 조회하면 캐시 키가 별칭이 되고
무효화가 그것을 못 지운다.** 직접 재현했다:

```
별칭 GET x40 로 캐시를 채우고 구조화 경로로 DELETE 한 뒤
  별칭 주소 GET x40    ->  200 이 40/40   (지워진 리소스가 계속 나온다)
  구조화 경로 GET x10  ->  404 가 10/10   (무효화는 이쪽만 지웠다)
```

경합이 아니라 영구다 — TTL 이 없고 LRU 상한 5만이 비-CIN 34,313 보다 커서
축출도 안 온다. 낡은 행으로 `acpi` 를 읽으므로 **권한 회수도 안 먹는다.**

이 구멍은 원래 `cache_resource_url` 에 있던 것이고 `cache_man` 이 만든 것이
아니다. 다만 **닫지 않은 채 워커 간 무효화를 고쳐, 캐시가 맞는 것처럼 보이게
만들었다.** 그쪽이 더 나쁘다.

**고쳐서 지킬 값이 안 나온다.** 정규 `ri` 로 키를 잡으면 되지만, 별칭을 정규
`ri` 로 푸는 것이 바로 캐시가 피하려던 그 DB 조회다. 게다가 배포 실측 미스율
1.5/25.9 = 5.79% 는 워커 16개에서 무효화가 자기 것만 지울 때의 기대값
1/16 = 6.25% 와 거의 같다 — **측정된 적중률 94% 가 상당 부분 무효화 고장의
산물**이고, 그것을 고치면 어차피 사라진다.

재도입 조건은 `app.js` 상단 주석과 `test/no-resource-cache.test.js` 에 있다.

### `06db502` — 시뮬레이터가 거짓말하던 것이 해소됐다

들어오기 전에 실측한 것:

```
잠근 곳 직접 조회/탐색 (제3자)   403
상위 AE 탐색 (제3자)            200, 4건 중 2건이 잠근 곳의 경로
콘솔 시뮬레이터                 DISCOVERY = 거부
```

시뮬레이터는 "거부" 라는데 상위 탐색에는 경로가 그대로 나왔다. 내용은 안 새고
**경로가 샜다**(이름·트리 구조·CIN 개수·생성 시각). 관리자가 화면을 보고
"잠갔다" 고 판단하면 틀리는 상태였다.

들어온 뒤 같은 시나리오: **누출 0건**, 시뮬레이터와 일치. 필터가 판정에
`security._evaluate_acp_rows` 를 그대로 쓰기 때문이다 — 시뮬레이터와 같은 함수라
원리적으로 갈리지 않는다.

> 남은 것: `conf.acpDiscoveryFilter` 를 `'off'` 로 두면 다시 새는데, 콘솔의
> `/api/session` 이 그 값을 안 내보낸다. §3-6.

## 2.5 설정 화면 (`conf.json`) — 사용자 지시, 준비 중

> 사용자 지시 둘. **"관리 UI 에서 conf.json 설정값을 설정할 수 있게, 필요한 것만
> 노출해서"**, 그리고 **"body limit 설정을 관리 UI 에서. 5메가든 10메가든"**.

### 이미 만든 것 — `admin/conf_store.js`

읽기/쓰기 기계. 스키마는 코어(`mobius/conf_schema`)가 준다. 테스트 19건.

- **모르는 키 보존** — 이 파일은 여럿이 동시에 고친다
- **원자적 쓰기(임시파일 + rename)** — 아래 이유로 필수다
- **비밀은 값 없이 존재 여부만** — `dbpass` `superUser` `adminPassword` `adminOrigin`
- **관문 두 겹** — `exposed()` 확인 + 코어 `validate()`. 한때 코어 `validate()`
  가 `dbpass` 에 `{ok:true}` 를 줬다(고쳐졌다). 비밀이 파일에 써지는 사고는
  되돌릴 수 없으므로 겹쳐 둔다
- **콘솔 자신의 키**(`adminPort` 류)는 코어 스키마가 모른다 — 알려진 키로 넣되
  편집은 막는다. 잘못 넣으면 다음 재기동에 화면으로 돌아올 길이 없다

### 원자적 쓰기가 필수인 이유 (실측)

`mobius.js` 가 파싱 실패 시 **설정 전체를 버리고 파일을 덮어썼다.** 워커 25개가
각자 기동 때 이 파일을 읽으므로, 콘솔이 제자리에서 쓰는 도중 워커 하나가
backstop 으로 되살아나면 그 경로를 탄다.

```
원본 8개 -> 반쪽 파일을 한 번 읽힌 뒤 3개만 남음
dbpass: realpassword -> dksdlfduq2 (하드코딩 기본값)
adminPassword 소실 -> 콘솔도 못 뜬다
```

> 코어가 고쳤다(`c19ca51`) — 이제 **파일이 없을 때만** 만들고 파싱이 깨지면
> 건드리지 않는다. mobius.js 를 그대로 떼어 실행해 확인했다.

### 아직 못 하는 것 — "지금 도는 값"

`conf` 는 기동 시 읽히고 `cluster.fork()` 가 엔트리를 재실행하므로 **워커마다
값이 다를 수 있다.** 되살아난 워커만 새 파일을 읽기 때문이다. 그래서 "적용값"
을 한 줄로 보여 주면 그 화면도 거짓말을 한다.

코어가 만들 계약: `{key, file, workers:[{pid,value}], agree}`. `agree:false` 면
화면이 "25개 중 18개는 observe, 7개는 off" 라고 말한다. **오기 전까지는 파일
값만 보여 주고 "지금 도는 서버의 값은 아직 알 수 없다" 를 명시한다.**

적용 시점은 키마다 다르다 — `runtime`(즉시) / `reload`(`reloadWith` 를 다시
불러야 함) / `restart`. 화면이 이걸 말하지 않으면 관리자가 "관찰 모드 껐다" 고
믿고 넘어간다.

### `maxBodyBytes` — 아직 스키마에 없다

사용자가 직접 지시한 항목인데 **코어 스키마에 등록되지 않았다.**

```
mobius.js:101      conf.maxBodyBytes 를 읽는다
conf_schema.js     maxBodyBytes 0회
```

등록되면 `conf_store` 가 자동으로 집어 온다(스키마를 그대로 쓰므로). 화면 쪽
요건만 적어 둔다.

| | 값 | 근거 |
|---|---|---|
| 기본값 | 10,485,760 (10MB) | |
| **하한** | **4,194,304 (4MB)** | 배포 `cin.con` 400만 행 표본 **최대 4,058,640 B**. 그보다 낮추면 이미지 장치의 정상 쓰기가 그 순간부터 413 |
| 상한 경고 | ~100MB | **실측 근거 없음.** 워커 하나가 요청 하나에 쓰는 메모리이고 워커 수 × 동시 요청만큼 곱해진다 |
| `0` | **받지 않는다** | `outboundTimeoutMs` 와 반대다. 여기서 0은 "상한 없음" 이고 그게 8년간 죽어 있던 상태다(6MB 본문이 201 로 통과) |

- **입력은 MB, 저장은 바이트.** 사용자가 "5메가든 10메가든" 이라고 했다.
  `10485760` 을 손으로 치게 하면 자릿수를 틀린다.
- 사용자가 말한 5MB 는 통과하지만 **여유가 23% 뿐**이다. 화면이 그걸 보여 준다.
- 틀렸을 때 증상이 보인다 — `[body_limit]` 로그가 쌓이고 이미지 장치가 413 을
  받는다. 로그 화면이 생기면 관리자가 스스로 되돌릴 수 있다.

## 2.6 구독 감사를 **콘솔의 DB 레이어로 직접 돌려 봤다** (2026-08-31)

읽어서 판단하지 않고 돌렸다. `feat/sub-audit-mqtt` 의 `sql_action.js` 를
`mobius/` 안에 복사해 두고, 콘솔이 쓰는 것과 같은 `db.connect` /
`db.getConnection` 으로 로컬 MySQL 에 붙여 커서를 끝까지 돌렸다.

    페이지 1, 훑은 구독 18, 적발 6
    사유별: {"nu_no_poa":5,"nu_unresolved":1}
    상수에 없는 reason: 없음

코어가 커밋 메시지에 적은 수치와 정확히 같다. **화면이 그릴 데이터가 실제로
나온다** — 예전에 `audit_subscriptions` 가 배포 형태에서 0건을 돌려주던 문제는
해소됐다.

### 문서화된 반환 형태에 `severity` 가 빠져 있다

주석의 `@returns` 는 `findings: [{ ri, pi, nu, reason, detail }]` 라고 적었지만
실제로 돌려주는 열은 여섯이다:

    detail, nu, pi, reason, ri, severity

`severity` 는 `broken` / `suspect` 둘이고, 갈리는 자리는 하나다:

| reason | severity |
|---|---|
| `no_sub_row`, `nu_empty`, `nu_unresolved`, `nu_no_poa`, `nu_bad_scheme` | `broken` |
| `mqtt_topic_unregistered` | **`suspect`** |

집계도 `byReason` 옆에 `bySeverity` 가 같이 온다.

**이것이 §3-1 이 걱정하던 바로 그 구분이다.** MQTT 토픽이 AE 로 등록돼 있지
않다는 것은 강한 신호지만 증거가 아니다(배포 표본 3,452건 중 1,028건, 29.8%).
코어가 이미 등급으로 갈라 놨으므로, 화면은 **직접 만든 기준이 아니라 코어의
`severity` 를 그대로 쓴다.** 고아 화면에서 `broken`/`suspect` 를 섞지 않기로
한 것과 같은 규칙이다 — 삭제 대상에는 `broken` 만 담는다.

### 커서는 상한에 걸릴 때만 생긴다

`batch: 5` 로 줘도 18건이 한 번에 다 훑리고 `next` 는 `null` 이었다. `batch` 는
DB 페이지 크기이고 함수가 내부에서 계속 돈다. `next` 가 채워지는 것은
`scanCap`(기본 20,000) 이나 `maxFindings`(기본 2,000) 에 걸렸을 때다.

화면은 그래도 커서를 처리해야 한다. **배포는 구독이 3,452건**이라 상한 설정에
따라 갈린다.

### 알림 결과 신호는 아직 못 쓴다 — 결정이 필요하다

`feat/noti-signal` 이 알림 결과를 `ok`/`reject`/`fail`/`unknown` 으로 가른다.
이 화면에 가장 필요한 데이터다 — 감사는 "보낼 수 없는 구독" 을 DB 로 찾지만,
URL 형식 `nu` 의 도달성은 **보내 봐야만** 안다(감사 코드 주석도 그렇게 적었다).

그런데 그 판정은 **로그에만 남는다.** 커밋이 "저장도, 정책도, 자동 삭제도
없다" 고 명시했고 스키마를 안 바꿨다. 콘솔은 DB 만 읽으므로 지금 상태로는
화면에 못 올린다. 길은 둘이다:

1. 콘솔이 `[noti]` 로그를 읽는다 — 콘솔이 처음으로 로그 파일에 의존하게 된다.
   로테이션·경로·다중 워커를 콘솔이 떠안는다.
2. 코어가 판정을 남긴다(구독 행의 마지막 결과, 또는 별도 테이블).

**2번을 코어에 요청한다.** 1번은 콘솔의 입력 표면을 DB 하나에서 둘로 늘리고,
그 둘째가 형식이 보장되지 않는 텍스트다. 다만 이건 코어의 몫이라 요청만 한다.

#### 요청했고 **사용자 결정 대기** (2026-08-31, mobius-87 회신)

코어가 "제가 결정할 일이 아니다" 며 사용자께 올렸다. 권고는 **하는 쪽**이다.
같이 준 실측이 내 근거 하나를 지웠다:

- **처리량은 논점이 아니다.** 배포에서 120초에 알림 판정 1건 — 하루 약 720건
  (구독 3,452개 기준 초당 0.008건). "핫패스에 쓰기를 더한다" 는 부담은 없다.
- **진짜 비용은 구조다.** `mobius/sgn_man.js` 는 **DB 접근이 0곳**이다
  (`fs`·`http`·`https`·`mqtt`·`coap`·`url`·`outbound` 만 require). 커넥션을
  주려면 파사드를 물려야 하고, 그건 이 모듈이 DB 를 모른다는 성질을 깨는
  변경이다. 위로 올리는 길은 막혀 있다 — `sgn.js:184` 가 `setTimeout(1~10ms)`
  안에서 fire-and-forget 으로 부르고 그 시점에 커넥션은 이미 반납됐다.
- **명시된 설계 결정에 닿는다.** CLAUDE.md 가 "알림은 fire-and-forget이다"
  라고 적어 두었다. 판정 저장은 재시도도 자동 삭제도 아니지만 발송 경로가
  DB 를 알게 되는 첫 걸음이다.

**콘솔 쪽 태도.** 이 답을 기다리느라 §3-1 을 멈추지 않는다. 감사(DB 기반)만으로
`broken` 5종은 지금 그릴 수 있다. 알림 판정은 URL 형식 `nu` 의 도달성을 채우는
**둘째 층**이므로, 화면을 그 층 없이도 성립하게 설계하고 열만 비워 둔다.

## 3. 지금 만들 수 있는 것 — 코어 함수가 이미 있다

### 3-1. 구독 화면 — 설계를 다시 그려야 한다 ⚠

> **배포 실측이 전제를 뒤집었다 (2026-08-30, mobius-87).** `audit_subscriptions`
> 를 그대로 화면으로 만들면 **배포에서 0건짜리 빈 화면**이 된다.

배포 숫자:

```
sub 3,452   (lookup ty=23 과 정확히 일치 — 고아 0)
  mqtt   3,425  99.2%      고유 nu 값   202 / 3,452
  http      27   0.8%      상위 3개      1,951건 (57%)
  ws/coap    0             ID 형식 nu        0
                           nu 2개 이상       0
```

**왜 0건인가.** `audit_subscriptions` 는 URL 형식 + 유효 스킴이면 findings 를
내지 않는다("URL 형식은 여기서 도달성을 알 수 없다" — 코드 주석). 배포는 100%
URL 형식이고 `mqtt`/`http` 는 둘 다 유효 스킴이며, `no_sub_row` 도 0(행 수가
정확히 일치)이다. 남는 사유가 없다.

**재현 (배포 비율 축소, mqtt 40 / http 1):**

```
scanned 41   findings 0   byReason {}
대조군 — 배포에 없는 형태를 넣으면 잡힌다:
  nu_bad_scheme  ftp://x/y
  nu_unresolved  /Mobius/사라진AE
```

**함수는 정상이다. 배포 데이터에 그것이 판정할 형태가 없을 뿐이다.**

#### 그래서 화면은 이렇게

- **주 화면은 엔드포인트 롤업.** 고유 `nu` 가 202개뿐이고 상위 3개가 57% 다.
  구독마다 한 줄이면 같은 수신처가 993번 반복된다. 호스트·토픽 단위로 묶고
  구독 목록은 드릴다운으로 둔다.
- **판정 단위가 3,452 → 202 로 줄어든다.** "이 브로커·토픽이 살아 있나" 를
  202번만 답하면 전부 판정된다. 구독을 하나씩 찌를 필요가 없다.
- **`audit_subscriptions` 는 보조 지표로 둔다.** 0건이 정상인 화면이므로,
  0건을 "문제 없음" 이 아니라 **"이 감사가 판정할 수 있는 것이 없음"** 으로
  적어야 한다. 둘은 다르다.
- MQTT/WS 는 QoS0 라 브로커 도달조차 알 수 없다. **'판정 불가' 배지가 필요하고,
  MQTT 구독을 "안 쓰는 구독" 목록에 넣으면 안 된다.**
- `et` 는 이 감사에 없다(일부러 뺐다). §3-2 참고.

#### 코어 쪽에서 정해질 것

mobius-87 이 방향을 사용자에게 확인 중이다. 원래 계획한 (구독ri, 엔드포인트)
관측 테이블은 3,452행 중 99.2% 가 `unknown` 으로 채워져 권하지 않는다는 판단.
대안 둘 — (가) MQTT 브로커에 묻는 신호(`$SYS`/관리 API), (나) `audit_subscriptions`
에 MQTT 판정 추가(호스트가 아는 브로커인지, 토픽의 AE-ID 가 실제 등록돼 있는지를
DB 만으로). **정해진 뒤에 화면을 그린다.**

#### 확신 등급을 섞으면 멀쩡한 구독을 지운다 ⚠

`da29b23` 이 사유마다 등급을 붙였다(`db_sql.SUB_AUDIT_SEVERITY`, 결과의
`bySeverity`).

| 등급 | 뜻 | 화면에서 |
|---|---|---|
| `broken` | 그 자체로 보낼 수 없다. 근거가 DB 안에서 닫힌다 | 삭제 후보로 올려도 된다 |
| `suspect` | 못 보낼 가능성이 높지만 DB 만으로는 단정할 수 없다 | **삭제 후보로 올리면 안 된다** |

지금 `suspect` 는 `mqtt_topic_unregistered` 하나다. MQTT 토픽을 AE 로 등록하지
않고 듣기만 하는 클라이언트가 있을 수 있다(배포 표본의 `mobmon_*` 이 그렇게
보인다). 등록이 없다는 것은 강한 신호지만 증거가 아니다 — MQTT 3.1.1 에는
구독자 존재를 발신자가 알 방법이 없다.

**두 등급을 한 목록에 섞어 일괄 선택을 열면 안 된다.** 나누어 보여 주고,
`suspect` 쪽은 "확인이 더 필요함" 으로 둔다.

사유 코드는 `db_sql.SUB_AUDIT_REASON` 으로 나온다 — 문자열을 화면에 복제하지 않는다.

### 3-2. 만료 화면의 구독(ty=23) — 노출은 의도된 설계다

> **결정 (2026-08-30, 사용자).** 만료된 구독을 만료 화면에 **그대로 노출하고,
> 관리자가 확인해 조치하는 것**이 의도한 동작이다. 감추지 않는다.

한때 이것을 결함으로 올렸었다. 아니다. 사실관계는 이렇다.

- `et` 는 런타임 어디에서도 강제되지 않는다 — 만료 스윕은 주기 실행이 걸려 있지
  않고, 알림·조회 경로에 `et` 비교가 없다.
- 그래서 **`et` 가 지난 구독의 대다수가 지금도 정상 동작 중**이다
  (배포 표본에서 `et` 의 81% 가 이미 과거).
- 서버가 알아서 정리하지 않으므로 **사람이 보고 판단하는 자리가 필요하고, 그
  자리가 이 화면이다.** 목록에서 빼면 아무도 못 보게 된다.

남는 것은 결함 수정이 아니라 **판단 재료**다. "만료됨" 이 곧 "안 쓰는 것" 은
아니므로, 관리자가 지우기 전에 그 구독이 실제로 도달 가능한지 알면 좋다 —
그 답이 §3-1 의 `audit_subscriptions` 다. 두 화면을 잇는 것은 그때 고민한다.
(URL 형식 `nu` 와 MQTT 는 감사가 판정하지 못하므로 "판정 불가" 가 나온다는
점도 함께 보여야 한다.)

### 3-3. ACP 신규 생성 + 대상에 붙이기

지금 쓰기는 `/api/acp/save`(기존 ACP 의 `pv`/`pvs` PUT) 하나뿐이다. `admin/cse.js`
에도 `create` 가 없다. 운영 방안이 정한 패턴 A/B/C 를 마법사로 두면 "예외 세
가지만 쓴다 · ACP 개수를 한 자리로 유지한다" 방침이 화면에서 지켜진다.
(템플릿 버튼은 편집 화면에 이미 있다 — `c031de6`)

### 3-4. 리소스 잠금 / 해제 — `acpi` 붙이기·떼기

운영 방안이 명시적으로 관리 UI 에 넘긴 항목이다. 붙이는 단위는 **AE 하나** —
컨테이너·CIN 에는 막아야 한다(상속되므로 붙일 이유가 없고, 붙이는 순간 관리
대상이 수만 개가 된다). 배포에 실제 대상이 있다: `/Mobius/sch8` 이 없는
`/Mobius/acp_sch1` 을 가리켜 잠겨 있다.

`acpi` 는 `varchar(200)` 이라 최대 7개다. 고르는 UI 여야 한다 — 서버가 오타를
막아 주기는 하지만(`400-63`), 손으로 적게 하면 그 400 을 화면에서 처음 만난다.

### 3-5. 전역 변경 이력 화면

`select_acp_audit` 은 `ri` 필터 없이도 부를 수 있는데 콘솔은 ACP 상세에서만
쓴다. `acpi_set`(리소스에 잠금을 걸고 푼 기록)은 ACP 상세에 안 보인다 — 그
리소스가 ACP 가 아니기 때문이다.

### 3-6. `/api/session` 에 `acpDiscoveryFilter` 노출

`mobius.js:133` 이 `global.acp_discovery_filter` 를 세운다. 콘솔의 `acp` 블록은
`observeMode/attachPolicy/defaultPolicy/audit/denyLog` 다섯만 내보낸다. `'off'`
면 잠근 곳의 경로가 다시 새므로 시뮬레이터의 `DISCOVERY` 판정이 보호를 과장하게
된다. 기존 블록과 같이 **설정값 기준**이라고 밝히면 된다.

### 3-7. 그 밖에

- 다중 `acpi` 는 OR 합집합이고 평가 순서는 `ri` 오름차순 — 화면도 그 순서로.
  정렬을 콘솔에서 다시 계산하면 MySQL 콜레이션과 갈릴 수 있으니, 코어가
  순서를 결과에 실어 주는 쪽이 안전하다.
- `acpAudit: 'off'` 일 때 "이력이 없습니다" 는 오표시다 — 끈 것과 없는 것은 다르다.
- 보존 정책(`mni`/`mbs`)이 사실상 꺼져 있다 — 판단할 화면이 없다.
- 컨테이너 `acpi` 증가 감시 — discovery 필터 성능 전제(`acpi` 가 채워진 리소스가
  배포에 2개)가 깨지는지.

## 4. 코어가 먼저 와야 하는 것

### 4-1. 대형 컨테이너 카운터 검증

인수인계 문서가 명시적으로 UI 에 넘겼는데(유예된 7개, `cni` 109만~593만) 착수할
수 없다.

- `reconcile_cnt_counters` 는 **드라이런이 없다** — 드리프트를 찾으면 즉시
  `update_cnt_cni` 로 UPDATE 한다. 조회 용도로 못 쓴다.
- 단건 지정 입구가 없다 — 커서 범위 스캔이라 `ri` 하나를 겨냥할 수 없다.
- 콘솔이 스윕을 돌리면 **안 된다.** `reconcile_running` 가드가 프로세스 로컬이라
  별도 프로세스인 콘솔은 그 바깥이고, 두 커서가 각자 전진하면 컨테이너를 건너뛴다.
- 유예/실패 목록이 `console.log` 로만 나가고 버려진다.
- **보정 쓰기 경로가 없다.** `cni`/`cbs` 는 oneM2M 에서 읽기 전용이고, PUT 경유는
  `st` 를 올려 없던 구독 알림을 낸다. 콘솔이 `update_cnt_cni` 를 직접 부르면
  워커 캐시가 낡는다 — "쓰기는 전부 CSE 경유" 의 첫 예외가 된다.

필요한 것: 읽기 전용 단건 집계 함수 · 유예 목록 조회 · 보정 쓰기 경로 결정.

### 4-1.5 알림 판정 저장 — **사용자 결정 대기**

§2.6 참고. 코어가 판정은 하지만 로그에만 남긴다. 권고는 "하는 쪽", 결정은
사용자. 콘솔은 이것 없이도 성립하게 §3-1 을 설계한다.

### 4-2. 거부 이력 / 로그 조회

운영자가 "왜 막혔나" 를 물을 곳이 콘솔뿐인데 볼 방법이 없다. `[acp] deny` 는
`console.log` 로만 나가고, 저장소가 쓰는 유일한 로그 파일은 morgan 액세스 로그다.
`acp_observe.snapshot()` 은 워커 메모리에만 있고 콘솔이 닿지 못한다.

필요한 것: 파일 싱크 또는 감사 테이블. 표본 정책(`denyLog: 'sample'`, 초당 5줄)
때문에 기록이 전수가 아니라는 점도 화면이 말해야 하므로 함께 정해야 한다.

### 4-3. 구독 목록·상세

`select_sub` 은 부모별 조회뿐이라 전역 페이징 진입점이 없다.
필요한 것: `select_sub_list`(키셋 페이징, `{rows, more, next}`) ·
`select_sub_detail`. 목록 행에 `nu`·`enc` 를 붙일 때는 구독마다 읽지 말고
배치 `whereIn` 으로.

### 4-4. `subl` 계열 — **보류 권장**

`subl` 자체를 폐기하는 방향으로 결론이 났다(진실은 `sub.pi` 에 있고 FK CASCADE 가
정합을 보장한다). 곧 없어질 것에 화면을 붙이는 셈이라 착수하지 않는다.

배경: `update_lookup` 이 `subl` 을 절대값으로 덮어쓰고 호출부가 26곳이라,
구독을 동시에 만들면 조용히 사라진다(실측: 12개 동시 생성 → 부모 `subl` 에 1개).
사라진 것들은 리소스로는 살아 있는데 알림만 영영 못 받는다.

### 4-5. AE·CSE 삭제 전 "깨지는 구독" 미리보기 → **코어가 왔다 (`da29b23`)**

> **`opts.targets` 가 들어왔다.** "이 리소스를 지우면 누구의 알림이 끊기는가" 에
> 답한다. MQTT 토픽 판정도 함께 왔다. **배포에 해당 사례가 986건 있다.**
> 대기가 풀리면 삭제 다이얼로그에 붙인다 — 지금은 자손만 경고하고 남의 구독은
> 말하지 않는다.
>
> 여기서도 등급을 섞지 않는다(§3-1). 삭제 경고에 `suspect` 를 넣으면 "이거
> 지우면 986건이 끊긴다" 가 과장이 되어, 몇 번 겪고 나면 경고 자체를 무시하게
> 된다. `broken` 을 앞세우고 `suspect` 는 따로 센다.

(아래는 들어오기 전의 기록)

지금 삭제 다이얼로그는 **자손**만 경고한다. 지우는 리소스를 `nu` 로 가리키는
구독은 말하지 않는다. `audit_subscriptions` 에 `opts.targets` 를 더하는 쪽이
새 함수보다 낫다 — 같은 2단계 해석을 재사용한다. mobius-87 이 받았고, 위 §3-1
방향이 정해진 뒤에 함께 넣기로 했다.

> **주의 — ID 형식 매칭만으로는 아무것도 안 잡힌다.** 배포의 `nu` 는 100% URL
> 형식이고 ID 형식이 0건이다. "이 AE 를 가리키는 구독" 을 찾으려면 MQTT 토픽의
> AE-ID 부분(`mqtt://host/<AE-ID>`)까지 봐야 한다. 상위 3개 토픽이
> `Sip3jTShhxs` 2,004건 · `S9X2LBlfBmM` 410건 · `SOrigin_cov` 127건이다.

## 5. 기각 — 다시 올라오지 않게

전수 조사에서 나온 뒤 **반증된** 것들이다. 근거를 남긴다.

| 주장 | 왜 아닌가 |
|---|---|
| discovery 필터가 콘솔을 틀리게 만든다 | 반대다. 콘솔 읽기는 DB 직접이라 필터를 안 타고, 필터가 시뮬레이터와 같은 평가 함수를 써서 오히려 맞아졌다 |
| 콘솔이 `resolve_acpi_entries` 를 안 불러 정상 참조가 미해결로 남는다 | `acp_lint.lint_acpi_refs` 가 내부에서 이미 부른다(`acp_lint.js:168`) |
| `select_lookup_acpi_in` 을 콘솔이 안 쓴다 | 소비자를 기다리는 export 가 아니라 `acp_filter` 의 내부 헬퍼다 |
| `select_sum_cbs`/`select_sum_ae` 가 미사용 | `app.js:1570/1580` 이 이미 서비스한다 |
| 관찰 모드 배지가 없다 | `App.vue` 가 이미 띄운다 |
| 마이그레이션 007 안내가 없다 | `admin/server.js` 가 503 + 적용 명령을 담아 준다 |
| `macp` 가드레일로 콘솔이 400 을 받는다 | 콘솔의 쓰기 본문에 `macp` 가 없다 |
| `[noti]` 로그로 알림 실패율 화면을 만든다 | 그 로그는 파일로 안 나간다. 코어 작업이지 콘솔 작업이 아니다 |

### mobius4 건 — 다른 저장소였다

`mobius4-c0` 세션이 상세한 지적을 보내왔으나 **다른 저장소**(`Workspace/mobius4`,
Sequelize/PostgreSQL/`hostingCSE.js`)를 보고 있었다. 이 저장소에는 `hostingCSE.js`
도 `int_cr` 도 없고, "`ty` 단독 인덱스 없음" 은 여기서 정반대다
(`mobiusdb.sql:342` 에 `idx_lookup_ty` 가 있다). 근거를 대고 확인 요청했고 상대도
확인 후 철회했다.

**교훈:** 다른 세션의 지적도 이 저장소의 코드로 확인하고 받는다. 그대로 반영했다면
없는 경합에 표류 감지를 붙이고, 없는 컬럼(`int_cr`)을 읽는 시뮬레이터를 만들 뻔했다.
