**날짜**: 2026-08-28
**시작점**: `lite` = `c6c3bd7` (배포본 장애 대응 4건 통합 완료)
**작업 브랜치**: `worktree-db-layer-migrate`

---

## 1. 목표 — 왜 이걸 하고 있나

### 원래 목표 (변함없음)

> DB 관련 함수들을 정형화·규격화·레이어화해서, **코어가 MySQL 인지 SQLite 인지
> 모르게** 만든다. 기존 동작을 유지하면서 하나씩 바꿔 간다.

**완료 기준**: `global.usesqlite` 를 읽는 곳이 `mobius/db/index.js` **한 곳**뿐일 것.

### 진행하며 늘어난 목표 2가지

**(가) 배포 서버에 안전하게 반영할 수 있을 것**

개발은 여기서 하고 배포는 `gcs.iotocean.org` 에서 한다. 그 서버에는 이미
데이터가 많다 (`cin` 1억 4558만 행 / 255GB, `lookup` 5740만 행 / 21.8GB).
코드는 그냥 덮으면 되지만 **DB 스키마는 그렇지 않다.**

지금 이 저장소에는 마이그레이션 수단이 **하나도 없다**:

| 백엔드 | 기존 DB 에 스키마 변경이 반영되는 방법 |
|--------|------------------------------------|
| SQLite | 기동마다 스키마 재실행(`IF NOT EXISTS`) — 우연히 되는 것이지 설계가 아님 |
| **MySQL** | **없음** — `mobiusdb.sql` 은 최초 설치용 |

**(나) 전환하면서 드러나는 실제 결함을 고칠 것**

함수를 하나씩 열어 보면 대개 뭔가 깨져 있었다. 지금까지 실측으로 확인해 고친 것이
14건이다(3절). 이건 부산물이 아니라 이 작업의 실질적 가치다.

## 2. 현황 (2026-08-31 갱신)

### 목표를 다시 적는다

원래 표현은 "`global.usesqlite` 를 읽는 곳을 한 곳으로" 였는데, 그것은 대리
지표였다. 사용자가 바로잡아 준 진짜 목표는 이것이다.

> **MySQL·SQLite 말고 다른 DB 를 붙일 때 최소한만 고쳐도 되게 한다.**

둘은 다르다. 전자를 좇으면 "두 백엔드가 같은 결과를 내야 한다" 로 기울어
등가성을 커밋마다 게이트로 걸게 되는데, **백엔드마다 동작이 다른 것은 정상**
이고 그게 어댑터가 있는 이유다. 지켜야 할 것은 하나뿐이다 — 프로덕션(MySQL)이
안 깨질 것. SQLite 는 *돌면* 된다.

완료 조건도 그래서 바뀐다: **`mobius/db/postgres.js` 를 쓰면 끝. 다른 곳은
안 건드린다.**

### 지표

| 지표 | 최초 | 현재 |
|------|------|------|
| `global.usesqlite` (코어 전체) | 44+ | **2** |
| 파사드를 우회해 커넥션을 얻는 파일 | 8 | **5** |
| 어댑터 등록 방식 | 손으로 적은 표 | **디렉터리 자동 인식** |
| 백엔드 선택자 | `usesqlite` boolean | **이름** (`usedb`) |
| 단위 테스트 | 0 | **773 pass / 0 fail** |
| 등가성 하네스 | 없음 | 32단계, 양쪽 백엔드 |

### 무엇이 실제로 달라졌나

**어댑터는 파일 하나다.** `mobius/db/<이름>.js` 를 두면 파사드가 자동으로
등록하고, `test/db-adapter-contract.test.js` 가 그 파일도 검사해 **빠진 것을
이름으로 알려준다.** 목록을 고칠 필요가 없다.

**선택자가 이름이다.** 예전에는 `usesqlite` boolean 이라 **세 번째 백엔드를
말할 방법이 아예 없었다.** 이제 `node mobius.js postgres` 나 `conf.json` 의
`"db": "postgres"` 로 고른다.

**커넥션 원천이 파사드 하나다.** 예전에는 `db_action` 이 자기 MySQL 풀을
들고 있어서, 어느 백엔드를 골랐든 요청 경로가 늘 MySQL 에서 커넥션을 받았다.
실측으로 확인한 증상 — MySQL 을 닿지 않는 주소에 두고 SQLite 모드로 띄우면
`listen` 에 도달하지 못했다(MySQL 에러조차 안 찍혔다. `acquireTimeout` 이
50초라 조용히 매달렸다). 지금은 뜬다.

**sqlite 핸들이 하나다.** `db_sqlite.js` 와 파사드 어댑터가 같은 파일을 각자
열어 한 프로세스에 핸들이 둘이었고 스키마 초기화도 두 번 돌았다.

### 남은 2개 — 없앨 것이 아니라 옮길 것

| 위치 | 무엇이 다른가 |
|------|--------------|
| `mobius/cnt_man.js:100` | 카운터 갱신. MySQL 은 다중 테이블 UPDATE 한 문장, SQLite 는 두 문장 |
| `mobius/sql_action.js:2122` | `delete_oldest`. **알고리즘 자체가 다르다** — MySQL 은 트랜잭션 + 행 잠금, SQLite 는 잠금 없이 |

둘 다 **진짜로 백엔드마다 동작이 다른 곳**이다. 통일할 대상이 아니라 어댑터
메서드로 옮길 대상이다. 그러면 코어에는 분기가 없고 각 어댑터가 자기 방식대로
구현한다 — 세 번째 백엔드가 와도 `if` 가 늘지 않는다.

`delete_oldest` 는 추가로 핸들의 드라이버 API 를 직접 쓴다
(`beginTransaction` / `commit` / `rollback` / `escape`). `.escape()` 는
sqlite3 에도 pg 에도 없다. 이 함수가 살아 있는 한 `sql_action.js` 는
`usesqlite` 리더로 남는다.

### 이 단계에서 그만두는 이유

프로덕션은 MySQL 이다. 남은 둘을 옮겨서 얻는 것은 "세 번째 백엔드를 붙일 수
있게 되는 것" 이고, 위험은 전부 SQLite 모드에 몰려 있다. SQLite 를 실제로
쓰기로 할 때 이어서 하면 된다 — 그때까지 `test/usesqlite-single-reader.test.js`
가 남은 수를 세고 있으므로 몰래 늘어나지 않는다.

## 3. 지금까지 고친 실제 결함 (전부 실측 확인)

| # | 결함 | 영향 |
|---|------|------|
| 1 | ACP 정책 갱신이 SQLite 에서 유실 | 접근 제어가 안 바뀜 |
| 2 | 구독(SUB) 갱신이 SQLite 에서 유실 | 알림 설정이 안 바뀜 |
| 3 | SQL Injection 2건 (`update_lookup`, `update_acp`) | `pv` 는 클라이언트 입력 |
| 4 | `update_cnt_by_delete` 인자 누락 | CIN 을 지워도 `cni`/`cbs` 가 안 줄었다 |
| 5 | `get_cni_count` 가 매번 O(n) 재집계 | 100k 기준 7.2ms → 0.13ms (**56배**) |
| 6 | `st` 가 CIN 사건에만 반응 | purge·CNT생성·SUB삭제 시 안 올랐다 |
| 7 | CNT 생성 시 부모 캐시 미무효화 | 조회가 낡은 `st` 를 돌려줌 |
| 8 | 만료 스윕이 **정반대로** 동작 | 만료 대상은 남기고 그 자식을 지웠다 |
| 9 | `et` 기본값이 생성+2년 | 스윕이 고쳐지면 조용히 사라질 뻔했다 |
| 10 | `useCert` 뒤 10억회 busy-wait 스핀 | 죽은 코드였으나 되살아났으면 장애 |
| 11 | 파사드 빌더의 동기 throw | 워커가 죽었다 |
| 12 | **동시 CIN 생성 시 57% 유실** | 40건 동시 → 17건만 성공 (`rn` 충돌) |
| 13 | `la`/`ol`/`delete_oldest` 가 틀린 대상 선택 | `ct` 초 단위 동점, MySQL `ol` 은 정렬 자체가 없었다 |
| 14 | **SQLite 스키마에 인덱스 0개** | 매 요청 쿼리가 풀스캔 (14.19ms → 0.18ms, **77배**) |

정합 작업은 운영 DB 에서 **실제 드리프트 3건**을 찾아 교정했다.

## 4. 이번 회차에 할 일

### A. 마이그레이션 러너 (사용자 항목 2)

```
migrations/
  001-<name>.js        번호순, 멱등
tools/migrate.js       --check (읽기 전용) / --apply
```

- **`schema_migrations` 테이블**에 적용 이력 기록
- **파사드를 통해 두 백엔드 모두** 지원
- **자동 실행 안 함** — 배포 시 사람이 명시적으로 호출
- MySQL 은 `ALGORITHM=INPLACE, LOCK=NONE` (무중단)

이미 만든 `tools/sqlite-indexes.js` 는 이 러너로 흡수한다.

### B. `lookup(pi, ty, ct)` 복합 인덱스 (사용자 항목 3)

운영에서 측정한 근거:

```
la 쿼리 (CIN 593만 건 컨테이너)
  key: idx_lookup_ct
  rows: 22,269,440      ← 2227만 행 범위 스캔
  filtered: 1.87%
```

복합 인덱스가 있으면 `rows: 10` 이 된다. A 의 첫 마이그레이션으로 넣는다.

**주의**: `lookup` 5740만 행이라 ONLINE DDL 로도 수십 분 걸린다. 한산한 시간대에.

### C. 착수 전 반드시 손봐야 할 것

**`reconcile_cnt_counters` 가 운영 규모를 못 견딘다.** 컨테이너마다 `cin` 하위
질의를 도는데, 593만 건짜리 컨테이너에서는 그 자체가 무겁다. 30,220개 컨테이너 ×
CIN 1억 4558만 규모에 그대로 올리면 안 된다.

고칠 방향: 큰 컨테이너를 건너뛰거나, 배치를 나누거나, 표본만 검사.

## 6. 운영 배포 시 지켜야 할 것

- **`id_ed25519` 가 `.gitignore` 에 없다.** 지금은 추적되지 않지만 `git add -A`
  한 번이면 커밋된다. 추가 필요.
- 배포 서버는 **MySQL** 이다 (`usesqlite: "false"`). SQLite 인덱스 작업은 무관.
- 스키마 변경은 **배포 전에** 마이그레이션을 돌리고, 그 다음 코드를 올린다.
- `mni` 기본값이 3153600000 이라 보존 정책이 사실상 작동하지 않는다.
  CIN 593만 건짜리 컨테이너가 존재한다 — 별도 판단 사항.
