# 관리 콘솔 목표 재정의

- 작성일: 2026-09-01
- 계기: 사용자 지시 — *"단순하게 리소스 관리나 권한을 UI로 관리하면 좋겠다는
  생각이었는데, 하다 보니까 전체 모비우스 서버 설정, db 설정, 실행과 종료의
  기능이 추가되면서 기능이 확대가 되었어. 다시 한번 정리해서 목표를 명확히
  하면 좋겠어."*
- 원 설계: `docs/superpowers/specs/2026-08-28-admin-console-design.md`
  (커밋 `1e6a1e5`)

---

## 0. 결론 — 문제는 "확대" 가 아니다

사용자가 느낀 것은 **기능이 늘었다**는 것인데, 대조해 보니 실상은 다르다.

> **원래 목표 넷 중 온전히 이행된 것은 하나뿐이다. 그런데 설계에 없던 층 둘은
> 완성되어 있다.**

즉 이것은 "할 일을 다 하고 더 나갔다" 가 아니라 **"본체를 절반쯤 지어 둔 채
옆 건물을 올렸다"** 에 가깝다. 목표를 다시 세우는 일의 절반은 뺄 것을 정하는
것이고, 나머지 절반은 **안 지어진 본체를 되찾는 것**이다.

---

## 1. 원래 무엇이었나

목적 문장(설계 27줄):

> 이 콘솔은 그 구멍을 사람이 메우는 도구다. 자동 삭제 범위를 넓히는 대신
> **관리자가 확인하고 판단해 삭제하거나 만료를 연장하는 경로**를 제공한다.

인수인계 문서가 한 겹 더 좁힌다(`2026-08-29-admin-ui-handoff.md:16`):

> 두 경우 모두 **자동으로 돌리면 되돌릴 수 없는 삭제나 대량 변경이 일어난다.**
> 그래서 코드는 "판정하고 목록을 돌려주는 것" 까지만 하고 멈춘다.

**목표 넷**(29–34줄)과 **비목표 다섯**(36–42줄)이 명시돼 있다. 비목표 첫 줄이
성격을 정한다 — *"Mobius 의 자동 만료 삭제 범위 확대(위험하고, 이 콘솔이 그
역할을 대신한다)."*

### 이 문서가 작업 브랜치에 없었다

`2026-08-28-admin-console-design.md` 는 **이 워크트리에 없다.** 원 저장소와
이력(`1e6a1e5`)에만 있다. 그 결과 감시 문서(`2026-08-30-admin-console-backlog.md`)
가 **목표/비목표 목록을 한 번도 대조하지 않았다.** 범위가 흐려진 구조적 조건
중 하나다.

## 2. 원래 목표의 현재 이행 상태

**여기가 이 문서의 핵심이다.** 전부 코드로 확인했다.

| 원래 목표 | 상태 | 근거 |
|---|---|---|
| ① 리소스 트리와 생성·수정·만료 시각, **최근 사용 여부** 확인 | **화면이 없다** | `views/` 에 리소스 조회·검색 화면 없음. `hit_ri` 도 없음 — **미착수가 아니라 다른 브랜치에 있었다.** §9 |
| ② 만료·**임박** 리소스를 걸러 삭제하거나 연장 | **절반** | ExpiredView 동작. 그러나 "임박" 은 없다 — `/api/expired` 는 이미 만료된 것만 |
| ③ ACP 확인·편집·**리소스에 연결/해제** | **절반** | 화면 4개 동작. `acpi` 연결/해제 없음. ACP 생성 없음(비목표의 유일한 예외였다) |
| ④ 별도 프로세스·별도 포트 | **완료** | `admin/server.js` 독립 기동 |

대조군 — **설계에 없던 층 둘은 닫혀 있다.**

| 설계에 없던 것 | 상태 |
|---|---|
| conf.json 편집 | ConfView + `conf_store.js` 228행. 원자적 쓰기·관문 두 겹·비밀 마스킹까지 완결 |
| 기동·정지·재기동 | ServerControl + `process_ctl.js` 242행. pm2 분기·pid 소유 확인·유예 폴링까지 완결 |

### 명시적 비목표를 위반한 것 하나

설계 341줄:

> 고아 탐지 · `LEFT JOIN lookup p ON l.pi=p.ri WHERE p.ri IS NULL` ·
> **배치 전용. 화면에서 라이브 실행 금지**

`OrphanView` 는 화면에서 "더 찾기"·"다시 세기" 로 라이브 스캔한다. 금지된 것을
하고 있다. (배포 `lookup` 은 5,740만 행이다.)

### 설계가 필수라고 적은 안전장치가 없다

설계의 일괄 작업 6단계 중 구현은 셋이다. 없는 것:

- **삭제 전 JSON 아카이브** (설계가 필수로 표시)
- **감사 로그** — `admin/audit.js` 없음
- **카나리 10건**, 삭제 사후 검증, 제3의 결론 '보존'
- **`admin.db` 영속 계층 전체.** 세션도(`server.js:117`) 작업 상태도
  (`jobs.js:8`) 메모리다. 콘솔을 재시작하면 도는 작업과 흔적이 사라진다

**되돌릴 수 없음에 대비하려던 장치가 없는 상태에서, 되돌릴 수 없음의 폭이 더
큰 층이 먼저 들어왔다.**

## 3. 어떻게 커졌나 — 출처별

`admin/` 과 스펙을 건드린 커밋 38건의 분포다.

| 출처 | 건수 | 그중 기능 범위를 넓힌 것 |
|---|---|---|
| 원래 목적 | 7 | 7 |
| 다른 세션 경유 | 15 | 2 (고아 화면, 구독 화면 설계) |
| 사용자 추가 요청 | 8 | **5** (conf 쓰기 계층, 설정 화면 3, 프로세스 제어) |
| 스스로 판단 | 8 | 0 |

### 확대는 사용자 지시로 들어왔다 — 다만 연쇄였다

    58bacce   "conf.json 설정값을 설정할 수 있게, 필요한 것만 노출해서"
    3d36767   "body limit 설정을 관리 UI 에서"
    32d6558   "파라미터들을 카테고리로 분류"
    1f20241   기동·정지·재기동

마지막 커밋이 스스로 적은 동기: *"설정 화면의 가장 큰 약점이 '저장해도 아무
일이 안 일어난다' 였는데, 재기동이 붙어 저장→재기동 한 흐름으로 닫힌다."*

**프로세스 제어는 사용자가 지시했지만, 그 지시를 부른 결함은 직전 확대가 만든
것이다.** 설정 편집은 원리적으로 "적용됐는지" 를 모른다(`runtimeKnown` 항상
false — `cluster.fork` 가 엔트리를 재실행해 워커마다 값이 다를 수 있다). 그
공백이 재기동 버튼을 요구했다.

### 그 다음 고리는 내가 만들었다

기동·정지와 함께 **`guard_busy`(도는 작업이 있으면 정지 409)** 를 붙였다. 이건
사용자 지시가 아니라 내 판단이다. 그리고 그것이 두 층을 서로 잠갔다 —
`cse.js` 가 끊긴 응답에 콜백을 부르지 않으면 작업이 갇히고, `guard_busy` 가
서버 제어를 **영구히** 막았다(`ed776f6`, `d0ff60d` 로 45초 유예를 넣어 해소).

> 정정 — 이건 운영 사고가 아니라 **내가 직접 시험하다 찾은 것**이다. 배포에서
> 일어난 적은 없다.

### 요청 없이 내가 넣은 것

범위를 넓힌 것은 없지만, 지시·요청 근거가 커밋에 없는 것이 있다.

- `8faac46` 오션 테마 전면 재도색과 가독성 조정
- `c031de6` ACP 정책 안내문(`AcpPolicyNote`)
- `eaf440b` 에이전트 73개로 전 브랜치를 훑은 추적 문서

나머지(응답 본문 상한, 취소 유예, 상수 드리프트 발견 등)는 견고성·자기검증이고
화면을 늘리지 않았다.

### 승인 단계가 없는 유입 경로가 하나 있다

코어 세션이 자동 실행을 뺄 때마다 커밋에 **"관리자 UI 로 넘긴다"** 고 적고,
그 목적지가 여기다. 고아 화면이 그렇게 들어왔다 — *"lite 가 고아 정리의 자동
실행을 빼고 '관리자 UI 로 넘긴다' 고 했는데 그 UI 가 없었다."* 대형 컨테이너
카운터도, 구독 감사도 같은 경로로 대기 중이다.

설계 목표 넷에 고아 정리는 없다. 문서의 **정신**에는 맞지만 **아무도 이 항목을
승인한 적이 없다.**

### 사용자 결정이 범위를 줄인 것은 하나다

- `53b7e77` 알림 판정 DB 저장 철회 — **축소**
- `2affdbf` 만료 SUB 노출은 의도된 설계 — 빼려던 것을 안 뺀 것이므로 **유지**

## 4. 성격이 다른 것들이 한 덩어리가 된 지점

대상이 **데이터 / 규칙 / 프로세스** 로 갈리는데 셸·인증·세션이 하나다.

### (1) 자물쇠가 하나다

세 층 전부 conf.json 의 **공유 비밀번호 하나**로 열린다. 세션에는 `{created}`
뿐이라 감사 로그에 '누가' 를 적을 수 없다. **만료 리소스 한 건 삭제와 서비스
전체 정지가 같은 자물쇠다.**

콘솔은 이미 같은 논리를 알고 있다. MySQL 쓰기를 검토할 때 *"전용 DB 계정은
경계가 아니다 — 콘솔이 그 자격증명을 들고 있고 인증은 비밀번호 하나뿐"* 이라고
결론냈다(§2.8). **같은 논리가 프로세스 제어에도 그대로 적용되는데, 거기서는
답이 달랐다.**

### (2) 확인 절차가 위험과 반대로 붙어 있다

| 동작 | 관문 |
|---|---|
| 리소스 삭제 | 프리플라이트 + 확인 대화상자(대상 표시) + 진행률·실패 사유 + 취소 — **네 겹** |
| 서버 정지·재기동 | 인라인 확인 한 번 + "도는 작업 없을 것" — **한 겹** |

가장 파괴력이 큰 동작이 가장 가벼운 관문을 지난다.

### (3) 되돌릴 수 있음의 단위

| | 단위 | 되돌리기 |
|---|---|---|
| 리소스 삭제 | 행 N건 | **불가** (아카이브로 대비하려 했으나 없음) |
| et 연장 / ACP 편집 | 행·ACP 1건 | 가능 |
| conf 저장 | 파일 | 가능. 단 다음 재기동에 워커 전부 적용 |
| **서버 정지** | **서비스 전체** | 재기동. **정지된 채 방치될 수 있는 유일한 동작** |

### (4) 확신할 수 있는 것은 줄어드는데 할 수 있는 일은 커진다

- **리소스 층** — 캐시 제거 이후 콘솔이 DB 에서 읽은 것 = 서버가 응답하는 것.
  화면이 참말을 할 수 있다.
- **설정 층** — "지금 적용 중인 값" 을 **원리적으로 모른다**.
- **프로세스 층** — 포트가 열렸는지, 우리가 띄운 pid 인지까지만.

이 역전이 문제의 핵심이다.

### (5) 코어 계약이 있는 층과 없는 층

리소스·ACP·설정은 코어 함수/스키마 위에 선다. 그래서 코어가 고치면 콘솔은 한
줄도 안 고치고 좋아진다 — `maxBodyBytes` 가 코어에 등록되자 화면에 저절로
나타났다. **프로세스 층에는 대응하는 코어 계약이 없다.** pm2 유무·pid 파일·포트
폴링은 콘솔이 혼자 정한 규약이고, 유지보수를 콘솔이 전부 떠안는다.

## 5. 목표 재정의안

> **관리 콘솔은 Mobius 가 자동으로 하지 않기로 한 판단을 사람이 내리는
> 자리다. 데이터(리소스·권한)에 대한 판단이 본체이고, 서버의 동작 규칙(설정)은
> 그 판단을 실행하는 데 필요한 만큼만 다루며, 서버와 DB 의 생사는 다루지
> 않는다.**

경계는 **규칙과 생사 사이**에 긋는다.

### 0층 — 말하는 방식 (전 층 공통)

읽기는 DB 직접 / 쓰기는 CSE 경유. 상한에 걸리면 `capped` 를 노출. 근거가 없으면
단언하지 않고 빈 칸. **코어 정책을 화면이 상수로 베끼지 않는다.**
`acpi like '%…%'` 와 전역 `COUNT(*)` 는 금지(5,740만 행).

**지금 위반 4건 이상** — 이게 재작업 첫 순번이다.

1. `AUTO_DELETED_RISKY` 가 ACP 에 없는 시한을 붙인다
2. `ET_EXTENDABLE` 이 코어가 연장해 주는 타입을 막는다 (서버에도 사본이 있어
   UI 우회해도 같다)
3. `AcpProblemsView` 가 `more/nextRi` 를 무시해 ACP 200개 넘으면 조용히 잘린다
4. `acpDiscoveryFilter` 미노출 — `'off'` 면 시뮬레이터가 **보호를 과장**한다

### 1층 — 판단 대기열 (본체)

코어가 "판정하고 목록만 돌려주고 멈춘" 것들. **먼저 되찾을 것은 목표 ①②다** —
리소스 조회 화면, `hit_ri` 사용 이력, **만료 임박**.

그 다음이 안전장치 복구(아카이브·감사·`admin.db`). **안전장치 없이 대기열을
늘리지 않는다.**

대기 중: 대형 컨테이너 카운터(코어 함수 셋 없음), 구독 감사(범위 미확정),
AE·CSE 삭제 시 '깨지는 구독' 미리보기(코어 함수는 왔음, 배포 986건).

### 2층 — 권한 (ACP)

**미완이 둘이다** — `acpi` 연결/해제, ACP 생성. 목표 ③의 절반이 아직 없다.

함께 지켜야 할 것: 잠그는 단위는 **AE 하나**(컨테이너·CIN 에는 못 붙이게 막는다),
`acpi` 최대 7개, 평가 순서 `ri` 오름차순, **생성자는 ACP 를 우회하므로 "완전히
잠갔다" 표시는 언제나 거짓**, 저장 전 simulate 필수(콘솔 origin 이
`usesuperuser` 라 자기가 만든 잠금을 자기 화면으로 못 느낀다).

### 3층 — 진단 (읽기 전용)

ACP 문제, **MySQL 세 값의 어긋남**(my.cnf / persist / 도는 값), 사용 이력,
카운터 불일치, ACP 변경 이력. 쓰기가 없으면 위험이 0 에 가깝다.

### 4층 — 설정 파일 (경계)

conf.json 노출 키 편집. 설계 근거는 없으나 사용자 직접 지시이고 이유가 실측으로
뒷받침된다(body limit 가 8년간 사실상 꺼져 있었다).

남은 위험: 적용 여부를 모른다는 것, 그리고 **저장 버튼만 `write.enabled` 에
묶여 있고 `POST /api/conf` 는 그 조건을 요구하지 않는다** — UI 를 우회하면
CSE 설정 없이 파일을 쓴다. 잠금이 아니라 표시일 뿐이다.

### 5층 — DB 백업 (사용자 지시로 경계 안. §8)

DB 를 **읽기만** 하고, 어댑터 계약을 갖고, 실패해도 원본이 변하지 않는 것.
복구 실행과 산출물 내려받기는 이 층에 들어오지 않는다.

### 경계 밖 — 프로세스·인프라의 생사

기동·정지·재기동, MySQL `SET GLOBAL`, my.cnf, **복구·마이그레이션 실행**.

밖인 이유: 설계 근거가 없고, 코어 계약이 없고, 인증이 다른 층과 같고, 관측이
포트·pid 까지뿐이며, 이미 다른 층과 상호 잠금을 일으켰다.

## 7. 사용자가 결정해야 할 것

**① 서버 기동·정지·재기동을 남기는가.**
직접 지시하신 기능이라 내가 뺄 수 없다. (가) 그대로 두되 이 층만 별도 인증
(나) **재기동만 남기고 정지를 뺀다** — 목적이 "저장 후 적용" 이었으므로 재기동
이면 충분하고, 정지는 방치될 수 있는 유일한 동작 (다) 통째로 빼고 "재기동이
필요합니다" 안내까지만. **권고는 (나).**

**② 관리자 1명 전제를 유지하는가.**
설계 비목표 3이다. 이 전제 때문에 감사 로그에 '누가' 를 못 적고, MySQL 쓰기·
프로세스 제어·대량 삭제가 전부 여기 걸린다. 유지하면 셋은 영구히 못 연다.
푸는 순간 콘솔은 다른 제품이 된다.

**③ '쓰기는 전부 CSE 경유' 에 첫 예외를 여는가.**
대형 컨테이너 카운터 보정이 그 예외다. `cni/cbs` 는 oneM2M 읽기 전용이라 PUT
으로 우회하면 `st` 가 올라 없던 구독 알림이 나간다. 안 열면 유예된 7개
(cni 109만~593만) 화면은 만들 수 없다.

**④ 보존 정책(mni/mbs)을 콘솔이 다루는가.**
기본값이 사실상 꺼진 상태라, 낮추는 순간 다음 CIN 삽입에서 `delete_oldest` 가
수백만 건을 즉시 지운다. 되돌릴 수 없음의 규모가 다른 항목과 자릿수가 다르다.

**⑤ MySQL 읽기 화면을 1차로 만드는가.**
검토 결론은 "읽기는 지금 가능, 쓰기는 인증 선행" 이었다. **쓰기 범위는 읽기
화면을 실제로 보신 뒤에 정하는 것이 낫다** — 노출 후보표는 §2.8 에 있다.

**⑥ 구독 화면을 콘솔 범위로 확정하는가.**
설계에 없고 backlog 로 들어온 항목이다. 삭제 후보에는 **`broken` 만** 담고
`suspect`(3,452 중 1,028건 = 29.8%)와 섞지 않는다는 원칙은 이미 정해져 있다.
범위에 넣을지 자체가 결정 사항이다.

**⑦ 거부·attach 로그 화면을 기각하는가.**
내가 착수 금지로 넣으려다 뺐다 — **대가가 있다.** 이 화면이 없으면
`acpiAttachPolicy: 'creator'` 를 켤 판단 근거가 없어, **아무나 남의 리소스를
잠글 수 있는 상태**가 그대로 남는다(실측 200, 그 뒤 생성자 조회 403).

**⑧ 4층을 동결하는가.**
"코어의 '도는 값' 계약이 오기 전까지 설정 화면을 더 넓히지 않는다" 는 제안인데,
사용자가 직접 지시하신 유일한 영역의 확장 정지라 결정으로 올린다.

**⑨ `usesuperuser` 값 교체를 어느 배포 회차에 묶는가.**
그 문자열만 알면 모든 ACP 를 우회하는데 콘솔의 기본 origin 이 그 값이다.
콘솔 배포와 같은 회차여야 한다.

## 8. DB 주기 백업 (사용자 지시, 2026-09-01)

> *"관리UI 상에서 모비우스가 사용하는 DB에 대해 주기적인 백업을 할 수 있는
> 방안을 조사해서 적용하고 싶어. 현재 db는 mysql, sqlite 대상이고 추후 db가
> 추가되면 추가된 db에 대해서도 적용될 수 있게 하는 것이야."*

§5 에서 백업을 경계 밖에 뒀다가 지시로 뒤집는다. **왜 다른지 근거를 남긴다.**

### 8.1 백업이 왜 경계 안인가

정지·`SET GLOBAL` 과 셋이 다르다.

- **되돌릴 수 없음의 방향이 반대다.** 저것들은 상태를 바꾸고 되돌릴 수 없다.
  백업은 DB 를 **읽기만** 한다. 실패해도 원본이 안 변한다. 이 콘솔의 가장 큰
  위험(잘못 눌러서 되돌릴 수 없음)이 이 기능에는 없다.
- **코어 계약이 있어야 할 자리에 실제로 있다.** "이 백엔드에서 일관된 스냅샷을
  어떻게 뜨는가" 는 백엔드가 아는 것이고, 담을 그릇(`mobius/db` 어댑터 +
  `capabilities`)이 이미 서 있다. 프로세스 제어에 없던 것이 여기엔 있다.
- **백업은 §2 가 지적한 미완 안전장치 그 자체다.** 아카이브가 리소스 단위
  되돌리기라면 백업은 DB 단위 되돌리기다. 위험한 층이 아니라 **늦게 온 안전장치**다.

**뒤집히지 않는 것 하나 — 인증.** 콘솔 인증은 공유 비밀번호 하나다. 그래서
**산출물 내려받기 엔드포인트를 만들지 않는다.** 인증을 고치지 못하므로 인증이
지킬 대상을 늘리지 않는다.

**예외의 범위를 못 박는다:** DB 를 읽기만 하고, 어댑터 계약을 갖고, 실패해도
원본이 변하지 않는 것. **복구 실행은 콘솔 밖**이다 — Mobius 를 멈추고 파일을
바꾸는 일이라 정확히 이 예외의 바깥이다.

### 8.2 착수 전에 고쳐야 할 결함 — 이게 1순위다

**지금 상태로 백업을 붙이면 엉뚱한 DB 를 백업하고 화면은 초록이 된다.**
실측으로 확인했다.

    .../worktrees/admin-console-part1/mobius.db             180,224 B
    C:/Users/ryeubi/Documents/Workspace/Mobius/mobius.db    274,432 B

**`mobius.db` 가 서로 다른 크기로 두 개 있다.** 원인 셋이 겹쳤다.

1. `mobius/db/sqlite.js:22` — `DB_PATH = process.env.MOBIUS_SQLITE_PATH || './mobius.db'`.
   **cwd 상대**이고 **export 되지 않는다.**
2. `sqlite.js:88` — `new sqlite3.Database(DB_PATH, cb)`. 모드 플래그가 없으면
   기본이 `OPEN_READWRITE | OPEN_CREATE` 다. **없으면 조용히 만든다.**
3. `admin/server.js:1014` — 콘솔이 기동 시 무조건 `db.connect(...)` 를 부르고,
   그것이 스키마 파일을 읽어 `db.exec(schema)` 한다.

콘솔은 Mobius 와 **다른 프로세스**다. 다른 디렉터리에서 띄우면 새 DB 를 만들고
스키마를 깔고 `[db/sqlite] connected / schema initialized` 를 찍는다 — 정상
기동과 구분되지 않는다. 이 세션의 콘솔 로그가 정확히 그 모습이었다.

백업이 붙으면 이 결함이 **데이터 손실**이 된다. 둘 다 비어 있지 않으므로 내용
검사(`lookup` 행수 ≠ 0, 테이블 수)를 **둘 다 통과한다.** 엉뚱한 것을 백업하고,
검증이 초록이고, 회전이 **진짜 DB 의 백업을 지운다.**

**export 하나를 추가하는 것으로는 안 닫힌다.** 콘솔 프로세스의 어댑터는 콘솔의
cwd 를 충실히 보고할 뿐이다. 필요한 것은 **"백업 대상이 Mobius 가 실제로 연
파일과 같은가"** 를 확인하는 단계다.

착수 전 선행 작업:

- SQLite 경로를 **절대 경로로 확정**하고 어댑터가 알린다.
- 콘솔은 **`OPEN_READONLY`** 로 연다. 없으면 만들지 않고 실패한다.
- 콘솔이 기동 시 스키마 DDL 을 날리지 않게 한다. **콘솔은 운영 DB 에 DDL 을 쓸
  이유가 없다** — 백업과 무관하게 이미 결함이다.
- 백업 대상이 Mobius 가 연 파일과 같은지 확인(pid 파일에 경로 기록 등).

### 8.3 확장 계약 — "추후 DB 추가" 의 답

**콘솔에 `switch` 를 두지 않는다.** `mobius/db` 어댑터 계약에 넣는다.

`test/db-adapter-contract.test.js` 가 이미 셋을 강제한다: `capabilities` 값은
**boolean 만**, 모든 어댑터의 **export 이름 집합이 같아야** 하고, 파사드가 부르는
함수는 `REQUIRED_FUNCTIONS` 에 있어야 한다. **목록을 늘리면 두 어댑터가 빨개지고
그 빨강이 곧 할 일 목록이다.** 새 장치를 만들 필요가 없다.

    exports.capabilities = { ..., backup: true };   // boolean 하나

    exports.backupPlan      = function ()                     // 정적 서술, 연결 불필요
    exports.backupPreflight = function (opts, cb)             // 시작해도 되는가
    exports.backupBaseline  = function (cb)                   // 검증 기준값
    exports.backupRun       = function (opts, cb)             // 실행. -> { cancel() }
    exports.backupVerify    = function (path, baseline, cb)   // 검증

`backupPlan()` 이 서술할 것과 각각이 막는 사고:

| 필드 | 막는 사고 |
|---|---|
| `source` | §8.2 의 엉뚱한 DB. **어댑터만이 진실을 안다** |
| `blocksWrites` | SQLite 가 WAL 이 아니면 백업이 Mobius 쓰기를 막는다. `'always'` 면 콘솔이 실행을 거부한다 |
| `retentionUnit` | 증분처럼 사슬이 있으면 중간을 지울 때 뒤가 전부 죽는다. `'chain'` 이면 **자동 회전 금지** |
| `maxDurationMs` | 콜백이 영영 안 오면 "진행 중" 이 영원히 남는다 (`jobs.js` 에서 겪은 부류) |
| `externalBins`, `runsInProcess` | 외부 실행이면 `execFile`·셸 없음. 동기 복사면 이벤트 루프가 멈춘다 |

**접속 정보를 콘솔이 다시 조립하지 않는다.** 어댑터는 이미
`connect({host, port, user, password})` 로 그 값을 받는다. 백업은 **어댑터가
기억하는 값**을 쓴다. 새 conf 키가 생기지 않는다. 비밀번호는 `argv` 에 넣지
않는다 — `ps` 로 보인다.

**새 DB 를 넣는 사람이 하는 일:** `mobius/db/<이름>.js` 에 위 다섯과
`capabilities.backup` 을 채운다. 계약 시험이 빠진 것을 이름으로 알려 준다.
콘솔·화면은 한 줄도 안 고친다. 못 하는 백엔드는 `backup: false` 와
`{supported:false, reason}` 만 적고 화면이 그 이유를 그대로 보여 준다.

### 8.4 누가 실행하는가 — 권고는 OS 스케줄러

**콘솔에 스케줄러가 하나도 없다** (`admin/*.js` 에 `setInterval` 0건). 넣는다는
것은 **콘솔이 아무도 안 볼 때 일하는 물건이 된다**는 뜻이다.

| | 얻는 것 | 대가 |
|---|---|---|
| (가) 콘솔 내부 스케줄러 | 한 곳에서 설정·조회·실행 | **콘솔이 꺼져 있으면 백업이 없다.** 상시 기동이 새 전제가 된다. 예약 영속을 위해 `admin.db` 가 필요한데 아직 없다 |
| **(나) OS 스케줄러 실행 / 콘솔은 관리·조회·수동 실행** | 콘솔이 꺼져 있어도, 재배포 중에도 돈다. 몇 시간짜리도 문제없다. **경계를 사실상 안 건드린다** | 등록이 사람 손. 화면에서 주기를 못 바꾼다 |
| (다) 콘솔이 crontab 편집 | — | **배제.** 크론 항목은 그 자체가 명령 문자열이다. `process_ctl` 규칙 2 를 정면으로 어긴다 |
| (라) Mobius 본체가 실행 | — | 배제. 25 워커 중 누가 도는지를 새로 정해야 하고, 콘솔 작업이 아니라 코어 작업이 된다 |

**권고 (나).** 백업의 신뢰도가 "콘솔이 떠 있는가" 에 걸리면 안 된다.

(나)의 약점은 "예약이 죽었다" 를 콘솔이 직접 못 안다는 것이다. 답은 **마지막
성공으로부터의 경과**다. 스케줄러를 보는 게 아니라 **결과를 본다** — 등록됐지만
매번 실패하는 크론도 잡힌다.

### 8.5 작업 엔진과 분리한다

**백업을 `admin/jobs.js` 에 얹지 않는다.** `jobs.js:127` 의
`if (active) return null` 때문에 백업이 도는 동안 삭제·연장이 전부 막히고,
`guard_busy` 가 재기동까지 막는다. 반대로 삭제 중이면 백업 회차가 조용히
건너뛰어진다.

단일 슬롯은 삭제 작업을 위한 **옳은 설계**다. 백업은 그 옆에 별도 슬롯으로 선다.

### 8.6 디스크 — 데이터를 지키려다 잃는 자리

**산출물을 DB 와 같은 볼륨에 쓰면, 차는 순간 DB 가 파일을 확장하지 못해 쓰기가
실패하고 서비스가 멈춘다.**

- 산출물 볼륨이 DB 볼륨과 같으면 **경고가 아니라 거부**.
- 시작 전 여유 공간 프리플라이트(`추정 x 1.5`). 부족하면 **시작하지 않는다**.
- **회전은 "내가 만든 것만" 지운다** — 이름 규칙과 기록에 **둘 다** 있는 것만.
  (`process_ctl` 의 "우리가 띄운 것만 내린다" 이식)
- **보존은 개수 기준.** 날짜 기준은 백업이 며칠 멈추면 남은 것까지 만료시킨다.
- **회전은 새 백업이 검증까지 통과한 뒤에.** 오늘 실패했는데 어제 것을 지우지
  않는다.
- 고정 파일명·덮어쓰기 금지. 산출물은 `.gitignore`.

### 8.7 검증 — 확인하지 않은 백업은 백업이 아니다

**구조 검사만으로는 부족하다.** 조사에서 손상된 SQLite 사본 둘이
`integrity_check` 를 **"ok" 로 통과했다.** 구조를 보지 데이터가 있는지는 안 본다.

- **층 1 (자동, 최종 이름 붙이기 전)** — 어댑터의 `backupVerify` 가 **내용 검사
  포함**으로 판정. 기준값은 백업 직전 원본에서 읽는다. 원본은 계속 쓰이므로
  **절대 일치가 아니라** "산출물 <= 원본, 차이가 소요 시간의 통상 증가분 안" 을
  본다. **통과한 것만 최종 이름을 받는다. 실패한 산출물은 지운다** — 깨진 백업이
  목록에 남는 것이 백업이 없는 것보다 위험하다.
- 파이프를 쓰지 않는다. `mysqldump | gzip > f.gz` 는 gzip 의 종료 코드를 돌려주어
  **mysqldump 실패가 조용히 묻힌다.**
- **층 2 (자동)** — 신선도, 크기 편차. 갑자기 절반이 된 산출물은 대개 "성공한
  것처럼 보이는 부분 백업" 이다.
- **층 3 (사람이, 콘솔 밖)** — 복구 리허설. 콘솔은 **"마지막 성공 리허설 날짜"를
  기록하고 오래되면 경고할 뿐**, 실행하지 않는다.
- **보관본 재검증** — 최신 것만 보지 않는다. 비트 손상은 조용히 진행된다.

### 8.8 화면

콘솔이 백엔드를 모른 채 그린다 — 전부 `backupPlan()` 과 기록에서 온다.

상단 판정 한 줄(마지막 성공 · 여유 공간 · 프리플라이트), 백엔드 카드(대상 경로,
쓰기를 막는가, 프리플라이트 항목별 결과와 **사람이 할 일**), 이력 표(시각·결과·
소요·크기 +-%·검증 요약·**실패 사유를 그 줄에서 읽게**), 디스크 카드(**DB 볼륨과
같으면 빨강**), 신선도 카드.

**없어야 하는 것:** 산출물 내려받기 버튼, 경로 편집(임의 위치 쓰기가 된다),
접속 정보. 실행 이력의 "누가" 는 **적을 수 없다** — `수동` / `스케줄러` 만 남긴다.

### 8.9 단계

    0  결정 기록 (코드 0줄) — §5 경계 수정. 이 문서가 그것이다
    1  §8.2 선행 결함 수정 — 절대 경로 · OPEN_READONLY · 기동 DDL 제거
    2  어댑터 계약 (콘솔 코드 0줄) — 계약 시험에 이름 추가, 빨강이 할 일 목록
    3  CLI 진입점 하나 (tools/backup.js) — **여기서 요구사항이 실제로 충족된다.**
       OS 스케줄러에 한 줄 걸면 주기 백업이 돈다. 배포 실측도 여기서 낸다
    4  콘솔 조회 화면 — 읽기 전용, 실행 없음. 경계를 안 건드린다
    5  콘솔의 수동 1회 실행 — 사람이 누른다. 별도 슬롯
    6  (조건부) 콘솔 내부 스케줄러 — 2~5 로 부족하다는 것이 드러난 뒤에만

**로컬로 잰 시간·잠금·디스크는 배포에서 성립하지 않는다.** 로컬 `mobius.db` 는
176KB 이고 배포는 `lookup` 만 5,740만 행이다. 3단계에서 작은 테이블로 바이트/초를
재고 외삽한다.

### 8.10 이 계획이 안 하는 것

복구 실행, 산출물 내려받기, 원격 전송·암호화(자격증명이 하나 더 생기면 §8.1 의
논거가 무너진다), PITR, SQLite 의 WAL 자동 전환(DB 속성을 영구히 바꾸는 일이고
다른 커넥션이 락을 쥐면 **에러 없이 조용히 이전 값을 돌려준다**), OS 스케줄러
편집, `jobs.js` 수정, `conf.json` 에 실행할 명령·경로 두기.

DB 만 백업한다 — `conf.json`·키 파일은 이 계획 밖이고, 함께 잃으면 복구가
온전하지 않다는 점은 별도 항목으로 남긴다.

### 8.11 사용자가 결정해야 할 것 (§7 에 이어서)

**⑩ 경계 예외를 승인하는가.** §8.1 의 근거로 백업을 경계 안에 두되, 읽기 전용·
복구 제외·내려받기 없음으로 한정한다.

**⑪ 실행 주체.** 권고는 (나) OS 스케줄러. (가) 를 택하면 **"콘솔이 상시
기동되어야 한다"** 가 새 전제로 추가된다.

**⑫ RPO — 얼마까지 잃어도 되는가.** 스냅샷 주기가 곧 최대 유실량이다. 이 값이
정해져야 주기가 정해진다.

**⑬ RTO — 복구에 얼마까지 걸려도 되는가.** 논리 덤프(mysqldump)만 갖고 있으면
5,740만 행 복구가 시간 단위로 걸린다. 짧아야 한다면 물리 백업(XtraBackup)이
후속 작업이 되고, 그건 이 계획의 범위 밖이다.

## 9. 브랜치를 하나로 합쳤다 (2026-09-02, 사용자 지시)

`feat/admin-console-part0` 와 `feat/admin-console-part1` 두 갈래였다. 합치면서
알게 된 것을 남긴다 — **§2 의 진단 하나를 정정한다.**

### 두 갈래였던 실상

분기점은 `a602faa`(2026-08-27). 그 뒤로 part0 에만 25개, part1 에만 287개가
쌓였고 **서로를 한 번도 병합하지 않았다.**

- **part0** — 선행 작업(P0). ACP 판정 추출, 워커 간 캐시 무효화, `hit_ri`
  사용 이력, 인덱스, `superUser`/`adminOrigin` 을 conf 로 분리.
  **`origin/lite` 를 한 번도 병합하지 않았다.**
- **part1** — 콘솔 본체. `origin/lite` 를 여러 번 병합해 따라왔다.

### part0 의 25개는 거의 다 죽어 있었다

lite 와 대조한 결과다.

| part0 의 작업 | 지금 상태 |
|---|---|
| `mobius/acp_eval.js` + `security.js` 위임 | **대체됨.** lite 가 자체 모듈군을 갖는다 — `acp.js`, `acp_filter.js`, `acp_lint.js`, `acp_observe.js`, `acp_simulate.js` |
| `mobius/cache_man.js` + 시험 3벌 | **의도적으로 삭제됨.** 별칭 키 구멍을 재현한 뒤 코어가 걷어냈다 |
| `superUser`/`adminOrigin` conf 분리 | **코어가 독자적으로 채택.** `origin/lite:mobius.js:80` 이 이미 읽는다 |
| 인덱스 | **lite 에 있다** |
| `select_expired_resources` 등 raw SQL | **대체됨.** DB 레이어 추상화가 knex 로 다시 썼다 |
| **`hit_ri` 사용 이력 (`hit_man.js`)** | **살아 있다. 유일하게 안 죽은 것.** ↓ |

### 그래서 `-s ours` 로 합쳤다

세 번 시도해서 나온 결론이다.

**1차 — 그냥 병합.** 11개 파일 충돌(`app.js`·`security.js`·`sql_action.js`·
`resource.js`·스키마 둘 포함)이고, **삭제된 `cache_man.js` 와 대체된
`acp_eval.js` 가 되살아난다.** 병합 기준에서 보면 part0 가 추가한 것이고
part1 에는 없으니 git 은 "추가" 로 본다.

**2차 — 충돌 구역만 HEAD 로.** 여기서 함정에 걸렸다. `security.js` 의
**자동 병합된** 부분이 `require('./acp_eval')` 을 조용히 끌고 들어와, 파일을
지우자 ACP 시험 3벌이 통째로 죽었다(`Cannot find module './acp_eval'`).
충돌 표식이 없는 곳도 part0 의 코드가 들어온다는 것을 놓쳤다.

**3차 — `-s ours`.** 이력은 합치고 트리는 현재 것을 그대로 둔다. 위 표대로
살아 있는 것이 사실상 없으므로 이것이 맞다. 문서 둘은 따로 되살렸다.

### `hit_ri` 는 그대로 못 가져온다 — 포팅이 필요하다

2차 시도에서 실제로 돌려 봤다. `hit_ri` 코드가 **DB 레이어 추상화 이전의 파사드
API** 를 쓴다:

    facade.conflictRef(col)      지금 파사드에 없다
    upsert_hit_ri_batch          그 위에 서 있다

시험이 그대로 빨갛다. **병합으로 해결되는 문제가 아니라 다시 쓰는 일이다.**

**잃어버린 것은 없다.** `-s ours` 병합이 part0 의 25개 커밋을 이력에 그대로
담고 있으므로 언제든 꺼낼 수 있다:

    git show feat/admin-console-part0:mobius/hit_man.js
    git log feat/admin-console-part0 -- mobius/hit_man.js

관련 커밋: `36c2808`(테이블·SQL), `dd15b64`(파사드 이동), `eeeba05`(버퍼·flush),
`eff4102`(리뷰 대응), `b5ef7f3`(수집 배선), `65146f5`(콜레이션), `2b57a8c`(고아 정리).

### `hit_ri` 를 포팅할 때 다시 아플 것들 (2026-09-02)

part0 워크트리를 정리하면서(`mobius-87`) 무시된 경로에 있던 그 세션의 기록이
드러났다. **재생성이 안 되는 산문 둘**을 저장소로 옮겼다:

    docs/superpowers/reports/2026-08-28-part0-collation-fix.md
    docs/superpowers/reports/2026-08-28-part0-final-fix.md

거기서 뽑은, **포팅할 때 다시 겪게 될 것들**이다. DDL 을 새로 쓰거나 모듈을
다시 짜면 전부 잃는다.

**① `hit_ri.ri` 의 콜레이션은 `lookup.ri` 와 같아야 한다.**

    `ri` varchar(200) CHARACTER SET utf8 COLLATE utf8_bin NOT NULL

`delete_hit_ri_orphan` 이 `hit_ri.ri` 를 `lookup.ri` 에 조인한다. 콜레이션이
어긋나면 **인덱스를 못 타고 조인이 조용히 느려지거나 안 맞는다.** 배포에서 이미
같은 부류를 겪었다 — `lookup.pi` 가 `utf8mb3_general_ci`, `ri` 가 `utf8mb3_bin`
이라 부모↔자식 조인이 인덱스를 못 탔다.

**② 파사드 실패 규약을 writer 가 버리면 안 된다.**
파사드는 실패 시 `callback(true, err)` 다. 두 번째 인자를 버리면 로그가
`flush failed, will retry: true` 가 되어 **원인을 못 본다.** 실제로 그랬고,
고친 뒤에야 `ER_NO_SUCH_TABLE: Table 'mobiusdb.hit_ri' doesn't exist` 가 보였다.

**③ 되돌리기 버퍼에 상한이 필요하다.** `MAX_BUFFER_KEYS = 50000`. 넘으면 가장
오래된 `ct` 부터 버린다(키가 `ri|ct` 이고 `ct` 가 `YYYYMMDD` 라 문자열 정렬이
곧 시간 순). DB 가 오래 죽어 있으면 버퍼가 무한히 자라는 자리다.

**④ 실패 로그를 조르지 않으면 하루 7만 줄이 된다.** 8워커 × 10초 주기 × 영구
실패. 첫 실패 한 번, 이후 360회마다 한 번, 복구되면 한 줄.

**⑤ 스키마가 두 곳에 있다.** `mobius/mobiusdb.sql`(신규 설치)과
`docs/mysql-migration-2.7.md`(기존 설치). 한쪽만 고치면 신규와 기존이 갈린다.

> 나머지 기록(SDD 진행 장부, 리뷰 diff 20여 개)은 옮기지 않았다. diff 는
> 커밋에서 다시 만들 수 있고 장부는 진행 기록이다. 백업 위치는 `mobius-87`
> 세션의 스크래치패드이고 임시 경로라 사라질 수 있다.

### §2 의 정정

목표 ① 의 "최근 사용 여부" 를 **"선행 P0-2 미착수"** 라고 적었는데 틀렸다.
**만들어져 있었고, 다른 브랜치에 있어서 안 보였을 뿐이다.** 그리고 그 브랜치가
lite 를 안 따라가는 사이 파사드가 바뀌어 지금은 그대로 못 쓴다.

§1 에서 "설계 문서가 작업 브랜치에 없었다" 를 범위가 흐려진 구조적 조건으로
꼽았는데, **같은 원인이 코드에도 있었다.** 선행 작업이 본체 브랜치에 없으니
본체가 그것을 못 쓰고, 안 쓰이는 사이 낡았다.
