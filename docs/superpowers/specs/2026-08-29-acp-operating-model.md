# ACP 운영 방안

현황 조사는 [2026-08-29-acp-survey.md](2026-08-29-acp-survey.md) 를 볼 것.
여기서는 **어떻게 쓸 것인가** 만 정한다.

## 대원칙

> **평소에는 아무것도 하지 않는다. 잠글 곳만 명시적으로 잠근다.**

지금 운영 방식(ACP 없이 다 돌아감)을 **기본값으로 유지**한다. ACP 는 "필요한
곳에만 나중에 얹는 것" 이지, 전체에 깔고 시작하는 것이 아니다.
이 원칙을 지키면 ACP 를 안 쓰는 리소스는 지금과 **완전히 똑같이** 동작한다.

---

## 1. 잠그는 단위는 AE 하나다

**AE 에 ACP 를 한 번 붙이면 그 아래 트리 전체에 적용된다.** 실측으로 확인했다
(컨테이너 3단 + CIN + la + 탐색까지 전부):

| 대상 | ACP 붙이기 전 | AE 에만 붙인 뒤 (제3자) | 같은 시점 (소유자) |
|---|---|---|---|
| AE | 200 | **403** | 200 |
| c1 / c2 / c3 | 200 | **403** | 200 |
| c3 의 `la` | 200 | **403** | 200 |
| 탐색 `?fu=1` | 200 | **403** | 200 |
| c3 에 CIN 생성 | — | **403** | — |

그래서 **컨테이너나 CIN 에는 절대 붙이지 않는다.** 붙일 이유가 없고,
붙이는 순간 관리 대상이 수만 개로 늘어난다.

> 예외: 한 AE 안에서 일부만 다르게 해야 할 때만 그 컨테이너에 붙인다.
> 그런 경우가 생기면 그 자체를 재검토 신호로 본다 — 대개 AE 를 나누는 게 맞다.

## 2. ACP 는 CSEBase 아래 공용 몇 개를 재사용한다

리소스마다 ACP 를 만들지 않는다. 지금 유일한 ACP 가
`/Mobius/Camera1/acp-Camera1` 인데, 이 방식대로 가면 ACP 가 AE 수만큼 늘어난다.

대신 `/Mobius` 아래에 **정해진 몇 개**를 두고 `acpi` 로 참조만 한다.

```
/Mobius/acp-private      지정한 원본만 전권          acop 63
/Mobius/acp-readonly     지정한 원본만 읽기·탐색     acop 34
/Mobius/acp-ingest       올리기·읽기만 (수정/삭제 X)  acop 35
```

`acop` 비트: `1` CREATE · `2` RETRIEVE · `4` UPDATE · `8` DELETE · `16` NOTIFY · `32` DISCOVERY

| 목적 | acop | 계산 |
|---|---|---|
| 전권 | 63 | 1+2+4+8+16+32 |
| 읽기·탐색만 | 34 | 2+32 |
| 올리기·읽기·탐색 (장비용) | 35 | 1+2+32 |
| 알림만 | 16 | |

**ACP 개수를 한 자리로 유지하는 것이 목표다.** 그래야 관리 UI 에서 한눈에
보이고, [방안 A](#부하-대책과의-관계) 의 경로 집합도 작게 유지된다.

만드는 예 (`POST /Mobius`, `Content-Type: application/json;ty=1`):

```json
{"m2m:acp": {
  "rn": "acp-private",
  "pv":  {"acr": [{"acor": ["SDeviceA", "SGcsApp"], "acop": 63}]},
  "pvs": {"acr": [{"acor": ["Sponde", "SAdmin"],    "acop": 63}]}
}}
```

붙이는 예 (`PUT /Mobius/<AE>`, `ty=2`):

```json
{"m2m:ae": {"acpi": ["/Mobius/acp-private"]}}
```

## 3. 지켜야 하는 규칙 넷

이걸 어기면 사고가 난다. 전부 실측으로 확인된 함정이다.

### ① `pvs` 에는 반드시 관리자 원본을 넣는다

`pvs` 는 "이 ACP 자체를 누가 고칠 수 있는가" 다. `acp` 테이블에는 `cr`
컬럼이 **없어서**, `pvs` 를 잘못 주면 생성자도 못 고치고 **수퍼유저만**
복구할 수 있다. 항상 관리자 원본을 넣는다.

> 더 나쁜 건 `pvs` 를 **수정**할 때는 아무 검증도 없다는 점이다
> (생성 시에는 `400-23` 이 막지만 UPDATE 경로는 그 검사에 도달하지 않는다).

### ② `acpi` 를 설정하기 전에 그 ACP 가 실재하는지 확인한다

**지금 서버는 존재하지 않는 ACP 를 가리켜도 그대로 받는다.** 그러면 그
리소스는 생성자 말고 아무도 못 쓰게 잠긴다. 운영 데이터에 실제로 그런 게
하나 있다 — `/Mobius/sch8` 이 없는 `/Mobius/acp_sch1` 을 가리켜 잠겨 있다.

오타 한 번이 곧 장애다. **ACP 를 먼저 만들고, 응답의 `ri` 를 그대로 복사해서
붙인다.** (서버가 이걸 검증하도록 고치는 것이 우선 과제 중 하나다)

### ③ ACP 를 지우기 전에 참조를 먼저 푼다

ACP 를 지우면 그걸 가리키던 리소스는 위 ②와 같은 상태가 된다. 지우기 전에
참조하는 리소스를 찾아 `acpi` 를 비운다. 찾는 질의는 싸다 (배포 서버 119ms):

```sql
select ri, acpi from lookup
 where ty in (1,2,3,5,9,10,13,14,16,23,24,27,28,38,39,91,92,93,94,95,96,97,98)
   and acpi like '%<지울 ACP 의 ri>%';
```

`ty` 목록으로 좁히는 것이 핵심이다. CIN(`ty=4`)까지 포함하면 6,620만 행
풀스캔이 된다. CIN 에 ACP 를 다는 일은 없으므로 빼도 된다.

### ④ `actw`(시간창)는 UTC 기준이다

`acco` 의 `actw` 를 쓸 때 한국 시간으로 적으면 9시간 어긋난다. KST 09:00 을
원하면 `0 0 0 * * *` 이다. 형식은 `초 분 시 일 월 요일` 6자리 정확히 일치만
지원한다 (`1-5`, `1,3` 같은 범위·목록 표기는 안 된다).

## 4. 잠겼을 때 복구 절차

| 상황 | 복구 |
|---|---|
| `acpi` 를 잘못 걸어 리소스가 잠김 | **생성자**로 `PUT {"m2m:<ty>":{"acpi":[]}}` |
| 생성자를 모르거나 없어짐 | 수퍼유저(`X-M2M-Origin: Sponde`)로 같은 요청 |
| ACP 의 `pvs` 를 잘못 줘서 ACP 를 못 고침 | 수퍼유저만 가능 |

실측 확인: 생성자는 되살릴 수 있고 제3자는 못 한다. 관리 UI 에 **"잠금 해제"**
버튼을 두고 수퍼유저로 대행하게 하면 이 절차가 사람 손을 덜 탄다.

## 5. 켜기 전에 관찰한다 — "설정했더니 동작 안 함" 의 해법

지금 가장 큰 고통은 **켜 보기 전에는 뭐가 막힐지 모른다**는 것이다.
그래서 순서를 이렇게 한다.

```
1) 거부 로그를 먼저 켠다        누가·무엇을·어느 ACP 때문에 막혔는지 남긴다
2) 관찰 모드로 ACP 를 건다       판정은 하되 막지 않고 로그만 남긴다
3) 하루~이틀 로그를 본다         막힐 뻔한 것이 의도한 것뿐인지 확인
4) 관찰 모드를 끈다              그때부터 실제로 막는다
```

2번(관찰 모드)이 없으면 3번을 할 수 없고, 그러면 "일단 걸고 터지면 푼다" 가
되어 지금 상황으로 되돌아간다. **이 두 가지(거부 로그 + 관찰 모드)가
ACP 를 쓸 수 있게 만드는 최소 조건이다.**

## 6. 관리 UI 가 해야 할 것

| 화면 | 내용 | 지금 가능한가 |
|---|---|---|
| ACP 목록 | `ri` / `pv` / `pvs` / **참조하는 리소스 수** | 가능 (119ms 역조회) |
| ACP 상세 | 규칙을 사람이 읽는 형태로 (`acop 63` → "전권") | 가능 |
| 리소스의 실효 권한 | 상속을 풀어서 "이 리소스에 실제로 적용되는 ACP" | 계산 필요 |
| 시뮬레이터 | "이 원본이 이 리소스에 이 연산을 하면?" → 허용/거부 + 근거 | **서버 지원 필요** |
| 거부 로그 | 최근 거부 목록 (누가·무엇을·왜) | **서버 지원 필요** |
| 잠금 해제 | `acpi` 비우기 (수퍼유저 대행) | 가능 |

**시뮬레이터가 핵심이다.** 이게 있으면 "걸어 보고 터지는지 확인" 하지 않아도
된다. 서버는 `security.check` 를 그대로 쓰되 실제 실행 없이 판정만 돌려주는
진단용 엔드포인트를 하나 두면 된다.

## 7. 설정으로 빼야 할 것

지금 하드코딩돼 있어 운영으로 바꿀 수 없는 값들이다.

| 값 | 위치 | 지금 | 해야 할 일 |
|---|---|---|---|
| `useaccesscontrolpolicy` | `mobius.js:88` | `'disable'` 고정 | conf 로. **기본값은 지금 값 유지** |
| `usesuperuser` | `mobius.js:50` | conf 에 없어서 `'Sponde'` | conf 에 명시. 문자열만 알면 전부 통과한다 |
| 관찰 모드 | 없음 | — | conf 로 켜고 끈다 |

`useaccesscontrolpolicy='disable'` 의 의미는 "ACP 를 안 쓴다" 가 아니라
**"`acpi` 가 없는 리소스의 기본 정책"** 이다:

| | 생성자 | 그 밖의 누구든 |
|---|---|---|
| CREATE / RETRIEVE / DISCOVERY | 허용 | **허용** |
| UPDATE / DELETE | 허용 | 거부 |

`'enable'` 로 바꾸면 **생성자만** 전부 허용이 된다. 지금 이걸 켜면 대부분의
읽기가 막히므로, 바꾸려면 5번의 관찰 절차를 거쳐야 한다.

## 부하 대책과의 관계

이 운영 방식(AE 단위, 공용 ACP 소수)을 지키면 `acpi` 가 채워진 리소스가
**수십 개** 를 넘지 않는다. 그러면 [방안 A](2026-08-29-acp-survey.md) —
"`acpi` 가 채워진 `ri` 집합을 메모리에 들고, 조상 중에 없으면 DB 를 안 친다" —
가 거의 모든 요청에서 적중한다.

지금 ACP 상속 조회가 **350만 회 / 전체 질의의 6.8%** 인데, 이 방식과 방안 A 를
같이 쓰면 사실상 0 이 된다. 반대로 컨테이너마다 ACP 를 붙이는 방식으로 가면
집합이 커져 효과가 줄고, 결국 `acpl`(실효 ACP 를 행에 미리 풀어 두기)까지
가야 한다.

**즉 운영 규칙 하나(AE 단위로만 붙인다)가 성능 대책을 결정한다.**

## 요약 — 3단계로 끝난다

무언가를 잠그고 싶을 때:

```
1) /Mobius 아래 공용 ACP 중 맞는 것을 고른다 (없으면 하나 만든다, pvs 에 관리자 포함)
2) 그 AE 에 acpi 를 건다      PUT /Mobius/<AE>  {"m2m:ae":{"acpi":["<ACP 의 ri>"]}}
3) 관찰 로그를 하루 본 뒤 관찰 모드를 끈다
```

풀고 싶을 때:

```
PUT /Mobius/<AE>  {"m2m:ae":{"acpi":[]}}     (생성자 또는 수퍼유저)
```

평소에는 **아무것도 하지 않는다.**
