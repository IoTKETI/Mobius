# ACP 운영 방안

현황 조사는 [2026-08-29-acp-survey.md](2026-08-29-acp-survey.md) 를 볼 것.
여기서는 **어떻게 쓸 것인가** 만 정한다. 표에 있는 수치는 전부 실측이다.

---

## 대원칙

> **1. 생성·조회는 누구나**
> **2. 수정·삭제는 생성자만**
> **3. 잠글 곳만 명시적으로 잠근다**

평소에는 아무것도 하지 않는다. ACP 는 이 원칙의 **예외를 표시하는 수단**이지,
전체에 깔고 시작하는 것이 아니다.

## 지금 이미 그렇게 돈다

기본 정책이 대원칙과 정확히 일치한다. 실측 (`Cowner` 가 만든 리소스):

| 연산 | Cowner (생성자) | Cteam | Cother |
|---|---|---|---|
| 조회 RETRIEVE | 200 | 200 | 200 |
| 생성 CREATE | 201 | 201 | 201 |
| 수정 UPDATE | 200 | **403** | **403** |

`mobius/security.js` 의 `security_default_check_action` 이 이걸 한다.
`acpi` 가 비어 있는 모든 리소스가 이 규칙으로 돈다. **바꿀 것이 없다.**

> 탐색(DISCOVERY)도 "조회" 에 포함된다. `?fu=1` 은 누구나 된다.

---

## ⚠ 가장 중요한 것: ACP 를 걸면 기본 정책이 통째로 대체된다

ACP 는 기본 정책에 **덧붙는 것이 아니라 갈아치우는 것**이다.
그리고 **생성자 권한도 같이 사라진다.**

실측 — `Cowner` 가 만든 AE 에, `acor` 에 `Cteam` 만 적은 ACP 를 걸었다:

| 연산 | Cowner (생성자) | Cteam | Cother |
|---|---|---|---|
| 조회 | **403** ← 만든 사람인데 막힌다 | 200 | 403 |
| 생성 | **403** | 201 | 403 |
| 수정 | **403** | 200 | 403 |

**"설정했더니 동작을 안 한다" 의 가장 큰 원인이 이것이다.** ACP 를 걸면
만든 사람 자신도 못 들어간다.

### 그래서 규칙 하나가 절대적이다

> **ACP 를 걸면 `pv.acr` 에 적힌 원본만 통과한다. 생성자라고 자동으로 남지 않는다.**

## 장치 원본은 어떻게 하나 — 사람이 그 ID 를 모른다

장치가 자기 ID 로 리소스를 만든다. 사람이 ACP 를 설정할 때 그 ID 를 알 방법이
없고, 안다 해도 장치마다 적는 것은 현실적이지 않다. **그러므로 "장치 원본을
`acr` 에 적는다" 는 운영 규칙이 될 수 없다.**

실측으로 갈랐다 (장치 `Sdevice_unknown_id` 가 컨테이너와 CIN 을 만든 상태,
ACP 의 `acor` 에는 `Cteam` 만 있다):

| | Cteam | **장치** | Cother |
|---|---|---|---|
| **ACP 없음** — 기본 정책 | | | |
| CIN 올리기 / 조회 / la / 탐색 | 201 / 200 | 201 / 200 | 201 / 200 |
| **패턴 A** — `acor=[Cteam]` 만 | | | |
| CIN 올리기 | 201 | **403** | 403 |
| 조회 · la · 탐색 | 200 | **403** | 403 |
| **패턴 B** — `+ {"acor":["all"],"acop":1}` | | | |
| CIN 올리기 | 201 | **201** | 201 |
| 조회 · la · 탐색 | 200 | 403 | 403 |

### 결론 — 두 갈래로 나뉜다

**① 장치가 올리기만 하면 된다 → 지금 그대로 된다.**
패턴 B 를 쓴다. `{"acor":["all"],"acop":1}` 한 줄이면 **장치 ID 를 몰라도**
장치는 계속 데이터를 올리고, 조회·탐색만 팀으로 제한된다.
"남이 못 보게" 하려는 목적의 대부분이 여기에 해당한다.

**② 장치가 자기 데이터를 읽어야 한다 → 서버 지원이 필요하다.**
`la` 로 마지막 값을 확인하는 장치 등. 지금은 방법이 없다.
**`acor` 에 `$creator` 토큰을 지원하면 된다** — 서버가 이걸 그 리소스의 `cr`
로 해석한다. 사람은 장치 ID 를 몰라도 "만든 자는 계속 접근" 을 표현할 수 있다.

```json
"pv": {"acr": [
  {"acor": ["$creator"], "acop": 63},
  {"acor": ["<팀AE>", "<관리자>"], "acop": 63}
]}
```

구현은 작다. `acor_allows` 가 `cr` 을 받아 한 줄을 더 보면 된다
(`all` / `*` 토큰이 이미 같은 방식이다). 대안으로 "ACP 가 걸려 있어도 생성자는
항상 통과" 를 서버 기본 동작으로 만드는 방법도 있지만, 그러면 정책 화면에
드러나지 않아 관리 UI 로 감시하기 어렵다 — **명시 토큰을 권한다.**

## `cr`(생성자)은 언제 따로 검사되는가

생성자를 따로 보는 분기가 **셋** 있다. 다만 **정상 ACP 를 걸면 그 셋을 다 안
탄다** — 그게 위의 함정이다. 실측 (컨테이너 `c1`, 생성자 `Cowner`):

| 상황 | Cowner (생성자) | Cother | `cr` 을 보는가 |
|---|---|---|---|
| (a) `acpi` 가 비어 있다 — 기본 정책 | 200 | 200 | **본다** (`security.js:354`) |
| (b) `acpi` 가 없는 ACP 를 가리킨다 | **200** | 403 | **본다** (`security.js:294`) |
| (c) 정상 ACP 인데 `acr` 에 없다 | **403** | 403 | **안 본다** |

한 가지 더: `pv` 의 규칙 객체에 `acr` **키 자체가 없으면** 거기서도 `cr` 로
판정한다(`security.js:311`). 하지만 `acr` 배열을 적는 정상적인 ACP 에서는
해당되지 않는다.

`cr` 이 무엇인지도 타입마다 다르다 (`app.js` 의 `resolve_cr`):

| 타입 | `cr` |
|---|---|
| AE (`ty=2`) | 그 AE 의 **`aei`** |
| remoteCSE (`ty=16`) | `csi` |
| cnt / cin / sub / fcnt / grp / smd | 만들 때의 `X-M2M-Origin` (자동으로 채워진다) |
| **acp (`ty=1`)** | **없다** — `acp` 테이블에 `cr` 컬럼 자체가 없다 |

> 마지막 줄이 중요하다. ACP 의 `pvs` 를 잘못 주면 **생성자 폴백이 아예 없어서**
> 수퍼유저 말고는 아무도 못 고친다.

**실제 사례** — 운영의 `/Mobius/sch8` 은 없는 ACP 를 가리켜 잠겨 있는데,
(b) 에 해당하므로 자기 `aei` 로 풀 수 있다:

```
GET /Mobius/sch8  as Cstranger      -> 403
GET /Mobius/sch8  as SVczINc68eh    -> 200   (= 그 AE 의 aei)
```

## ACP 템플릿 — 예외 세 가지만 쓴다

`/Mobius` 아래에 공용으로 두고 `acpi` 로 참조만 한다.
**리소스마다 만들지 않는다.** ACP 개수를 한 자리로 유지하는 것이 목표다.

`acop` 비트: `1` CREATE · `2` RETRIEVE · `4` UPDATE · `8` DELETE · `16` NOTIFY · `32` DISCOVERY

| 조합 | 값 | 뜻 |
|---|---|---|
| 전권 | **63** | 1+2+4+8+16+32 |
| 조회·탐색만 | **34** | 2+32 |
| 생성만 | **1** | 올리기만, 못 봄 |
| 생성·조회·탐색 | **35** | 1+2+32 (기본 정책의 "누구나" 부분) |

### 패턴 A — 완전 비공개 (`$creator` 지원이 필요하다)

"이 AE 의 데이터는 정해진 곳만 본다. 단 장치는 자기 것을 계속 읽고 쓴다."

```json
{"m2m:acp": {
  "rn": "acp-private-<이름>",
  "pv":  {"acr": [
    {"acor": ["$creator"], "acop": 63},
    {"acor": ["<팀AE>", "<관리자>"], "acop": 63}
  ]},
  "pvs": {"acr": [{"acor": ["<관리자>", "Sponde"], "acop": 63}]}
}}
```

`$creator` 가 없으면 장치가 자기 데이터도 못 읽는다. 그 토큰이 구현되기
전까지는 패턴 B 를 쓴다.

### 패턴 B — 올리기는 열고, 보는 것만 제한 (지금 바로 쓸 수 있다)

"장비는 계속 데이터를 올려야 하는데 조회는 우리만."
**장치 ID 를 몰라도 된다** — 실측으로 확인했다.

```json
{"m2m:acp": {
  "rn": "acp-ingest-<이름>",
  "pv":  {"acr": [
    {"acor": ["<소유AE>", "<팀AE>", "<관리자>"], "acop": 63},
    {"acor": ["all"], "acop": 1}
  ]},
  "pvs": {"acr": [{"acor": ["<관리자>", "Sponde"], "acop": 63}]}
}}
```

### 패턴 C — 보는 건 열고, 만드는 것까지 막기

"읽기는 지금처럼 열되 아무나 데이터를 넣지는 못하게."

```json
{"m2m:acp": {
  "rn": "acp-readonly-<이름>",
  "pv":  {"acr": [
    {"acor": ["<소유AE>", "<관리자>"], "acop": 63},
    {"acor": ["all"], "acop": 34}
  ]},
  "pvs": {"acr": [{"acor": ["<관리자>", "Sponde"], "acop": 63}]}
}}
```

> 대원칙을 그대로 ACP 로 옮기고 싶으면 `{"acor":["all"],"acop":35}` +
> 소유자 전권이다. 다만 그건 기본 정책과 같으므로 **ACP 를 걸 이유가 없다.**

## 잠그는 단위는 AE 하나

**AE 에 한 번 붙이면 그 아래 트리 전체에 적용된다.** 실측 (컨테이너 3단 +
CIN + `la` + 탐색, 아래는 전혀 안 건드림):

| 대상 | 붙이기 전 | AE 에만 붙인 뒤 (제3자) | 같은 시점 (허용 원본) |
|---|---|---|---|
| AE | 200 | **403** | 200 |
| c1 / c2 / c3 | 200 | **403** | 200 |
| c3 의 `la` | 200 | **403** | 200 |
| 탐색 `?fu=1` | 200 | **403** (0건) | 200 |
| c3 에 CIN 생성 | 201 | **403** | 201 |

그래서 **컨테이너나 CIN 에는 붙이지 않는다.** 붙일 이유가 없고(상속되므로),
붙이는 순간 관리 대상이 수만 개가 된다.

> 한 AE 안에서 일부만 다르게 해야 하면 — 대개 AE 를 나누라는 신호다.
> 그래도 필요하면 컨테이너에 직접 걸 수 있다. 아래 "컨테이너에 걸면" 참고.

## 운용 우려 세 가지 — 실측

### ① `acpi` 에 ACP 를 둘 이상 넣으면

**OR(합집합)이다.** 하나라도 통과시키면 통과한다. 교집합이 아니다.

| 대상 | Cteam | Cdev | Cother |
|---|---|---|---|
| AE (`acp_team`) | 200 | 403 | 403 |
| `shared` (`[acp_team, acp_dev]`) | **200** | **200** | 403 |

함정이 셋 있다.

**평가 순서를 정하는 것은 `acpi` 배열이 아니라 ACP 이름의 사전순이다.**
`select_acp_in`(`sql_action.js:2062`)은 `whereIn` 인데 `ORDER BY` 가 없다.
`acp.ri` 가 PK 이고 `ri` 는 구조화 경로(`/Mobius/<AE>/<ACP 이름>`)라 MySQL 이
PK 순서로 돌려준다. 계측:

```
요청순=[acp_mmm_dev, acp_zzz_empty]  반환순=[acp_mmm_dev, acp_zzz_empty]
요청순=[acp_mmm_dev, acp_aaa_empty]  반환순=[acp_aaa_empty, acp_mmm_dev]   ← 뒤집힘
```

**`pv` 에 `acr` 키가 없는 ACP 를 만나면 거기서 평가가 끝난다.**
`security.js:311` 이 생성자 비교 결과를 돌려주고 `return` 한다 — 뒤에 남은 ACP 는
아예 안 본다. `pv: {}` 는 `HTTP 201` 로 그냥 만들어진다. 앞의 순서 문제와
겹치면 **이름이 앞서는 빈 ACP 하나가 나머지 권한을 통째로 무효화한다.** 아래
두 줄은 운영자가 적은 `acpi` 순서가 같고 ACP 이름만 다르다:

| 구성 | Cowner | Cdev | Cother |
|---|---|---|---|
| `[acp_mmm_dev, acp_zzz_empty]` | 200 | **200** | 403 |
| `[acp_mmm_dev, acp_aaa_empty]` | 200 | **403** | 403 |

**`lookup.acpi` 는 `varchar(200)` 이다.** `ri` 22자 기준 7개가 한계이고 8개부터
`HTTP 500` 이다. `400` 이 아니라 `500` 이라 원인을 알 수 없다. 기존 값은
깨지지 않고 롤백된다.

```
 4개 (JSON 101자) -> 200,  저장 4
 6개 (JSON 151자) -> 200,  저장 6
 8개 (JSON 201자) -> 500,  저장 6 (그대로)
```

### ② 컨테이너에 걸면 — 합쳐지지 않고 덮어쓴다

`select_acp_cnt`(`sql_action.js:2017`)는 `acpi` 가 비어 있고 `ty == '3'` 인
동안만 위로 올라가, **가장 가까운 비어 있지 않은 `acpi` 하나**를 반환하고 멈춘다.

| 대상 | Cteam | Cdev | Cother |
|---|---|---|---|
| AE (`acp_team`) | 200 | 403 | 403 |
| `open` (빈 `acpi` → AE 상속) | 200 | 403 | 403 |
| `devonly` (`acp_dev`) | **403** | **200** | 403 |
| `devonly/sub` (빈 `acpi` → `devonly` 상속) | **403** | 200 | 403 |

`Cteam` 은 AE 에서 전권인데 `devonly` 에서 403 이다. **AE 의 ACP 를 아무리 고쳐도
그 컨테이너에는 안 먹는다.** 장애 대응 때 "AE ACP 봤는데 맞는데요?" 가 되는
전형적인 함정이다. `acpi` 가 빈 리소스에는 아무나 ACP 를 붙일 수 있으므로
(`resource.js:2228`), **장치가 자기 컨테이너를 잠가 팀을 막는** 일이 가능하다.

### ③ AE 와 컨테이너를, 또는 컨테이너끼리 다르게 하려면

②의 메커니즘이 그대로 답이다. 예외를 둘 컨테이너에 `acpi` 를 직접 건다.
그 아래는 자동 상속된다. 세 가지를 지켜야 한다.

**덮어쓰기라서 AE 규칙을 다시 다 적어야 한다.** 예외 ACP 를 새로 쓰지 말고
**AE ACP 를 복사한 뒤 규칙을 더하거나 뺀다.** 팀·관리자 규칙을 빠뜨리면
관리자 자신이 잠긴다 — 배포의 `/Mobius/sch8` 이 그 상태다.

**CSE 전역 ACP 는 불가능하다.** `/Mobius` 에 `acpi` PUT 은 `HTTP 405` 이고,
상속 체인도 `ty == '3'` 동안만 올라가 AE 에서 멈춘다. **AE 마다 걸어야 한다.**

```
설정                    AE      AE/c1   AE/c1/deep
아무 데도 안 걸음         200     200     200
CSEBase 에만 걸음        200     200     200      ← PUT 자체가 405
AE 에 걸음              403     403     403
```

**방안 A 의 집합이 커진다.** AE 단위면 568개인데 컨테이너 단위로 흩어지면
이론상 최대 30,281개다. "예외만 잠근다" 를 지키면 실제로는 수십 개라
문제없지만, 컨테이너 `acpi` 가 늘어나는지는 감시해야 한다.

## 사고를 막는 규칙 다섯

전부 실측으로 확인된 함정이다.

### ① 접근해야 하는 원본을 `pv.acr` 에 빠짐없이 적는다
위의 ⚠ 항목. 생성자라고 자동으로 남지 않는다. 장치 ID 를 모를 때는
패턴 B(`all` 에 CREATE) 또는 `$creator` 토큰을 쓴다.

### ② `pvs` 에 관리자를 반드시 넣는다
`pvs` 는 "이 ACP 자체를 누가 고칠 수 있는가" 다. `acp` 테이블에는 `cr` 컬럼이
**없어서** 잘못 주면 생성자도 못 고치고 **수퍼유저만** 복구할 수 있다.
게다가 `pvs` 를 **수정**할 때는 아무 검증도 없다(생성 시에만 검사한다).

### ③ `acpi` 를 걸기 전에 그 ACP 가 실재하는지 확인한다
서버가 **존재하지 않는 ACP 를 가리켜도 그대로 받는다.** 그러면 그 리소스는
생성자 말고 아무도 못 쓰게 잠긴다. 운영 데이터에 실제로 하나 있다 —
`/Mobius/sch8` 이 없는 `/Mobius/acp_sch1` 을 가리켜 잠겨 있다.

**ACP 를 먼저 만들고, 응답의 `ri` 를 그대로 복사해서 붙인다.**

### ④ ACP 를 지우기 전에 참조를 먼저 푼다
지우면 ③과 같은 상태가 된다. 찾는 질의는 싸다 (배포 서버 **119ms**):

```sql
select ri, acpi from lookup
 where ty in (1,2,3,5,9,10,13,14,16,23,24,27,28,38,39,91,92,93,94,95,96,97,98)
   and acpi like '%<지울 ACP 의 ri>%';
```

`ty` 목록으로 좁히는 것이 핵심이다. CIN(`ty=4`)까지 넣으면 6,620만 행
풀스캔이 된다.

### ⑤ `actw`(시간창)는 UTC 기준이다
KST 09:00 을 원하면 `0 0 0 * * *` 이다. 형식은 `초 분 시 일 월 요일` 6자리
정확히 일치만 지원한다 (`1-5`, `1,3` 같은 범위·목록은 안 된다).

## 잠겼을 때 복구

| 상황 | 누가 풀 수 있나 | 방법 |
|---|---|---|
| 없는 ACP 를 가리켜 잠김 (dangling) | **생성자** 또는 수퍼유저 | `PUT {"m2m:<ty>":{"acpi":[]}}` |
| 정상 ACP 인데 `acr` 에 자기가 없어 잠김 | `acr` 에 적힌 원본 또는 수퍼유저 | 같음 |
| ACP 의 `pvs` 를 잘못 줌 | **수퍼유저만** (`acp` 에는 `cr` 이 없다) | 같음 |

AE 의 생성자는 그 AE 의 **`aei`** 다 — `X-M2M-Origin` 에 `aei` 를 넣으면 된다.
컨테이너 등은 만들 때 쓴 `X-M2M-Origin` 이 `cr` 로 들어가 있다.

관리 UI 에 **"잠금 해제"** 버튼을 두고 수퍼유저로 대행하게 하면 이 절차가
사람 손을 덜 탄다.

## 켜기 전에 관찰한다

지금 가장 큰 고통은 **켜 보기 전에는 뭐가 막힐지 모른다**는 것이다.
순서를 이렇게 한다.

```
1) 거부 로그를 먼저 켠다      누가·무엇을·어느 ACP 때문에 막혔는지 남긴다
2) 관찰 모드로 ACP 를 건다     판정은 하되 막지 않고 로그만 남긴다
3) 하루~이틀 로그를 본다       막힐 뻔한 것이 의도한 것뿐인지 확인
4) 관찰 모드를 끈다            그때부터 실제로 막는다
```

2번이 없으면 3번을 할 수 없고, 그러면 "일단 걸고 터지면 푼다" 가 되어
지금 상황으로 되돌아간다. **거부 로그 + 관찰 모드가 ACP 를 쓸 수 있게 만드는
최소 조건이다.**

지금은 거부가 나도 서버 로그에 **한 줄도 안 남고**, 응답도
`{"m2m:dbg":"ACCESS DENIED"}` 뿐이라 어느 ACP 의 어느 규칙 때문인지 알 수 없다.

## 관리 UI 가 해야 할 것

| 화면 | 내용 | 지금 가능한가 |
|---|---|---|
| ACP 목록 | `ri` / `pv` / `pvs` / **참조하는 리소스 수** | 가능 (119ms) |
| ACP 상세 | 규칙을 사람이 읽는 형태로 (`acop 63` → "전권") | 가능 |
| 리소스의 실효 권한 | 상속을 풀어 "실제로 적용되는 ACP" | 계산 필요 |
| **시뮬레이터** | "이 원본이 이 리소스에 이 연산을 하면?" → 허용/거부 + 근거 | **서버 지원 필요** |
| 거부 로그 | 최근 거부 목록 (누가·무엇을·왜) | **서버 지원 필요** |
| 잠금 해제 | `acpi` 비우기 (수퍼유저 대행) | 가능 |
| **소유자 누락 경고** | `pv.acr` 에 소유 AE 가 없으면 저장 전에 경고 | 필요 |

**시뮬레이터가 핵심이다.** 이게 있으면 "걸어 보고 터지는지 확인" 을 안 해도
된다. `security.check` 를 그대로 쓰되 실제 실행 없이 판정만 돌려주는 진단용
엔드포인트 하나면 된다.

## 설정으로 빼야 할 것

| 값 | 위치 | 지금 | 해야 할 일 |
|---|---|---|---|
| `useaccesscontrolpolicy` | `mobius.js:88` | `'disable'` 고정 | conf 로. **기본값은 지금 값 유지** |
| `usesuperuser` | `mobius.js:50` | conf 에 없어 `'Sponde'` | conf 에 명시 |
| 관찰 모드 | 없음 | — | conf 로 켜고 끈다 |

`useaccesscontrolpolicy` 라는 이름이 오해를 부른다. 실제 의미는
"**`acpi` 가 없는 리소스의 기본 정책**" 이다:

| 값 | 생성·조회·탐색 | 수정·삭제 |
|---|---|---|
| `'disable'` (지금 / 대원칙) | 누구나 | 생성자만 |
| `'enable'` | **생성자만** | 생성자만 |

대원칙대로면 **`'disable'` 이 정답이고 바꿀 일이 없다.** 이름만 바로잡는다
(예: `defaultAccessPolicy: 'open-read'`).

`usesuperuser` 는 그 문자열만 알면 모든 ACP 를 우회한다. conf 로 빼고
운영에서는 추측하기 어려운 값으로 바꾸는 것이 좋다.

## 부하 대책과의 관계

이 방식(AE 단위 + 공용 ACP 소수)을 지키면 `acpi` 가 채워진 리소스가
**수십 개**를 넘지 않는다. 그러면 **방안 A** — "`acpi` 가 채워진 `ri` 집합을
메모리에 들고, 조상 중에 하나도 없으면 DB 를 치지 않는다" — 가 거의 모든
요청에서 적중한다.

지금 ACP 상속 조회는 **3,518,444회 / 전체 질의의 6.8%** 인데, 그중 실제로
ACP 를 찾아내는 것은 사실상 없다. 이 운영 방식 + 방안 A 면 **0 에 수렴한다.**

반대로 컨테이너마다 붙이는 방식으로 가면 집합이 커져 효과가 줄고, 결국
`acpl`(실효 ACP 를 행에 미리 풀어 두기)까지 가야 한다.

> **운영 규칙 하나(AE 단위로만 붙인다)가 성능 대책을 결정한다.**

## 요약

**평소** — 아무것도 하지 않는다. 생성·조회는 누구나, 수정·삭제는 생성자만.

**잠글 때**

```
1) 패턴 A/B/C 중 하나로 /Mobius 아래 ACP 를 만든다
   - 장치가 올리기만 하면 패턴 B — 장치 ID 를 몰라도 된다
   - 장치가 읽어야 하면 패턴 A + $creator (서버 지원 필요)
   - pv.acr 에 팀 AE / 관리자를 적는다
   - pvs.acr 에 관리자를 반드시 넣는다
2) 응답의 ri 를 복사해 그 AE 에만 건다
   PUT /Mobius/<AE>  {"m2m:ae":{"acpi":["<ACP 의 ri>"]}}
3) 관찰 로그를 하루 본 뒤 관찰 모드를 끈다
```

**풀 때**

```
PUT /Mobius/<AE>  {"m2m:ae":{"acpi":[]}}     (생성자 또는 수퍼유저)
```
