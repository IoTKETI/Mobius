# CIN 쓰기 경로 효율 분석 — 측정 기반

**날짜**: 2026-08-27
**질문 1**: CIN 생성/삭제 시 부모 `cnt` 갱신 흐름이 지금 구조로 최대 효율인가.
**질문 2**: `cin` 과 `cnt` 가 분리돼 있어 SQL 이 복잡하고 매번 2회 이상 호출된다.
DB 구조를 바꾸는 게 낫지 않나.

**방법**: 추측하지 않고 실측했다. `tools/golden/tap.js` 로 실제 실행되는 SQL 을
전부 기록하고, SQLite 로 규모별 벤치마크를 돌렸다.

---

## 0. 결론 먼저

| 질문 | 답 |
|------|-----|
| 지금이 최대 효율인가 | **아니다.** 다만 병목은 테이블 분리가 아니다. |
| 진짜 병목 | `get_cni_count` 의 **O(n) 재집계**. 컨테이너의 CIN 이 늘수록 선형으로 느려지고 상한이 없다. |
| 테이블 병합이 답인가 | **아니다. 오히려 손해다.** 삽입에서 0.012 ms 를 아끼는 대신 discovery 스캔이 2배 느려지고 `lookup` 이 16배 커진다. |
| 해야 할 것 | 스키마가 아니라 **재집계를 없애는 것**. 저장된 `cni`/`cbs` 를 믿을 수 있게 되었으므로 가능해졌다. |

## 1. CIN 1건 삽입에 실제로 도는 SQL — 9개

SQL tap 을 켜고 CIN 을 1건 POST 해서 기록한 것이다 (배경 하트비트 제외).

| # | SQL | 목적 | 비용 |
|---|-----|------|------|
| 1 | `select * from lookup where (ri=?) or (sri=?)` | 대상 컨테이너 해석 | PK/인덱스 1행 |
| 2 | `select * from cnt where ri=?` | 부모의 `mni`/`mbs` 로드 | PK 1행 |
| 3 | `select * from lookup where pi=? and ty='39'` | `tr`(transaction) 확인 | 인덱스 |
| 4 | `select acpi, ty from lookup where ri=?` | 접근 제어 확인 | PK 1행 |
| 5 | `insert into lookup (...)` | CIN 의 공통 속성 행 | PK 삽입 |
| 6 | `insert into cin (...)` | CIN 본문 행 | PK 삽입 |
| 7 | `UPDATE cnt SET cni=cni+δ, cbs=cbs+δ` | 부모 카운터 | **배치** (1초 debounce) |
| 8 | `UPDATE lookup SET st=st+δ` | 부모 stateTag | **배치** |
| 9 | `select lookup.st, count(*), sum(cin.cs) FROM lookup, cin where ...` | 한도 검사용 재집계 | **배치, 그러나 O(n)** |

7·8·9 는 `cnt_man` 이 1초 단위로 모으므로, 초당 100건이 들어와도 **1회로 합쳐진다.**
즉 요청당 실제 비용은 1~6 의 **6개** 이고, 그중 4개가 읽기다.

**요청당 SQL 은 이미 잘 눌려 있다.** `cnt_man` 을 만드신 판단이 정확했다.

## 2. 진짜 병목 — 9번 재집계는 O(n) 이다

```sql
select lookup.st, count(*) as cnt, sum(cin.cs) as size
  FROM lookup, cin
 where lookup.ri = ? and cin.pi = ?
```

이 문장은 **컨테이너에 든 모든 CIN 을 훑는다.** `cin_ri_idx(pi, ri, cs)` 커버링 인덱스
덕에 테이블 본체는 안 읽지만, 여전히 행 수에 비례한다.

### 실측 (SQLite, 같은 컨테이너)

| 컨테이너 CIN 수 | 9번 재집계 | `select cni, cbs from cnt` (저장값) |
|----------------|-----------|-----------------------------------|
| 20,001 | 1.181 ms | 0.146 ms |
| 100,001 | **12.740 ms** | 0.159 ms |

행 수 5배 → 재집계 **약 11배**. 저장값 조회는 **변화 없음**.

### 왜 이게 큰 문제인가

- 이 재집계는 **`cnt_man` flush 마다** 돈다 → 활성 컨테이너당 약 1초에 1회.
- `mni` 기본값이 `3153600000` 이라 컨테이너는 사실상 무제한으로 자란다.
- 100만 건이면 한 번에 약 127 ms. 활성 컨테이너 10개면 **초당 1.27초의 DB 시간**을
  재집계에만 쓴다 — 그 시점에 이미 못 버틴다.

### 왜 저장값을 안 믿고 있었나

`sql_action.js:504` 주석:

> `// SQLite: 저장된 cni 대신 실제 COUNT로 판단 (클러스터 환경에서 저장값 신뢰 불가)`

**그 불신에는 근거가 있었다.** 저장값을 유지하는 주체 중 **감소 쪽이 깨져 있었기 때문이다** —
`update_cnt_by_delete` 호출부가 `cs` 인자를 빠뜨려서 CIN 을 지워도 `cni` 가 안 줄었다
(2026-08-27 수정, 커밋 `ea40cbc`).

즉 **재집계는 그 버그를 가려 주던 안전망**이었다. 버그를 고친 지금은 사정이 다르다:

| 주체 | 방식 | 동시성 |
|------|------|-------|
| `cnt_man` flush | `cni = cni + δ` | 안전 (증분) |
| `delete_oldest` | `cni = cni - N` | 안전 (증분) |
| `update_parent_by_delete` | `cni = cni - 1` | 안전 (증분) |

**전부 증분이라 워커가 동시에 돌아도 서로 안 덮어쓴다.** 저장값을 믿을 조건이 갖춰졌다.

## 3. 테이블 병합 — 실측해 보니 손해다

"`cin` 과 `cnt` 가 분리돼 SQL 이 2회 이상 나간다" 는 지적은 사실이다.
그런데 그게 **얼마나 비싼지** 재보면 이야기가 달라진다.

### 얻는 것 — 삽입 1건당 0.012 ms

`lookup` + `cin` 두 INSERT 를 한 테이블 INSERT 로 합쳐서 20,000건 삽입:

| 구조 | 총 시간 | 건당 |
|------|--------|------|
| 분리 (INSERT 2회) | 587 ms | 0.0294 ms |
| 병합 (INSERT 1회) | 348 ms | **0.0174 ms** |

**절약: 건당 0.012 ms.**

### 잃는 것 — discovery 스캔 2배, 테이블 16배

`lookup` 은 discovery 에 계속 스캔된다 (`select ... from lookup where pi=? and ty=?`).
여기에 `con`(CIN 본문)을 합치면 행이 커져 같은 스캔에 더 많은 페이지를 읽는다.

현실적인 페이로드(`con` 500바이트, 20,000건)로 측정:

| | discovery 스캔 (`select ri ... where ty=4`) | 테이블 크기 |
|---|---|---|
| 분리 `lookup` | **11.05 ms** | **0.69 MB** |
| 병합 | **22.62 ms** | **11.20 MB** |

**discovery 가 2배 느려지고, 스캔 대상 테이블이 16배 커진다.**

(`con` 을 10바이트로 두고 재면 차이가 안 난다. 그래서 처음 측정은 무의미했고
현실적인 크기로 다시 쟀다.)

### 비교

| 항목 | 크기 |
|------|------|
| 병합으로 아끼는 것 (삽입 1건) | **0.012 ms** |
| 재집계가 쓰는 것 (CIN 100k) | **12.740 ms** |

**약 1,000배 차이다.** 게다가 병합은 대규모 마이그레이션이고, 되돌리기 어렵다.

### 지금 구조가 왜 맞는가

`lookup`(공통 속성) + 타입별 테이블은 **class table inheritance** 패턴이다.
Mobius 에서 이게 잘 맞는 이유:

- `lookup` 을 좁게 유지해야 **discovery 와 subtree 순회가 빠르다.** 이 두 가지가
  oneM2M 미들웨어의 핵심 읽기 경로다.
- CIN 본문(`con`, longtext)은 대부분의 쿼리가 안 읽는다. 분리해 두면 스캔에서 빠진다.
- 타입마다 컬럼이 크게 다르다 (`sub` 12개, `cnt` 8개, `ae` 9개…). 한 테이블로 합치면
  50개 가까운 nullable 컬럼이 된다.

**분리는 실수가 아니라 설계다.**

## 4. 그래서 무엇을 할 것인가

### 안 1 — 저장값을 믿는다 (권장)

`get_cni_count` 가 매번 재집계하는 것을 멈추고, `cnt.cni`/`cnt.cbs` 를 읽는다.

```
현재:  flush → UPDATE cni/cbs → select count(*), sum(cs)  ← O(n)
개선:  flush → UPDATE cni/cbs → select cni, cbs from cnt   ← O(1)
```

| 얻는 것 | 대가 |
|--------|------|
| 100k 기준 12.74 ms → 0.16 ms (**80배**) | 저장값이 틀어지면 한도 판정이 틀어진다 |
| 컨테이너가 커져도 비용이 안 늘어난다 | 드리프트 감시 장치가 필요하다 |

**드리프트 원인과 대응**:

| 원인 | 지금 상태 | 대응 |
|------|----------|------|
| CIN 삽입 | `cnt_man` 이 증분 | 문제 없음 |
| 한도 초과 밀어내기 | `delete_oldest` 가 증분 | 문제 없음 |
| CIN 단건 삭제 | `update_parent_by_delete` 가 증분 (`ea40cbc` 로 수정됨) | 문제 없음 |
| **subtree 배경 삭제** (`delete_descendants_background`) | **감산 없음** | 드리프트 발생 |
| **만료 스윕** (`delete_lookup_et`, 수정 후) | **감산 없음** | 드리프트 발생 |
| 프로세스 중단, 직접 DB 조작 | — | 드리프트 발생 |

즉 **안 1 은 안 2 와 짝을 이뤄야 한다.**

### 안 2 — 주기적 정합 맞추기 (안 1 과 함께)

재집계를 없애는 대신, **주기적으로 한 번씩** 실제 값으로 교정한다.

- 컨테이너별로 하루 1회, 또는 flush N회마다 1회.
- 기존 `select_count_ri` 를 그대로 쓰면 되므로 새 쿼리가 필요 없다.
- 이미 있는 정리 작업들(`del_orphan_resource` 등)과 같은 자리에 걸면 된다.

### 안 3 — 요청당 읽기 4개를 줄인다 (선택, 효과 작음)

1~4번 SELECT 중 1·2·4 는 같은 컨테이너를 세 번 조회한다.

- 1번이 `lookup` 행을, 2번이 `cnt` 행을, 4번이 다시 `lookup.acpi` 를 읽는다.
- 1번과 4번은 **같은 행**이다. 1번 결과를 재사용하면 4번이 없어진다.
- 1번과 2번은 `lookup JOIN cnt` 한 번으로 합칠 수 있다.

요청당 6 → 4 로 줄어든다. 다만 전부 PK/인덱스 1행 조회라 절대 비용이 작다.
**안 1 을 끝낸 뒤에 볼 일이다.**

### 하지 말 것 — 테이블 병합

3절의 측정대로 순손실이다.

## 5. 권장 순서

| 순서 | 작업 | 근거 |
|------|------|------|
| 1 | **안 1 + 안 2** — 재집계 제거 + 주기적 정합 | 100k 기준 80배, 규모가 클수록 커짐 |
| 2 | 만료 스윕 수정 (별도 문서) | 스윕이 감산을 안 하므로 안 2 가 먼저 있어야 안전 |
| 3 | 안 3 — 요청당 읽기 축소 | 효과 작음, 나중 |
| — | 테이블 병합 | **하지 않음** |

**주의**: 안 1 을 안 2 없이 넣으면 안 된다. subtree 배경 삭제와 만료 스윕이
감산을 안 하므로, 재집계라는 안전망만 걷어내면 카운터가 서서히 부풀어 오른다.

## 부록 — 측정 재현 방법

SQL 기록:

```bash
# preload 로 tap 을 설치하고 서버를 띄운다
node --require <scratch>/preload-tap.js mobius.js sqlite
# 요청을 보낸 뒤
cat tools/golden/out/*.jsonl
```

규모별 벤치마크는 SQLite 파일에 CIN 을 대량 삽입한 뒤
재집계 쿼리와 저장값 조회 쿼리를 각각 반복 실행해 평균을 냈다.
병합 비교는 `lookup`+`cin` 구조와 단일 테이블 구조를 같은 DB 안에 만들어
같은 데이터를 넣고 삽입/스캔을 각각 측정했다.
